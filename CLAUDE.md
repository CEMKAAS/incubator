# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Инкубатор" — a Russian-language Android app (Jetpack Compose + Room, offline-only) for tracking poultry egg incubation.

Two entities, and keeping them apart matters: an **`Incubator`** is the physical device (name and capacity required, brand / model / price / note optional, auto-turn and auto-airing flags required), and a **`Batch`** (закладка) is one clutch of eggs inside it — species, start date, egg count. Creating a batch materializes a full per-day schedule of temperature / humidity / turning / airing rows (`Value`, one per incubation day), a set of daily reminder times (`Time`), and its species chips (`Species`).

**The naming is now literal, and it should stay that way.** Anything named `Incubator*` is the device and lives in `ui/incubator/`; anything named `Batch*` is a clutch and lives in `ui/batch/`. Before schema v2 the table called `Incubator` actually held batches and every batch screen was named after the incubator, so old commits and any stale branch will read the opposite way.

Two deliberate exceptions, both in `ui/batch/`: the AppMetrica event names (`"Инкубатор"`, `"Incubator Edit"`) keep their original wording so historical analytics stay comparable — `"Incubator Archive"` no longer fires at all, since the silent archive button it belonged to is gone and finishing now reports `"Полное завершение"` / `"Досрочное завершение"` — and user-facing copy like "заложили в инкубатор" or "убрать из инкубатора" is correct as written — the eggs really do go into the device.

All UI copy is hardcoded Russian string literals in Kotlin — `strings.xml` holds only `app_name`.

## Build & test

Requires JDK 17+ and an Android SDK path in `local.properties` (`sdk.dir`). `java` is not on the shell PATH in this environment — use Android Studio's bundled JBR or set `JAVA_HOME` before invoking Gradle. Verified against both JDK 17 and the Android Studio JBR (25).

```powershell
.\gradlew.bat assembleDebug          # build
.\gradlew.bat build                  # debug + release + lint + unit tests
.\gradlew.bat installDebug           # build + install on connected device/emulator
.\gradlew.bat test                   # host unit tests (app/src/test)
.\gradlew.bat connectedAndroidTest   # instrumented tests (needs device)
.\gradlew.bat testDebugUnitTest --tests "ru.zaroslikov.incubator.ExampleUnitTest"   # single test
.\gradlew.bat clean
```

`:app` has effectively no tests — only the generated `ExampleUnitTest` / `ExampleInstrumentedTest`. The one real test is `:domain`'s `IncubationPeriodTest`; because `:domain` is a plain JVM module, `gradlew :domain:test` runs in seconds with no emulator, which makes it the natural home for further tests of the species logic. Real verification of a change is still `gradlew build` (which also runs lint on debug and release) plus running the app.

`lint` is part of `build` and **fails the build on errors**. `ReminderWorker` guards its `NotificationManagerCompat.notify` call with an explicit `POST_NOTIFICATIONS` check specifically to satisfy lint' `MissingPermission`; do not drop that guard.

`build` also assembles the **minified** release now, so it takes a minute longer and R8 runs on every full build. That is deliberate: minification breaks only at runtime and only in release, so the earlier it is exercised the better. What it cannot catch is still up to a person — install the release APK and open it (see `app/proguard-rules.pro` for what exactly is at risk). An unsigned release APK can be signed with the debug key for that: `apksigner sign --ks ~/.android/debug.keystore --ks-pass pass:android --ks-key-alias androiddebugkey app-release-unsigned.apk`.

Git in this repo may report "dubious ownership"; fix with `git config --global --add safe.directory D:/Work/_Project/Incubator`.

## Toolchain and dependency versions

`gradle/libs.versions.toml` is the **single source of truth** — the root and app build scripts declare no inline versions, and plugins are applied via `alias(libs.plugins.…)`. Add new dependencies to the catalog, not as coordinate strings.

Constraints worth knowing before bumping anything:

- **AGP 9 supplies Kotlin itself** for both `com.android.application` and `com.android.library`. Applying `org.jetbrains.kotlin.android` is now a hard error ("no longer required for Kotlin support since AGP 9.0"). There is no `composeOptions.kotlinCompilerExtensionVersion` any more — the Compose compiler *is* the Kotlin plugin.
- **`:domain` is the one module that needs an explicit Kotlin plugin** (`org.jetbrains.kotlin.jvm`), since AGP only supplies Kotlin to Android modules. It is also why `:domain` declares `kotlinx-coroutines-core` explicitly — it gets nothing transitively from AndroidX. That dependency is `api`, not `implementation`, because `Flow` appears in `ItemsRepository`'s signatures.
- **Every plugin must be declared in the root `build.gradle.kts` with `apply false`.** Applying `com.android.library` with a version directly in `data/build.gradle.kts` fails with "the plugin is already on the classpath with an unknown version" once `:app` has pulled AGP in.
- `kotlin-parcelize` was removed: `Parcelize`/`Parcelable` are used nowhere. `ksp` is applied only in `:data` — `:app` has no code generation left.
- **KSP pins the Kotlin version.** KSP publishes no releases on the Kotlin 2.4 line, so Kotlin cannot go past 2.3.x while Room is generated through KSP. Check `com.google.devtools.ksp:symbol-processing-gradle-plugin` on Maven Central before raising `kotlin`.
- **compileSdk 37 is forced by AndroidX** — `core-ktx` 1.19 and its siblings refuse to compile against 36.
- **`targetSdk` is 37, which means edge-to-edge is mandatory on Android 15+.** The app never calls `enableEdgeToEdge()` and does not manage insets explicitly, so it relies entirely on Material3 defaults. The likely trouble spot, which lint does not flag (it reports 0 errors): the root `Scaffold` in `InventoryApp` applies `systemBars` content insets *and* every screen nests its own `Scaffold` + `TopAppBar` that applies status-bar insets again, so top spacing can be counted twice. Verify on an Android 15+ device before shipping.
- `kotlinOptions` was replaced by the `kotlin { compilerOptions { jvmTarget … } }` block.
- Material icons are no longer transitive from material3; `material-icons-core` is declared explicitly (the BOM still pins it, at its final 1.7.8). Every icon the app uses — `ArrowBack`, `Close`, `DateRange`, `Info`, `Notifications`, `Add`, `Settings`, `Menu`, `MoreVert` — lives in *core*, so `material-icons-extended` is not needed.
- **`buildConfig = true` is on, for two fields only**: `VERSION_NAME`, which Gradle fills in itself, and `RELEASE_DATE`, a `buildConfigField` sitting next to `versionName` in `app/build.gradle.kts`. Both are read by «О приложении». The date is its own field because there is nowhere else to get it — an APK carries a build time, but that changes on every rebuild and is not a release date — and it sits beside `versionName` precisely so that bumping one without the other takes effort.
- **The release build is minified, and `app/proguard-rules.pro` is the reason it still works.** R8 renames whatever is not reachable by a call, and three things in this app are reached **by name**: `ReminderWorker` (WorkManager keeps the class name as a string in its own database, so a renamed worker means already-scheduled reminders stop firing — for people who updated, not for you), `IncubatorBackupAgent` (`android:backupAgent` is a name in the manifest, and unlike activities and receivers it is not covered by the keep rules AGP generates from it), and the constants of `ThemeMode` (`AppSettings` stores the enum **name**, so renaming them would silently return everyone who chose light or dark to «системная»). Everything else is left to the libraries' own consumer rules — an extra `-keep` does not make a build safer, it just turns shrinking off where it was working. All three break only in release and only at runtime: the debug build is not minified, the tests run against it, and lint knows nothing about any of this, so **a release build has to be installed and opened before it ships**. Verified that way: 6.0 MB against 21.3 MB unminified, and the app creates an incubator, lays a batch, schedules its reminder, loads both ad surfaces and remembers a dark theme across a process restart.
- **`ui-tooling` is `debugImplementation`.** It is the layout inspector's half of Compose — a developer tool that costs the user classes and composition metadata and gives them nothing. `ui-tooling-preview`, which `` annotations need at compile time, stays a normal `implementation`.

## Modules

Four Gradle modules; the dependency graph is `:app → :data → :domain`, `:app → :domain` and `:app → :design`.

**`:design` is the theme and the domain-free composables, and it depends on nothing of the project's.** Package `ru.zaroslikov.incubator.design`: `theme/` (`Color.kt` with the M3 schemes and `DesignColors` / `DesignPalette`, `Type.kt` with the Google Fonts and `DesignType`, `Theme.kt` with `IncubatorTheme` and `ThemeMode`) and `components/` (the sheet primitives of `SheetForm.kt`, `SlidingTabs`, `ChoiceChip`, `TileRow`, `TruncatedText`, `LoadingState`, `FocusClear`, `SheetDraft`, `SystemBars`, `NumberFormat`). Its two resources are the ones those files read — `font_certs.xml` and `ic_close_design.xml` — so a screen in `:app` that wants that icon writes `ru.zaroslikov.incubator.design.R.drawable.ic_close_design`; the app's own `R` no longer holds it. The line is drawn by imports, not by taste: a composable whose signature needs `:domain` or `settings/` is part of a screen and stays under `ui/` — `ScheduleTable.kt` edits `ValueUiState`, `IncubatorTabParts.kt` formats money in a `Currency`. Compose and Material are `api` dependencies of the module because `Modifier`, `Color` and `TextStyle` stand in its public signatures. **`ThemeMode` moved with the theme, and the R8 keep rule in `app/proguard-rules.pro` names its new package** — `AppSettings` stores the enum *name*, so the package change costs nobody their choice, but a rule left pointing at `ui.theme` would keep nothing and the release build would quietly return everyone to «системная».

**Room is confined to `:data` and must stay there.** `room-runtime` is an `implementation`
dependency, so `:app` cannot see `RoomDatabase` at all — that is why `:data` exposes
`provideItemsRepository(context)` instead of handing out `InventoryDatabase`. If you find
yourself wanting `api(libs.androidx.room.runtime)`, add a factory function to `:data`
instead. Verify with `gradlew :app:dependencies --configuration debugCompileClasspath | grep androidx.room` — it must return nothing.

**Exporting and importing the whole database lives in `:data` for the same reason** — `DatabaseTransfer.kt`, `exportDatabase` / `importDatabase`. The database file name, the schema version and Room's open connection are all details of that module, and the settings screen never sees any of them: it hands over a `Uri` from the system document picker and gets back an `ImportResult`. The file itself is transferred rather than a JSON dump, the export is checkpointed out of WAL first, and a successful import kills the process — the reasoning for all three is in `data/CLAUDE.md`. **`wipeDatabase` — «Удалить все данные» — is in the same file and deletes the database file rather than the rows**, for the same reason the transfer moves a file: `DELETE FROM` over eight tables would need keeping in step with the schema by hand, and a forgotten table would leave live rows behind «удалить всё». It restarts the process afterwards, like an import.

WorkManager lives in `:app`, not `:data`, because `ReminderWorker` builds a notification
using `R.drawable.baseline_egg_24` and a `PendingIntent` into `MainActivity`. The
`WorkRepository` interface still lives in `:domain`, so ViewModels depend on the abstraction.

## Architecture

Manual DI, no Hilt/Koin:

- `InventoryApplication` (also `Configuration.Provider` for WorkManager) builds an `AppDataContainer` exposing `itemsRepository`, `workRepository`, `appSettings` and `transferController`.
- **`settings/DataTransferController.kt` is in the container rather than a ViewModel on purpose.** Moving the database in or out has to outlive the screen that started it: `importDatabase` is a plain blocking call, so leaving the settings screen mid-import did not stop the swap — it only removed anyone who could ask for the restart the swap makes mandatory, leaving the app running on a closed connection until the next screen crashed. The controller owns the transfer state, and after a swap it restarts the process itself.
- **`settings/AppSettings.kt` is the third kind of storage, and it is deliberately not the database.** It wraps two `SharedPreferences` files, and what divides them is the Android backup, not tidiness. `app_prefs` holds what the person chose for themselves — `remindersEnabled`, the master switch on the settings screen, `themeMode` — «Системная / Светлая / Тёмная» under «Оформление» — and the two units, `temperatureUnit` and `currency` (below), all stored as the enum *name* so that inserting a fourth mode can never re-point an old number at a different theme. `MainActivity` collects `themeModeFlow()` and hands `ThemeMode.isDark()` to `IncubatorTheme`, with the initial value read synchronously so a dark launch never flashes cream first. **The system is told too**: `AppSettings.syncNightMode()` — from the setter and once in `InventoryApplication.onCreate`, since prefs travel in Android backups and `UiModeManager` state does not — calls `setApplicationNightMode` on Android 12+, so the starting window (`values` / `values-night` `windowBackground`) follows the app's choice rather than the phone's; below 12 `MainActivity.paintWindowForTheme` sets the window background before `setContent`, which covers everything but the splash frame. The line between it and Room is not tidiness — the database is the user's data and travels between phones as a file (see below), while a preference belongs to *this installation*: a reminder switch riding along inside someone else's backup would turn on notifications nobody asked for. The switch is honoured by `ReminderWorker`, which returns `Result.success()` without notifying, rather than by cancelling the scheduled work: the times and their texts belong to the batch, and cancelled work could not be put back — the form is the only place that knows what to put.
- **`settings/Units.kt` — `TemperatureUnit` (°C / °F) and `Currency` (₽ $ € ₸ Br ¥) — are display settings, and the database never learns about them.** Temperature is stored in Celsius always: the `:domain` regimens are written in it, schedule files travel in it, and a batch laid under one unit must read under the other without touching its rows. The whole conversion lives at the screen boundary in `ui/batch/ValueFormat.kt` — `formatTemp(unit)` / `formatTempOrDash(unit)` for an absolute reading, `formatTempDelta(unit)` for a difference (×1.8, no +32 — a deviation or a spread is the same on both scales apart from the length of a degree), `toTempFieldText(unit)` / `toCelsiusOrNull(unit)` for the input fields — and every threshold, tolerance and average stays in Celsius underneath; `MeasureTile` / `DeviationBar` get their `minor` / `major` / `scale` through `unit.scale(...)` so the severity comes out identical. **Fahrenheit is kept to two decimals precisely so the round trip is lossless**: 37.8 °C is exactly 100.04 °F and comes back as exactly 37.8, while one decimal would have turned every regimen saved under °F into 37.78 — `UnitsTest` pins that for the regimen's values. The one input-side consequence: `filterMeasureInput(integerDigits)` takes the digit budget from `TemperatureUnit.integerDigits` (2 / 3), because 100.4 °F does not fit two. Composables read the current pair from `LocalUnits` (`ui/LocalUnits.kt`, provided in `MainActivity` from `AppSettings.unitsFlow()` beside the theme); the three ViewModels whose UI state holds temperature *strings* — `AddBatchViewModel`, `BatchDetailViewModel`, `CustomSpeciesViewModel` — take `AppSettings` and pass `temperatureUnit` into `toValueUiState(unit)` / `toValue(unit)` and the measurement form, since a `CompositionLocal` cannot reach them. **Currency is only a sign**: `formatMoney(amount, currency)` appends `Currency.symbol`, nothing is converted by any rate, and the card under the chips says so — the app does not know what currency a sum was typed in. Both are `app_prefs` keys (a person's choice, so they travel in the backup) and both go into the AppMetrica profile as «Градусы» / «Валюта».
- **`device_prefs` is the second settings file, and it exists because backup rules work on files, not on keys.** It holds the properties of *this installation*: `installationId` (the AppMetrica profile id), `remindersMigrated`, `adsVersionCode`, `guidePending` / `addIncubatorPending`. `res/xml/backup_rules.xml` and `res/xml/data_extraction_rules.xml` exclude that one file — restored on a second phone, those keys would put two installations into one analytics profile, mark the legacy-work cleanup as done where it never ran, and tell a brand-new phone it had already seen the guide. There was no way to exclude a single key from `app_prefs.xml`, so the split had to be by file; keys written before it moved across on first launch (`AppSettings.migrateInstallationKeys`), because starting to read `installationId` from a new file would have handed every updating user a new identity and cut their history in analytics at that version.
- **The database, by contrast, does travel in the backup — and `IncubatorBackupAgent` is what makes that copy whole.** Auto backup copies files as they are, while Room keeps the database in WAL mode: recent writes sit in the sibling `-wal`, which is excluded (a journal belonging to another database either replays foreign pages onto it or stops it opening). So the agent runs `checkpointForBackup` from `:data` before the copy — the same `wal_checkpoint` `exportDatabase` performs, and for the same reason. Unlike the export it swallows a failure: the export promises the user a complete copy and may refuse, a backup happens without anyone asking and having none is worse than having one a little older.
- `ui/AppViewModelProvider.Factory` is a single `viewModelFactory` holding one `initializer` per ViewModel, pulling dependencies off the container via the `CreationExtras.inventoryApplication()` extension. **Every new ViewModel must be registered there**, and screens obtain them with `viewModel(factory = AppViewModelProvider.Factory)`.
- Adding a repository query touches four places: `ItemDao` (entity types), the mapper if a new type appears, the `ItemsRepository` interface in `:domain`, and `OfflineItemsRepository`, which maps at the boundary (`Flow` via `kotlinx.coroutines.flow.map`).
- **A `Flow` of a single row is `Flow<X?>`, always.** For a non-nullable single-row result Room generates `error("The query result was empty…")`, and because it is a `Flow` the query re-runs on every change to the table: deleting a batch while its sheet is open, or archiving a device while `IncubatorViewModel` is subscribed, threw straight into the collector. A missing row is an ordinary answer — `getIncubator`, `getBatch`, `getValue` and `getBatchValueForDay` all return it, `getUser()` always did — and the `filterNotNull()` calls in three ViewModels only started working once the type admitted a null.
- **`User` is the eighth table and holds exactly one row: the owner's profile** — name, farm, city, avatar (JPEG bytes) and `vkUserId` since v19. Key fixed at `1`, no `autoGenerate` — the phone has one signed-in account at a time and the row belongs to it (it is written only through `AccountRepository.editProfile` and emptied at sign-out, see «Profile and VK ID»), and a fixed key makes saving a plain insert-with-replace instead of a search for the previous row. An absent row and an empty profile are the same answer to the same question, so `OfflineItemsRepository.getUser()` collapses both into `User()` and nothing above the repository has to know the difference. `User` compares `avatar` by content (overridden `equals` / `hashCode`, pinned by `UserTest`), or every Room answer would redraw the profile.
- Domain models and Room entities are separate classes with identical field names. The domain copies keep the **same mutability** as the entities (`Value.id`, `idPT`, `airingCount`, `airingTime`, `over`, `temp`, `damp`, `note` are `var`; `Time` is all `var`; `Batch` only `arhive`) because UI code mutates them in place — see `ScheduleTransforms.setAutoIncubator` / `setIdPTTime`. Turning them into `val` breaks the UI.
- `Batch.airing` / `Batch.over` do **not** duplicate `Incubator.autoAiring` / `autoTurn`. The device fields are its capability; the batch fields record what was actually used when its schedule was generated, and those values are already baked into its `Value` rows — do not rewrite them retroactively. A *new* batch takes them from its device as a **default**, once, at creation — «Автоматика инкубатора», two switches on the batch form — and the person laying the clutch may turn either off for that clutch alone: the device turns eggs, this tray is turned by hand. The switches are creation-only for the rule above, and toggling one rewrites the two columns of the schedule the form is about to save, never the rows of an existing batch (`ui/CLAUDE.md`). **`Batch.type` is creation-only too, and more so**: the schedule was generated for that bird and another bird has another term, so the edit form shows the species as a locked field and `AddBatchViewModel.updateForm` refuses the change (`ui/CLAUDE.md`).
- **`Measurement` is fact, `Value` is plan** — do not merge them. `Value` says what day 15 *should* be (37.8 °, 55 %); `Measurement` says what the user read off the device at 22:18, and it hangs off that day's `Value` row via `idValue`. Both sides are `Double?` since v5, so the deviation is plain subtraction. The deviation shown in the batch sheet is the difference between the two, and the thresholds behind «в норме / небольшое / заметное отклонение» (±0.2 / ±0.5 ° and ±3 / ±7 %) are the app's own — the mockup only ever draws the «заметное» case. `Measurement.over`, `airingCount` and `airingTime` are counts — turns, airings and minutes per airing — not the automation flags of the same name on `Batch`. Today's date decides *which* day row is current, never which measurements belong to it.
- **A measurement can be taken for the whole incubator, and it is still `Measurement` rows — one copy per running batch, tied together by `Measurement.groupId` (schema v17).** The thermometer sits in the device, not in the clutch, so «Внести замер» under the batch list (`IncubatorMeasurementSheet`, `ui/incubator/`) writes the same reading into the current-day `Value` row of every running batch of that incubator, all copies carrying one UUID; a reading typed inside a batch has `groupId = null` and belongs to that batch alone. Copies rather than a device table, because everything that reads measurements — the batch sheet, the day analytics, `batchTotals`, the averaged schedule that goes into an export file — reads them per batch and per day and should stay ignorant of the device; only the incubator sheet reads the column, to show a group as one journal line and to edit or delete it whole (`ItemsRepository.getMeasurementsForDays` / `insertMeasurements` / `updateMeasurements` / `deleteMeasurements`, list writes so a group lands or fails together — and **`getMeasurementGroup(groupId)` for editing and deleting, because the copies of a group are found by the mark, not by today's rows**: a batch finished after the reading still holds its copy, and a group edit or delete must reach it there too). **A copy edited inside a batch sheet stays in its group**: `MeasurementForm.groupId` carries the mark from `Measurement.toForm` back into `persist`, since Room's `@Update` writes every column and a form that forgot the mark would silently pull the copy out of the group — only the incubator sheet ever sets it, the batch form only preserves it. Two rules carry it. **The day row is chosen by `incubationDay()` in `ui/batch/IncubationDay.kt`, the same function `BatchDetailViewModel.load` uses**, so a copy lands in exactly the row the batch will show as «Замеры за сегодня» — a batch with no such row (unparseable start date, day past the schedule) gets no copy, and the sheet says so instead of skipping it silently. And **automation is applied per copy** (`measurementCopies` / `updatedCopies` in `ui/incubator/IncubatorMeasurements.kt`, pinned by `IncubatorMeasurementsTest`): the temperature is shared, but a batch whose incubator turns its eggs gets `over = null`, exactly as `persist` would strip it — the same reading yields different copies where the automation differs, and that is correct. The tiles' «цель» in that sheet is `averagePlan()`: the mean of the selected batches' day plans, field by field over the batches that have that field (a batch on automation, with `null` turns, does not drag the norm towards zero) — there is one thermometer, and the only place it can be held is between what the batches ask for, so the mean is the point the deviation is measured from; a target of one batch shown over a reading of the whole device would be a lie about the others.
- **A batch holds one species and one breed, and `Batch.breed` — a text field — is where it lives.** «Ломан Браун» beside «Хайсекс» in one tray is laid as **two batches**: the batch form takes any number of breeds at creation (`BreedUiState` rows — name, eggs, price each), and «Заложить 2 закладки» writes one batch per row through its own `insertBatchWithSchedule`, with copies of the day rows and reminder rows and the breed as a tail on the title («Весенняя партия — Хайсекс», `BatchUiState.toBatches()` / `splitBatchTitle`). Editing shows the breed as one text field — renamable, never addable: another breed is another batch, since this one already owns its eggs, its regimen and its measurements, and `AddBatchViewModel.addBreed()` refuses while `isEditing` (the form hides the button as well). This is deliberately the *third* model the breed has had. Schema versions 15–17 kept breeds as rows of a `Batch_breed` table, several per batch, each with its own eggs, hatch, cull and two prices, and a candling's cull was split over `Batch_candling_breed`; every number of the batch was then held twice and reconciled by `Batch.withBreeds`, the finish dialog asked per breed, the candling sheet culled per breed, and the statistics cut a batch between its rows. One rule replaced all of it: **a breed's hatch, cull and money are its batch's** — `Batch.eggAllEND`, `Batch_candling.rejected`, `Batch.price` — and nothing keeps a second ledger inside a batch. `MIGRATION_17_18` joins the row names back into the column and drops both tables (`data/CLAUDE.md`). What survives from the row era: `knownBreeds(batches, type)` in `Batch.kt` (the dropdown under the field — that species only, newest first, folded case-insensitively), `Batch.breed` in the AppMetrica «Порода» parameter (one string, series unbroken), and `HatchOutcome` — `finishedOnTime(outcome, dateEnd)` takes the dialog's hatched count and chick price as one value so the two cannot part ways between dialog, ViewModel and `:domain`. `BatchOutcomeTest` in `:domain` pins the three writers and the suggestions, `BatchSplitTest` in `app/src/test` the split, `BatchTransactionTest` / `MigrationTest` in `data/src/androidTest` the round trip and the migration.
- **`Batch.price` is the number the user typed, and `pricePerEgg` says which number it was** — per egg or for the whole clutch. Do not normalise one into the other on save: the egg count can still change, and «22 ₽ за яйцо» would then be lost. The two summary tiles under the field are derived, never stored, and the per-egg one uses integer division — the app has no kopecks anywhere else.
- **`Batch.endReason` says *how* a batch ended, and it is the only thing that does.** A finished batch (`arhive == "1"`) with a blank reason ran its term; a non-blank one was stopped early, and then `eggAllEND` is deliberately `0` — «hatched none» is a result, not a missing one, and «средний вывод» on the incubator screen counts such a batch like any other.
- **Those two fields together are the batch's status, and `BatchStatus` in `:domain` is how you ask for it** — `Batch.status` returns `Active` / `Hatched` / `Stopped`, the third being the early-stopped batch shown as «Не завершено» on the card and gathered under the «Не завершённые» filter chip. It is derived, never stored: a third column could be made to disagree with the two that actually get written at finish time, and both of those are written in the same `updateBatch`. `arhive` is checked first, so a stray reason on a running batch reads as running rather than as stopped. `BatchStatusTest` in `:domain` pins the table, including that zero chicks alone does not make a batch `Stopped` and that `reopened()` returns it to `Active`. **Each direction has exactly one writer, both in `Batch.kt`**: `stoppedEarly(reason, dateEnd)` puts a batch into `Stopped` — from the batch sheet's «Завершить досрочно» and from the incubator archive, which stops a whole device's worth at once, hence the date being a parameter rather than a `Date()` inside — and `reopened()` brings it back to `Active`. Write those five fields by hand somewhere new and the two paths will disagree about what an interrupted batch looks like. **Prefer `status` over hand-rolled `arhive != "0"` checks in new UI code** — the three-way question is now the common one, and the two-way one is `status != BatchStatus.Active`. `chickPrice` / `chickPricePerHead` are the same literal-storage pair as `price` / `pricePerEgg`, for chicks instead of eggs. **`BatchUiState` carries all three even though the batch form never shows them**: editing goes through `toBatch()`, and a state that dropped them would wipe the reason and the chick price off any batch edited after it finished.
- **A batch carried to term with chicks ends in a celebration — `HatchCelebrationDialog` (`ui/batch/`), fireworks over «Поздравляем!» and a short summary — and `HatchSummary` in `domain.stats` is the summary.** `hatchSummaryOf(batch, rejected, termDays)` is the one place the figures come from — eggs, cull, hatched, `rate` (hatched over *laid*, the `StatsSlice.rate` denominator), the species' term, and the money through `batchFinanceOf` (made public for it), so the number on the party card cannot disagree with what «Статистика» and «Финансы» print a minute later. Money is only what was typed — `invested` with an egg price, `income` with a chick price, `profit` **only with both**: with one addend missing the difference invents a loss or a gain. `List<HatchSummary>.combined()` folds a party of breeds into one row, summing money only when every batch carries that price. The summary travels in the finish effects (`BatchDetailEffect.Finished(hatched)`, `FinishGroupEffect.Finished(summaries)`) rather than being re-read: the batch is already written, and the ViewModel held the cull and the term anyway. **Only for chicks**: a stopped batch and a zero hatch are grief, not a party — the effect carries `null` and the sheet simply closes; for a party the sum decides, and then every finished breed is listed, the zero one included. `IncubatorScreen` hosts it (`celebration`, a `rememberSaveable` with `HatchSummariesSaver`, so a rotation does not end the party) as the one point all three on-time paths pass through, reports `Events.HATCH_CELEBRATED` there, and asks for the RuStore review on its «Отлично» (below). `HatchSummaryTest` in `:domain` pins the arithmetic; `HatchCelebrationTest` in `app/src/test` the opening line. The fireworks are `design/components/Fireworks.kt` — a `Canvas` of bursts computed as pure functions of elapsed time (drag plus gravity), driven by `withFrameNanos` into a state only the draw lambda reads, so the dialog over it never recomposes per frame; frequent for six seconds, then sparse, and over after forty — the card may be read for a while, and an empty canvas redrawn at sixty frames a second for all of it would be waste. Bursts spawn only in the bands above and below the card (`originBands`): the card is opaque, and the first version — bursts anywhere in the upper half — showed a party with no sparks. **Both finish ViewModels carry a `finishing` guard** (reset in `load`): the confirm button stays live until the write returns as an effect, and a second tap in that window wrote the batch twice and left a second `Finished` in the channel, which the next opening of that sheet would have consumed as «close at once and celebrate the old batch».
- **A second `:domain` package, `domain.stats`, holds the arithmetic behind the «Статистика» tab** — `IncubatorStats.kt`, one entry point `incubatorStats(batches, candlings)`. It sits there rather than next to the screen for the same reason `BatchStatus` does: summing eggs and dividing percentages is arithmetic over batches, not Compose work, and `IncubatorStatsTest` pins it with a plain JVM test instead of an emulator. The rule worth carrying in your head before touching it: **eggs are counted over all batches, percentages only over finished ones** (`StatsSlice.finishedEggs` / `finishedHatched`), because a running batch has `eggAllEND = 0` and would halve every rate without breaking anything visible. A slice with nothing finished yet has `rate == null` — «неизвестно», not «ноль». **Both denominators are part of the answer, not an implementation detail** — `activeEggs` / `activeBatches` name the difference, and the screen prints it under every figure, because «700 яиц» beside «429 вылупилось» reads as a sum that does not add up until someone says the rest is still in the incubator. Породы are `Batch.breed` (one text field per batch, see below — not the `Species` chips, which are extra *species*), so a breed row is simply the batches of that species wearing that name, with their whole eggs, hatch and cull; a batch with a blank breed collapses into a `NO_BREED` row **per species**, because breeds are counted inside their bird — `SpeciesStats.breeds` is the only breed cut there is, and `IncubatorStats.breeds` merely flattens it, so no second count can drift from the first. «Отбраковано» is `Batch.eggRejected` **plus** the batch's `Candling.rejected` — the same two-ledger sum «Осталось» uses, which is why the tab needs `ItemsRepository.getCandlingsFor(incubatorId)`, one JOIN rather than a subscription per batch.
- **`domain.stats` has a second entry point, `incubatorFinance(incubatorPrice, batches)` in `IncubatorFinance.kt`, and it is the whole «Финансы» tab.** No table and no column was added for it either: the app knows exactly three money facts — `Batch.price` / `pricePerEgg` (what the eggs cost), `Batch.chickPrice` / `chickPricePerHead` (what the chicks fetched) and `Incubator.price` (what the device cost) — and everything else is arithmetic over them. Three rules carry the file. **Потери are a slice of the расход, not an addition to it**: they are the price of the eggs that never hatched, already inside what was spent, and summing them alongside would charge those eggs twice — which is also why `lostEggs` counts actual eggs instead of dividing money by an average that no batch was bought at. **Every average has its own denominator, and only priced batches enter it**: a batch whose price nobody typed contributes zero to the numerator, so letting its eggs into `pricedEggs` would quietly deflate «расход на яйцо»; `chickCost` narrows further to *finished* batches, exactly as `StatsSlice.rate` does and for the same reason. **The incubator's own price enters both `expense` and `balance`** — the same money bought it, and a hatchery is not in the black until it has earned that back too. The stored field is `eggsExpense` (eggs only) and `expense` is the sum, because the per-unit figures (`expensePerEgg`, `chickCost`) divide by eggs and chicks and equipment is bought per neither; `invested` is the eggs half under its own name. The price of that decision is that a young hatchery reads as loss-making, so **the screen must always name the two parts** — the expense tile is captioned «инкубатор + яйца» and the incubator card spells the addition out. `payback` therefore divides by `profitOnBatches` (profit *before* equipment), never by `balance`, which already has the equipment subtracted — dividing that by the same price would deduct it twice. The two are tied: `balance >= 0` exactly when `payback >= 100`. `BatchFinance.profit` is `null` while a batch runs, not zero: its money is spent and its chicks are not sold, and any number there would read as a loss that has not happened.
- **`Batch.time` moves no day boundary, and `Batch.eggRejected` is a second cull ledger.** `time` («ЧЧ:ММ», blank on anything created before schema v10) records the hour the eggs went in; the incubation day stays a whole-day diff from `Batch.data`, because hanging it on the clock would shift every day and every schedule row with it. **One thing does read the hour** — `batchFinishMoment()` in `ui/incubator/FinishedBatchPrompt.kt`, which decides *when* the «Инкубация завершена» prompt appears: the term runs out on the hatch date at the laying hour, not at its midnight. A blank time means the whole hatch day counts as elapsed. `eggRejected` is the cull typed by hand in the batch form — eggs lost *between* candlings, cracked or rotten — and it does not replace `Batch_candling`, which records what each candling removed as an event with a day. `BatchDetailViewModel.rejectedTotal` adds the two and «Осталось» subtracts the sum, so the same egg entered in both places is counted twice.
- **`Batch.hidden` is «в архиве» in the UI, and `Batch.arhive` is not** — despite the name. `arhive` has meant «incubation is over» since v1 and drives the status chip, the active/finished split and the hatch-rate average; `hidden` means only «not shown in the incubator's list». Two fields because one could not do both: with a single flag you could either hide every finished batch at once or hide none. Only a finished batch can be hidden — `IncubatorViewModel.setBatchHidden` refuses an active one, and `reopened()` clears the flag. **The two flags do go up together, though, in `BatchDetailViewModel.archive(finished, hide, onDone)`**: «Убрать в архив» on a running batch finishes it and files it away in a single `updateBatch`, because the menu item promises the archive and a two-press version of it is the same action asked for twice. The other two finish paths — the batch sheet's own button and the «Инкубация завершена» prompt — pass `hide = false`: they record a result, they do not put anything away. **A hidden batch still counts everywhere else** — header figures, the species chart, the hatch-rate average: hiding takes a card off the screen, it does not unmake the clutch.
- **`Incubator.hidden` is the same «в архиве», one level up, and it is the device's only flag of that kind.** It means «выведен из работы»: the card leaves the start screen, everything inside the device becomes read-only (below), **and every batch still running in it is stopped** — `Batch.stoppedEarly(reason, dateEnd)` with the reason `StartScreenViewModel.ARCHIVE_END_REASON` («Инкубатор переведён в архив»), one date across all of them, reminders cancelled batch by batch the way `deleteIncubator` cancels them. A clutch in a device taken out of service is not a clutch: left running it would keep eggs nobody is warming in the «в работе» tile at the top of the start screen and keep waking its owner at eight every morning. Already-finished batches are untouched, result and foreign `endReason` included — their outcome is recorded, and the device's archive has no business rewriting it. **Coming back out of the archive undoes none of that**: it lifts the read-only lock, and each batch is returned to work one at a time by its own «Вернуть в инкубацию» (`reopened()`), which is also the only thing that knows what to do with the result. An automatic revival could not tell a batch stopped *by* the archive from one stopped before it — and «Отключили свет» is a different story from «Инкубатор переведён в архив». Because the press writes an outcome that does not undo itself, **it is the one archive action in the app that asks first** (`ConfirmArchiveIncubatorDialog`, and only when there is something to interrupt); the batch-level «Убрать в архив» is not comparable — it opens the real finish dialogs. There is no second flag beside `hidden`, and there should not be: a batch has an end of incubation (`arhive`) to be separate from, a device has no end at all, so the batch rule «only a finished batch can be hidden» has nothing here to attach to and `StartScreenViewModel.setIncubatorHidden` refuses nothing. **An archived incubator is read-only, and that is the second half of what the flag means**: `IncubatorUiState.readOnly` is `incubator.hidden`, and while it holds, the screen offers no way to add, edit, finish, hide, reopen or delete a batch, the «Инкубация завершена» prompt does not appear, and `BatchDetailSheet(readOnly = true)` drops its measurement form, the row edit/delete actions, both candling buttons, the day-plan editor and «Завершить инкубацию» — everything that writes. Viewing is untouched: sums, deviations, the measurement log and «Аналитика» all still work. A finished batch of such a device is the same sheet in the same state — since it is read-only for its own reason too (below), the device's archive adds nothing to it. The ViewModels refuse the same operations rather than trusting the UI (`IncubatorViewModel.deleteBatch` / `setBatchHidden` / `unarchiveBatch`), because a composition can outlive the state it was built from. The lock itself is lifted where it was applied — «Вернуть в список» on the start screen — so the *lock* needs no confirmation; what the dialog above asks about is the batches, which the same press stops for good. **The pencil in the header stays live**: it edits the *device*, and the rule is about its batches; a name or a capacity typed in while the incubator sits in the archive is a correction to a record, not a change to a clutch.
- **Deleting a device is the one place a cascade is not enough**: `ON DELETE CASCADE` runs from `Incubator` through `Batch` down to days, measurements, candlings and reminder rows, but the scheduled reminders live in WorkManager, outside the database, so `deleteIncubator` cancels them batch by batch first — the same thing `IncubatorViewModel.deleteBatch` does, for the same reason.
- Room DB `incubator_database`, **version 19**, `exportSchema = true` (schemas land in `data/schemas/`). `fallbackToDestructiveMigration()` was **removed on purpose** — with it, every version bump silently wiped users' projects. Migrations are hand-written in `InventoryDatabase`; **add a new one for every schema change rather than bumping the version alone**, and remember that editing a `*Entity` class *is* editing the schema. Why each existing migration is shaped the way it is — and the SQLite 3.18 constraints behind the create-copy-drop dance — is in `data/CLAUDE.md`.
- **Every foreign key carries an index, and v14 is where that became true.** `Batch.incubatorId`, `Batch_value.idPT`, `Batch_measurement.idValue`, `Batch_time.idPT`, `Batch_species.idPT`. Before it the whole database had three indexes, all unique ones put there for integrity. Deleting paid the most: `ON DELETE CASCADE` made SQLite scan `Batch_measurement` end to end for each of the 17–31 `Batch_value` rows going away, and deleting a device multiplied that by its batches. A new foreign key needs its index in the same commit — Room prints a warning about it that nothing in this project treats as an error.

**Four screens hang off the app menu on the start screen** — «Профиль» (`ui/profile/`, below), then «Аналитика», «Настройки», «О приложении» in `ui/menu/`, all ordinary navigation destinations rather than sheets. They replaced the old info icon and its `InfoBottomSheet` («Инкубатор v1.00» plus a button into the VK group): «О приложении» says all of that and more, and two buttons in one header leading to the same place invite the question of how they differ. The AppMetrica event `"Информация"` moved with the content and keeps its name, so the old series stays comparable.

**«Аналитика» has no cards of its own, and that is the point.** It reuses `StatsTab` and `FinanceTab` verbatim, feeding them `incubatorStats(allBatches, allCandlings)` and `incubatorFinance(sumOfDevicePrices, allBatches)` — those functions never cared how many devices a list of batches came from. A second implementation of «the same sums, but over everything» would drift from the first at the first formula change, and the farm would get two different answers to one question. What genuinely differs between the two scopes is six captions, and `TabScope` in `IncubatorTabParts.kt` holds all six — «инкубатор + яйца» against «инкубаторы + яйца», and so on. Feeding the sum of every device price in as `incubatorPrice` is honest arithmetic, not a hack: inside, that number is one addend of the expense and the denominator of payback, and both meanings survive the summation.

Navigation: each screen file declares its own `object …Destination : NavigationDestination` with `route`, `titleRes`, `itemIdArg`, and `routeWithArgs`; all of them are wired in `ui/navigation/InventoryNavGraph.kt`, which also fires the AppMetrica screen events. Route args are declared `NavType.IntType` while the ViewModels read them as `Long` — keep that pairing when adding routes.

**State: every ViewModel is MVI, and `ui/mvi/MviViewModel.kt` is the contract.** Three types per screen — `@Immutable data class …State` (one object holding everything the screen draws), `sealed interface …Intent` (one variant per thing the user or the screen can do; `onIntent()` is the ViewModel's only public entry) and `sealed interface …Effect` (one-shot events — «saved, close the sheet», «open the picker» — delivered through a buffered `Channel` so one sent before the screen re-subscribes waits rather than vanishes). A screen reads `state.collectAsStateWithLifecycle()`, sends `viewModel.onIntent(…)`, and takes effects through `CollectEffects(viewModel) { … }` (`ui/mvi/MviCompose.kt`, which collects only while `STARTED`, because an effect is «navigate» and navigating from the background crashes). Callback parameters like `save(onSaved)` are gone: the intent is `Save`, the answer is `Effect.Saved(id)`. **Where the state comes from is the one thing the base leaves open**, and it does so for a documented reason. A form holds its input locally — `StatefulMviViewModel(initial)` with `reduce { copy(…) }` and `current`, its database flows collected inside `load()` with the previous `Job` cancelled — while a list screen holds nothing: its `state` is `combine(repository flows, private MutableStateFlow of local flags).flowOn(Dispatchers.Default).stateIn(viewModelScope, MviSharing.WhileVisible, …State())`, exactly the shape the old `StateFlow` screens had. A base class that filled one `MutableStateFlow` from a collector in `init` would have thrown that away: the collector would live as long as the ViewModel, i.e. while the screen sits in the back stack, and Room would go back to recomputing the farm for nobody. `MviSharing.WhileVisible` is the one `WhileSubscribed(5_000)` for the whole app, spelling out the default `replayExpirationMillis = Long.MAX_VALUE` because the return from the background rests on it: the subscription dies five seconds after the screen goes, the last state stays cached, and the screen shows what was there rather than its initial value while Room answers again. **A form that mixes local input with database hints keeps the hints in their own `StateFlow`** (`AddIncubatorViewModel.hints`): a single `combine` of both emits only once every source has, and three of them are Room, so the form would open on its initial state — or, on a re-subscription, on the previous incubator's fields — until the database replied. Mapping extensions (`toIncubatorUiState()` / `toIncubatorTable()`, `toValueUiState()` / `toValue()`) live next to the ViewModel that owns the state.

**Two rules go with that `stateIn`, and both were missing until they were looked for.** A `combine` that walks every batch of the household and runs the `:domain` arithmetic over them ends in `.flowOn(Dispatchers.Default)`: `stateIn(viewModelScope)` assembles on `Dispatchers.Main.immediate`, so without it that work happened on the frame-drawing thread on every answer from the database. And screens collect with **`collectAsStateWithLifecycle()`**, never `collectAsState()` — the latter keeps the subscription alive in the background, so `WhileSubscribed(5_000)` never fired and Room kept recomputing the whole farm for a screen nobody was looking at. `lifecycle-runtime-compose` has been in the graph since the settings screen needed `LifecycleResumeEffect`.

**A derived value that is expensive to compute is a field of the state, recomputed only in the reducer branches that change its inputs — never a `get()` on the state and never on every intent.** `BatchDetailViewModel`'s `totals` walks the whole schedule and every measurement of the batch, and the batch sheet reads the measurement form at its top level — so it recomposes on each typed character, and a `get()` would walk with it. Before MVI these were `by derivedStateOf` on the ViewModel; now the state carries `totals`, `rejectedTotal`, `candlingToday` (and `AddBatchViewModel`'s `knownBreeds`) as plain fields, and one private `withDerived()` refreshes them in the branches that handle an answer from the database or a change of day or species. The branch that handles a typed character does not call it. Cheap derivations — `isValid`, `canSave`, `status` — may stay as `get()` on the state; the test is whether the getter walks a list.

## Domain conventions that bite

- **Booleans and dates are stored as strings; every measurable quantity is a number.** `Batch.airing`, `Batch.over`, `arhive` are `String` columns holding `"true"/"false"` or `"0"/"1"`, converted at the UiState boundary — those are the *automation flags*, not counts. Dates are `dd.MM.yyyy` text; `getAllIncubator()` sorts by re-slicing that text into ISO order inside SQL, and the current incubation day is computed in the UI as a `TimeUnit.DAYS` diff between parsed `Date`s. `temp` and `damp` are `Double?` since schema v5 — `null` means «не задано».
- **Every one of those date strings goes through `ui/DateUtils.kt`, and nothing parses one by hand.** One `Locale("ru")` formatter for reading and writing, held in a `ThreadLocal` (`SimpleDateFormat` is not thread-safe, and these are called from composition and from `viewModelScope` alike; it also stopped the batch card from building up to five formatters per redraw). Two rules in it are load-bearing. **Parsing is strict** (`isLenient = false`): «5.8.2026» is still read, since the separators are explicit, but «32.13.2025» comes back `null` instead of silently becoming 1 February 2026 — a date nobody entered, given to a clutch as its term. And **an unparseable date is an ordinary answer, not a crash**: `dateToPickerMillis` replaced `convertDateStringToMillis`, which cut the string with `split(".")` and `toInt()` and took down the batch form on the tap that opened the date picker — a blank date is what every batch created before schema v10 carries, and a foreign one arrives with any imported database. `DateUtilsTest` in `app/src/test` pins exactly those inputs. The utilities used to live at the bottom of `IncubatorScreen.kt`, which made a screen into the app's date module.
- **Turning and airing are numbers since v9, and airing is two columns, not one.** `Value.over` / `Measurement.over` (how many turns), `airingCount` (how many airings) and `airingTime` (**minutes of a single airing**, so a day's total is count × time) are all `Int?` in both the plan and the fact. They used to be text — «2-3», «Авто», «2 раза по 5 минут» in the plan, minutes-of-one-airing in the measurement — which no arithmetic could reach without a regex, and which could not record two airings in one measurement at all. **`null` and `0` are different answers**: `0` is a quota («do not turn»), `null` is the absence of one — the field was cleared, or the incubator does it itself. Which of the two is displayed as «Авто» is decided by `Batch.over` / `Batch.airing`, carried into the sheet as `BatchDetailUiState.autoTurn` / `autoAiring`; the word is back only as a placeholder: a column handed to the automation is not editable at all — `ScheduleRow(autoTurn = …, autoAiring = …)` in the form's table and `DayEditor` in the sheet lock those two cells and print «Авто» in them — while the database still holds no text there. In a measurement `null` means «not recorded», and `actionCountsOf()` counts it as zero. **The measurement form asks for the minutes only** — one entry is one airing, so `MeasurementForm.airingCountValue` fills `airingCount` with `1` whenever the minutes are there; the plan, unlike the fact, sets both numbers itself.
- **Input rules for the numeric fields live in `ValueFormat.kt` too, and the caller picks which one applies.** `filterMeasureInput()` — temperature and humidity — allows at most **two digits before the separator and two after**, normalising a comma to a dot and refusing a separator as the first character: «37.55» goes in whole, «333.44» becomes «33.44», «33.333» becomes «33.33». Two integer digits is what these quantities actually use — incubation temperature lives between 36 and 39, working humidity between 30 and 90 — and **the cost is that «100» cannot be typed into the humidity field**; raising `MAX_INTEGER_DIGITS` to 3 is the one-line change if that ever matters. `filterCountInput()` — turning in the plan table and in the day editor, and the measurement form's minutes — deliberately does *not* follow that rule: those are whole counts, so it takes digits only and stops at a separator, turning a pasted «2.5» into «2» rather than «25». `filterAiringInput()` is a third rule, for the cell that holds two numbers — «Проветривание», in the batch form's schedule table and in the sheet's day editor alike, typed as «2×15»: one digit of times, then a «×» the mask inserts itself with the second digit, then up to two digits of minutes (`parseAiringCell()` / `airingCellText()` take it apart and put it back). `NumberField` does not filter at all: it serves every kind. `ValueFormatTest` in `app/src/test` pins every case, including the two the rule was written for.
- **Display follows the same two-decimal budget.** `formatTemp()` keeps one decimal and shows a second only when it carries information («37.0», «37.5», «37.55») — the regimen is written with one, and a bare «37» in a column of «37.5» reads as a different quantity. `formatDamp()` drops the fraction entirely when it is zero («60», not «60.0»). Both go through `Locale.US` so the separator is a dot, matching the mockup and the `:domain` schedule. The deviation line under each tile still rounds to one decimal for temperature and none for humidity — it summarises, it is not a reading.
- **Species knowledge lives in `:domain`, package `domain.incubation`, and `SpeciesCatalog` is the only door to it from `:app`.** `SpeciesCatalog(customSpecies)` answers every question about a bird — `incubationDays`, `isIncubationFinished`, `canFinishIncubation`, `isCandlingDay`, `candlingStage`, `schedule` — for the five built-in species *and* for the user's own (`CustomSpecies`, below). It looks among the custom ones first and falls back to the built-in `when`s. **The old free functions of the same names are `internal` to `:domain` now, on purpose**: a screen that called `incubationDays(type)` directly would see a custom species as «unknown» — no term, always ready to finish, no candling at all — and nothing would flag it. Every ViewModel that needs the answer collects `ItemsRepository.getCustomSpecies()`, builds a catalog and carries it in its UI state (`IncubatorUiState.catalog`, `BatchDetailUiState.catalog`, `AddBatchViewModel.catalog`); `SpeciesCatalog.EMPTY` is the built-ins only, the honest answer until the database replies. `SpeciesCatalog.BUILT_IN` is the picker's list of the five, in mockup order. `SpeciesCatalogTest` pins that the catalog agrees with the `when`s for built-ins and answers from the rows for a custom one. The files behind it:
  - `IncubationSchedule.kt` — `setIncubator(type)`, a ~1600-line `when` emitting one `Value` per incubation day. This is the default regimen (temperature, humidity, turns, airing) and the bulk of the module. Since v9 every value in it is a number: ranges collapsed to their **upper** bound («2-3» → 3, «4-6» → 6), «2 раза по 5 минут» became `airingCount = 2` + `airingTime = 5`, and «нет» became `0` — not `null`, which here would mean automation.
  - `IncubationPeriod.kt` — `isIncubationFinished(type, day)`, the per-species incubation length that triggers the "project finished" dialog, and `canFinishIncubation(type, day)`, which is `day >= days - 1`. Two functions rather than one because the questions differ: the first answers «the term is up» and decides whether to offer a result, the second answers «finishing is allowed now» and colours the batch sheet's button. `IncubationPeriodTest` pins both.
  - `Candling.kt` — `setOvoskop(type, day)`, which days offer candling (овоскопирование), and `ovoskopStage(type, day)`, which of the two or three that day is. The stage is counted by walking the days through `setOvoskop` rather than kept in a second table: the list of days is already there, and two copies would inevitably drift when a bird is added.
  - `ScheduleTransforms.kt` — `setAutoIncubator()` (clears every day's `airingCount` / `airingTime` / `over` to `null` when the project flag is set — since v9 the columns are numeric, and «no quota» is the absence of a number, never a zero) and `setIdPTTime` (stamps the parent batch id onto generated reminder rows before saving). `setIdPT`, its counterpart for the day rows, is gone: the schedule is now written by `ItemDao.insertBatchWithSchedule`, which stamps `idPT` inside its own transaction because that is the first moment the id exists.
  A batch is created by that one transaction — the row, the species chip, all 17–31 day rows and the reminder times together. Separately they were twenty to thirty commits with no promise of finishing: a process killed midway left a batch that is already in the list with half a schedule behind it, and both «День N/M» and the «Расписание» tab read row N as day N.
  - **Quail days 15–17 were corrected from 37.5 % to 65 % humidity.** The original file had them at `"37,5"` — the only humidity in the whole regimen written with a comma, and the shape of a temperature pasted into the wrong column: days 11–14 sit at 55 %, and the hatching phase needs *more* humidity, not a third less. Old builds and any archived batch created before this change still carry 37.5, since a batch keeps the `Value` rows it was generated with.
- **A user's own species is the same three facts stored as rows** — `CustomSpecies` (`Custom_species`: one row per species, name unique) with its `CustomSpeciesDay`s (`Custom_species_day`: the four plan figures of `Value` plus a `candling` flag, one row per day, unique per species and day). The term is the number of days; the candling days are the flagged rows; the schedule is the rows turned into `Value`s. It is in the database rather than in preferences because it is the user's data and travels with the export, the same reason `User` is a table. **A batch references its species by name only**, exactly as it does a built-in one (`Batch.type`, the `Batch_species` chip), so renaming a custom species cascades through both in `ItemDao.saveCustomSpecies`, in one transaction. **Editing its days does not rewrite the `Value` rows of batches already created from it** — those were baked at creation, the same rule as `Batch.airing` / `Batch.over` — but candling days are computed live from the catalog, so a running batch does follow a changed candling day. **Deletion is refused while a running batch uses the species** (`countActiveBatchesOfType`), because that batch would lose its term and its candlings mid-way; finished ones do not object, their plan is their own. Custom species are created from the batch form's species grid («Свой вид» tile) and managed — edited, deleted — under «Настройки»; both open the same `CustomSpeciesSheet` (see `ui/CLAUDE.md`).
- **Adding a built-in bird now means the four domain files and `SpeciesCatalog.BUILT_IN` (the picker's list) — nothing in the candling sheet.** It used to also mean `setOvoskopImage(day, type)`, a per-species `when` over days; that function is gone. Its whole species branch was an illusion: `chiken1`, `goose1`, `turkeys1`, `quail1` and `duck1` were one file byte for byte, as were all four third-stage images, so the picker sorted five species into three distinct pictures. What actually varies is the stage, and `ovoskopStage` in `:domain` already computes it, so `candlingImage(stage)` takes that instead. The same goes for the rest of that sheet's copy — `stageGoal()`, the steps, the reminders: incubation lengths differ between a hen and a goose, but what a first, second or third candling looks like through the shell does not. Note that the domain `when` blocks still fall through to `else` silently, so a bird missed there is a runtime behaviour bug, not a compile error.
- `isIncubationFinished` is the one function that was rewritten rather than moved: the old `endInc` took a Compose `MutableState` and opened the dialog itself. `IncubationPeriodTest` in `:domain` pins the new version against a verbatim copy of the old logic across every species and day, so changing a threshold there fails the test.
- **A finished batch is a source of regimen for the next one, in two forms.** The batch form's «Взять из архива» seeds the day table from any batch of the same species with `arhive = "1"` — either from its saved `Value` rows (`getValueArchive`) or from the average of its `Measurement`s folded back into `Value`s (`averagedScheduleOf` in `ui/batch/BatchAnalytics.kt`). The plan says what that batch set out to do; the average says what its incubator actually held, which is the more useful of the two once someone has run the bird before. Details of the picker are in `ui/CLAUDE.md`.

## Schedule files

**The day-by-day regimen of a single batch can leave the app as a file and come back into the table of a new one, and that is a different thing from the database copy in «Настройки».** The copy moves *everything* and replaces everything; a schedule file moves one thing — the day table («температура, влажность, поворот, проветривание» per day) and the species it belongs to — and replaces only the table: the form of a new batch takes it the way it takes a regimen from «Взять из архива», and the title, breeds, eggs, price, date, reminders and automation stay with the person laying eggs now. It deliberately carries nothing else about the source batch — not its name, not its result, not the measurements themselves — except **the average of those measurements folded back into a day table** (`fact`, with `measurementCount` beside it), so that the import can offer the same two things «Взять из архива» does: the plan the batch started with, or what the regimen actually turned out to be on that incubator. **Two more fields ride along for display only — the breed label and the incubator’s brand and model** (`breed`, `incubatorBrand` / `incubatorModel`, blank when not filled in): a regimen proven on a «Блиц Норма 72» for «Ломан Браун» is a different thing from a regimen of no provenance, and that is what decides whether to take it; but neither is written into the form, whose breed and device are its own. `FileProvenanceLines` prints them in the import dialog and in `FileSourceCard`, and only when non-blank. Everything about it lives in `app/src/main/java/ru/zaroslikov/incubator/transfer/`; `:data` knows nothing of it, since it never touches the database file.

- **Only a successful batch can be exported — `Batch.exportable` in `:domain`, next to `status`**: `Hatched` *and* `eggAllEND > 0`. The file is a regimen offered as an example, and only what worked is an example: a stopped batch was not run to the end, a batch with zero chicks has a result but nothing to share. The rule is in `:domain` so that the card menu (which hides the item rather than greying it out) and `ScheduleTransferController.exportOf` (which refuses) cannot disagree. `BatchStatusTest` pins the four cases.
- **The format is JSON with explicit fields, sealed with AES-256-GCM (`ScheduleFileCodec` + `ScheduleFileCipher`), extension `.incs`.** Not a SQLite file: eight tables of foreign keys are the reason the *database* moves as a file, while this is a species name and two lists of days, and a JSON written by hand survives every future migration — a renamed column changes nothing here. `format` is the version of the JSON, bumped only when the meaning of a field changes; the cipher container (`INCS` magic, one version byte, a 12-byte nonce, then ciphertext and tag) has its own. **The key is one constant for every install, and that is a condition of the task, not an oversight**: the file must open on somebody else's phone, where there is no account, no password and no key exchange, and a Keystore key would never leave the device it was made on. So the honest boundary is stated in the file's comment — the file is closed to other programs and to a casual look, and it cannot be changed unnoticed (GCM refuses a file with one flipped byte rather than producing a table with garbage in the cells) — but it does not protect against someone who unpacks the APK and takes the key. Nothing inside is worth that: an incubation regimen. Every file gets its own nonce, so two exports of the same batch differ byte for byte. `ScheduleFileCodecTest` (`app/src/test`, JVM) pins the round trip, the zeroed ids and the day order, the null-vs-zero distinction in the plan, «no measurements means no fact», the tamper refusal and the file name; it needs `org.json` on the test classpath (`testImplementation(libs.org.json)`), because the platform's copy is a stub in unit tests.
- **A custom species travels with the schedule, and an unknown one is created on import.** `ScheduleExport.customSpecies` carries the description (days, candling flags) when the batch ran on one; on the other phone `AddBatchViewModel.confirmImport` looks the name up in the catalog — case-insensitively, the same rule as `SpeciesCatalog.isNameTaken`, and it resolves to the catalog's own spelling because a batch references its species by name verbatim — and if nothing matches, saves it through `saveCustomSpecies` and selects it (`selectNewSpecies`, so the table does not draw the fallback regimen first). A file that has no description — a foreign build, an older format — still yields a species, built from the plan rows without candling days (`speciesToCreate`). **That save is the only database write an import makes, and it survives a cancelled form**; the dialog says so before the press. The catalog for that check is re-read from the repository rather than taken from `catalog` state, which in the first frames of the form is the built-ins only and would promise to create a species the unique index then rejects.
- **A species mismatch is a warning, not a refusal.** The form opens on «Курицы»; a file with a duck regimen, applied, switches the batch to «Утки» with its term and candlings — which is right when the eggs are duck eggs and wrong when the file was picked by mistake, and the app cannot tell which. So `ImportPreview.speciesChanges` puts a highlighted notice into the dialog («если яйца не этой птицы, файл не подходит») and the confirm button stays; a silent swap was the one thing ruled out, because the species tile on the other page is where nobody is looking at that moment.
- **What the import applies, in order**: the species (creating or switching, which regenerates the table), then the chosen list — the plan, or the measured average when the dialog offered it and the user picked it (`ArchiveScheduleSource`, the same enum the archive dialog uses; a file without measurements silently means the plan) — as the new `scheduleBase` with `applyAutoToSchedule` over it — the form’s own automation switches stay as they were and clear the columns they own, exactly as with a regimen from the archive — and `scheduleOrigin = ScheduleOrigin.File(export, source)`, so `FileSourceCard` («Режим из файла расписания» or «Среднее по замерам из файла расписания», species, term, measurement count, file date) stands over the table where `ArchiveSourceCard` or the disclaimer would. `ScheduleOrigin` is one sealed type for both sources because that slot holds exactly one of three things, and two independent fields would let two summaries stand at once.
- **`ScheduleTransferController` sits in `AppContainer` for the reason `DataTransferController` does**: a file write started from the card menu must finish even if the screen is closed, or the chosen location keeps an empty file with the batch's name. Reading is a plain `suspend fun read(uri)` in the form's own scope — a form closed mid-read simply does not get its table replaced, nothing is lost. Sharing goes through the same `FileProvider` path as the database copy, in `exports/schedules` under the cache (`file_paths.xml` already covers `exports/`), and `IncubatorScreen` launches the chooser on `ReadyToShare` exactly as `SettingsScreen` does. The file is named after the species first («Расписание Курицы — Весенняя партия.incs»), since that is what it will be looked for by.
- **AppMetrica**: `SCHEDULE_EXPORT` / `SCHEDULE_SHARE` from the export dialog's two buttons, `SCHEDULE_IMPORT` from the import dialog's confirm — not from the file pick, since a rejected file is not an import — with «Вид», «Дней», «Источник» (план or замеры), «Вид создан» and «Вид сменён».

## QR codes

**A device can wear a QR code, and scanning it opens that device's «Замеры за сегодня».** Everything Compose-free about it lives in `app/src/main/java/ru/zaroslikov/incubator/qr/`, the screens in `ui/qr/`. Four rules carry the feature.

- **The code holds a link, `incubator://measure/<id>`, and nothing else** — `QrLink.encode` / `QrLink.parse`, pinned by `QrLinkTest`. A custom scheme rather than `https://…` because an `https` link opens the app only through verified App Links, which need a domain and an `assetlinks.json` on it; without one Android 12+ hands the link to the browser. A custom scheme always reaches the app when it is installed. The price is that not every camera app offers to open such a link (Pixel and Samsung cameras do), which is what the in-app scanner is for. **The id is the row id in this installation's database**, not the name (renamed devices keep their sticker) and not the installation id: the database travels between phones as a file with its ids intact, so stickers printed before a transfer keep working after it. A code from someone else's phone points at an id this database does not hold, and both the scanner («Такого инкубатора нет в приложении») and `IncubatorScreen`'s `MissingIncubator` say so. **The manifest repeats the scheme and host verbatim** in `MainActivity`'s `VIEW` intent filter — it cannot see Kotlin constants, and if the two drift the camera stops offering the app.
- **Generation and recognition are both ZXing (`com.google.zxing:core`), the frames come from CameraX.** ZXing is pure Java: `qrModules(text)` in `QrCode.kt` returns a `QrModules` grid (error correction **H**, no quiet zone — the caller adds its own), and `QrCodeTest` encodes a link and decodes the same grid back on the JVM, with no emulator. **The app icon sits in the middle of the code, and `logoLayout()` is the one geometry for it**: a white rounded pad of 26 % of the code side (≈7 % of the area) with the launcher icon (`appIconBitmap`, the same `getApplicationIcon` call «О приложении» uses) at 20 % inside it. H rather than Q is what pays for the logo — 30 % recoverable, of which the pad spends 7, leaving more for dirt and scratches than Q would have left with no logo at all; the price is one QR version, 33×33 modules for a six-digit id. The pad is not decoration: an icon laid straight over modules turns its edges into false modules, and the white field separates the two the way the quiet zone separates the code from the paper. `QrCodeTest` blanks the pad by that same layout and decodes what is left, so the on-screen `QrImage`, the printed `QrBitmap` and the test cannot cover different modules. ML Kit was rejected because it leans on Google Play services, which a RuStore phone may not have; a scanner that works wherever there is a camera is the point of an offline app. `QrFrameAnalyzer` is the CameraX `ImageAnalysis.Analyzer`: it reads the Y plane only (a QR code is monochrome), honours `rowStride`, decodes only the QR format with `TRY_HARDER`, and closes every frame in `finally` — an unclosed frame stops the analysis stream for good. `QrBitmap` renders the printable PNG: black on white regardless of theme, a four-module quiet zone, the device name as a caption so four stickers can be told apart before they are stuck on. **The `CAMERA` permission exists for this screen alone** — the candling torch uses `setTorchMode`, which needs none — and `android.hardware.camera.any` is `required="false"`, so a tablet without a camera can still install the app.
- **Opening from outside goes through `LaunchTarget` in `MainActivity.kt`** — a sealed type over `ReminderTarget` (the notification, unchanged) and `QrTarget` (a `VIEW` intent whose data parses as a link). `MainActivity` is `singleTop` now, and that is the one change to how the app is launched: the camera opens the link into the *running* app through `onNewIntent`, where the activity calls `setIntent` and bumps `launchSerial`. `InventoryNavHost` keeps the last handled serial in `rememberSaveable` and navigates only when the serial is ahead of it — a rotation is a new activity whose serial starts at zero, so nothing repeats, and a second sticker scanned into a running app is a new serial, so it does. The reminder path keeps `FLAG_ACTIVITY_CLEAR_TASK` and therefore still arrives through `onCreate`; the guide is skipped for a QR launch exactly as for a reminder. **A QR navigation is `popUpTo` the graph's start destination (`findStartDestination()`, not `Start` by name — while the guide is showing the start is the guide and `Start` is not on the stack at all) then the incubator, a reminder is a plain push**: scanning is «walk up to this device», and a round of the hatchery must not pile one incubator per sticker onto the back stack. The route carries `IncubatorDestination.measureArg`, a `BoolType` beside `batchIdArg`, and `IncubatorScreen` opens `IncubatorMeasurementSheet` once the state has loaded — only for a device that exists and is not archived, under the same `reminderOpened` guard the notification uses.
- **Two entry points into the sheet, two into the scanner, one event each.** `IncubatorQrSheet` (the QR icon in the incubator header, and «QR-код» in the start screen's card menu) shows the code on a white card and offers «Сохранить картинку» (`ACTION_CREATE_DOCUMENT`, `image/png`) and «Отправить» (FileProvider under `exports/qr`, the same `exports/` the database and schedule copies use); `IncubatorQrViewModel` writes the PNG in `viewModelScope` — a hundred kilobytes, not a database, so it does not need a controller in `AppContainer`. `ScanQrScreen` (the scanner icon beside the hamburger on the start screen, and the FAB in the measurement sheet) asks for the camera on entry, decodes, and `ScanQrViewModel` looks the id up in the repository before navigating so «нет такого» is said where the person is standing. Analytics: `QR_SHOWN`, `QR_EXPORT`, `QR_SHARE`, `SCANNER_OPENED`, and `QR_OPENED` with «Источник» = «камера» / «сканер» — the share of «камера» is the only measure of whether phone cameras open the custom scheme at all.

## Notifications

**There is exactly one reminder work in the whole app, and it knows only the next moment.** `ReminderScheduler` enqueues a single `OneTimeWorkRequest` under `REMINDER_WORK_NAME`, carrying nothing but the moment it was set for (`KEY_FIRE_AT`); when it fires, `ReminderWorker` shows everything that fell on that moment and enqueues the next one itself. Each `Time` carries a `note` — the reminder's own text, typed in the batch form; blank means the notification falls back to `NOTIFICATION_TITLE` from `work/Constants.kt`. WorkManager's default initializer is stripped in the manifest via the `InitializationProvider` `tools:node="remove"` block, so on-demand init through `Configuration.Provider` is required — note that `Configuration.Provider` exposes a `val workManagerConfiguration` property, not the old `getWorkManagerConfiguration()` method.

**One work, and not one per reminder, because the old arrangement ran out of scheduler.** There used to be a `PeriodicWorkRequest` for every «batch × time» pair: a household with twenty running batches at four reminders each is eighty works, against `Configuration.maxSchedulerLimit`'s default of 50 and JobScheduler's hard 100 jobs per app. Past that line some of them simply never reached the system, and reminders stopped arriving with no error anywhere. Now the count of batches changes nothing about the count of works.

**And one-time, not periodic, because only the first run of a periodic work is on time.** Its `flex` defaults to the whole interval — a day — so after the first fire the system may run it anywhere inside the following 24 hours. The only thing that used to straighten this out was the person opening the app, which for an offline app is backwards: the app is opened *because* the reminder arrived. A one-time work computes its delay afresh before every fire, from the current clock in the current time zone, so it accumulates neither drift nor a time-zone shift. Measured on an Android 15 emulator: fired at 19:00:00.13 for a 19:00 reminder, and immediately queued the next one.

**«08:00» means eight in the morning where the person is, and `TimeChangeReceiver` is what keeps that true.** A scheduled work knows only an absolute moment, computed in whatever zone was current when it was set; flying from Moscow to Vladivostok would leave the reminder ringing at the old local hour until the app was opened by hand. The receiver is declared in the manifest — the app is not running at that moment, that is the whole point — and listens for `ACTION_TIMEZONE_CHANGED` and `ACTION_TIME_SET` (a daylight-saving change arrives as the latter). Verified on the emulator: switching the zone moved the pending reminder from 01:58 to 22:58 local, i.e. it stayed on the hour written in the batch.

**A reminder belongs to a batch, not to its name.** The notification id and the `PendingIntent` request code are computed from `Batch.id` in `work/ReminderPlan.kt`, which is Compose-free and pinned by `ReminderPlanTest`. They used to be the title plus the bare time string, and both halves broke: one constant notification id meant the third batch's reminder overwrote the second's, and one request code meant every notification's `PendingIntent` was rewritten by the next (`FLAG_UPDATE_CURRENT`). `nextReminderMillis` lives there too, and fixes a third-order bug of the same vintage: the delay used to be «today at HH:MM minus now», which for a time already past came out negative, and WorkManager reads a negative delay as *immediately* — setting an 08:00 reminder in the afternoon fired it on the spot.

**Nothing outside `work/` decides whether a reminder should exist.** `WorkRepository` has one method — `refreshReminders()` — and every ViewModel that writes to the database calls it afterwards. It used to have three (schedule / cancel one / cancel all), and each caller had to remember which of them matched what it had just written: finished a batch — cancel, reopened it — schedule, saved the form — cancel and schedule again. Six places remembering a rule is five places that can forget it, and one did: saving the form of a finished batch used to resurrect its alarms. The schedule is derived from the database anyway — which batches are running and what times they hold — so «recompute» is the only sensible thing to say after a write.

**What must be shown is decided when the work fires, not when it is set.** The work re-reads the whole plan from the database, and `jobsDueAt` picks what belonged to its own moment — from `fireAt - 1`, not from the current clock, because in Doze a work can wake tens of minutes late and «what rings now» would already be tomorrow's list. A batch finished, deleted or renamed in the meantime is therefore handled by construction: it is simply not in the plan any more. That is what makes «a finished batch wakes nobody» true even for a batch that arrived already finished inside somebody else's imported database.

**A failed read is a retry, never a silent success.** The chain of one-time works is the only thing that continues the schedule, so a work that returns `success` without enqueueing the next one ends reminders until the app is opened. An unreadable database — it may be mid-swap during an import — returns `Result.retry()`; a failure while showing a notification is caught so that the next work is still enqueued. Cancellation is rethrown rather than swallowed: stopping a work is routine, and a swallowed `CancellationException` would read as «the database is empty».

**Reminders survive export/import because they are not stored — they are derived.** `work/ReminderSync.kt` reads the database, builds the plan and hands the nearest moment to the scheduler; `MainActivity.onCreate` runs it at every launch. That is what carries reminders across a transfer: the batches and their `Batch_time` rows travel in the file, the scheduled work does not, and importing ends in a process restart (`DataTransferController`), so the first thing that happens afterwards is this pass. It runs from `MainActivity`, **not** `Application.onCreate`, because WorkManager itself starts the process when a reminder is due, and rebuilding there would cancel the work that is running. `AppSettings.remindersMigrated` guards a one-time `purgeLegacyWork()` for the title-tagged work of previous versions and for the per-time works of the versions after them, which no current name can reach; it waits for the cancellation to complete before raising the flag, since a process death in between would strand that old work forever.

**It reconciles rather than rebuilds, and that distinction cost a real bug to learn.** The first version cancelled everything tagged `REMINDER_TAG` and enqueued the plan afresh. But a due reminder is not delivered the instant its time arrives — in Doze it slips by tens of minutes — and the next moment is *strictly* in the future by construction. Opening the app at 08:20 on a reminder set for 08:00 that had not fired yet therefore cancelled the pending run and scheduled the next one for tomorrow: today's notification vanished silently, and for someone who opens the app every morning it would have vanished every day. `ReminderScheduler.schedule` leaves an overdue-but-pending work alone — it will fire, and firing is exactly what recomputes the following moment — re-anchors work whose moment has moved more than a minute, and cancels it outright when there is nothing left to ring.

Reading the database before touching WorkManager is deliberate too: a failed read now leaves the previous schedule alive instead of leaving the phone silent until the next launch. Both reads are bounded by a timeout, because `try/catch` catches a throw but not a hang. The remaining race — a batch finished between the read and the enqueue keeps its place in the plan — is harmless, because the work re-reads the plan when it fires and shows nothing for it.

**Reopening a batch brings its reminders back** (`IncubatorViewModel.unarchiveBatch`). Finishing never deleted the `Batch_time` rows — only the scheduled work — so the plan simply contains them again the moment the batch counts as running, and the recompute after the write picks them up. Nothing here is a special case: it is the same `refreshReminders()` every other write calls.

**Tapping a notification opens that batch inside its incubator.** `reminderContentIntent` puts `EXTRA_INCUBATOR_ID` / `EXTRA_BATCH_ID` on an intent into `MainActivity`; `ReminderTarget.from` parses them; `InventoryNavHost` navigates to `IncubatorDestination.routeFor(incubatorId, batchId)`, whose optional `batchId` argument makes `IncubatorScreen` open the batch sheet. The incubator id is required — the sheet has no route of its own and is reachable only through its screen. `FLAG_ACTIVITY_CLEAR_TASK` means the intent always arrives through `onCreate`, so there is no `onNewIntent` path. The intent building is a separate function from the `PendingIntent` solely so a test can read it back: `ReminderWorkerTest` round-trips it through `ReminderTarget`.

**Two `rememberSaveable` flags guard that deep link, and both are load-bearing.** An `Activity` keeps its launch intent across recreation, so a screen rotation is an `onCreate` carrying the *same* extras: without `reminderHandled` in `InventoryNavHost` the graph navigates again on every rotation — the closed batch sheet came back, and the back stack quietly grew one `Incubator` entry per turn of the phone. `reminderOpened` in `IncubatorScreen` covers the other half: `LaunchedEffect(openBatchId)` re-runs when the restored composition is rebuilt, which would reopen a sheet closed before the rotation even with the navigation guarded. Neither can be replaced by a `LaunchedEffect` key — the key does not change; what changes is that the composition is new. Both reset correctly for the *next* notification, because `FLAG_ACTIVITY_CLEAR_TASK` starts a fresh task with no saved state. Verified on an Android 15 emulator: sheet closed → rotate → stays closed, one back press reaches the incubator list, and a subsequent notification still opens the batch.

Tests: `ReminderPlanTest` (JVM, `app/src/test`) pins the notification ids, the next-occurrence arithmetic, the dispatcher (`nextFire` / `jobsDueAt`) and `plannedReminders` — including that the same «08:00» is a different moment in two zones, and that a work waking late shows its own moment rather than tomorrow's. `ReminderWorkerTest` and `ReminderSyncTest` (`app/src/androidTest`, `androidx.work:work-testing`) run the real worker against the real database and check the notification shade — two batches on one hour give two notifications — and check that firing enqueues the next work and that a recompute leaves an unchanged schedule alone. `connectedDebugAndroidTest` needs a device.

## Calendar

**Right after a batch is created the app offers to put its important dates into the phone's calendar**, and everything Compose-free about it lives in `app/src/main/java/ru/zaroslikov/incubator/calendar/`; the dialog is `ui/batch/AddToCalendarDialog.kt` (see `ui/CLAUDE.md`, «The batch form»).

- **Three kinds of date, all already known to the form** (`batchCalendarDates` in `BatchCalendar.kt`, pinned by `BatchCalendarTest`): every candling day from `SpeciesCatalog.candlingStage` (numbered), the day turning stops — the first day of the plan's tail where turns are `0`, found by `stopTurningDay` — and the hatch, `start + term`, the same moment `batchFinishMoment` keys the «Инкубация завершена» prompt to. Day N is `start + N − 1`, as in `incubationDay`. **The stop-turning day is read from the plan as it will be saved, and from `scheduleBase` under auto-turn** — an incubator that turns by itself still has to be switched off on that day, and the automation has erased the column that knows it. A `null` anywhere in the tail means «no quota», not «do not turn», so it yields no date rather than a guess. Dates before today are dropped: a batch may be entered after the fact.
- **Written directly through `CalendarContract` with `READ_CALENDAR` / `WRITE_CALENDAR`, not one `ACTION_INSERT` per date** (`CalendarWriter`): four or five dates each needing «Сохранить» in another app is work, not «add the dates». All events go in one `applyBatch` with their reminders — half the dates in a calendar look like all of them. **All-day events** (UTC midnight, `EVENT_TIMEZONE = "UTC"`, as the provider requires) **with a reminder at 18:00 the evening before** (360 minutes): candling and the move to hatching are done during a day, and the evening before is when knowing helps. The insert intent survives as the fallback that needs no permission.
- **These events are the user's once written**: the app keeps no ids and never updates or deletes them — a batch finished early or deleted leaves its calendar entries behind, and the dialog says that shifting dates is done in the calendar itself. Tracking them would mean a table of foreign ids and a permission check on every batch write, for the rare case.
- **Events are written «свободен» (`AVAILABILITY_FREE`)** — five all-day «busy» blocks in a work calendar would show to colleagues — and only calendars with `SYNC_EVENTS = 1` are offered, since an unsynced account calendar accepts events that go nowhere.
- **The write survives a rotation by construction**: `applyBatch` is blocking and cancelling the coroutine does not stop it, so the dialog saves a `Writing` step before launching; a restored `Writing` with no live coroutine means the transaction committed and goes to «Готово» instead of offering «Добавить» again (which would duplicate every event). The permission request raises `busy`, and an empty result — an interrupted or doubled request — leaves the question standing rather than reading as a refusal.
- AppMetrica: `CALENDAR_ADDED` («Способ» = «напрямую» with «Дат», or «по одной» with «Открыто» — forms opened, not events known to be saved; «Вид») and `CALENDAR_DECLINED` («Дат», plus «Этап» = «по одной» when the fallback was closed with nothing opened), so added + declined adds up to the offers shown.

## The airing timer

**A measurement form can time an airing, and the minutes it counted go into «ПРОВ., МИН» when it ends.** Everything Compose-free lives in `airing/`; the card is `ui/batch/AiringTimerCard.kt`. Five rules carry it.

- **One timer for the whole app, and `AiringTimerController` in `AppContainer` is its only writer.** `AiringTimerState` is `Idle` / `Running` / `Done`, with a target (`AiringTimerTarget(incubatorId, batchId)` — `batchId = 0` is the incubator's «Замеры за сегодня» sheet) and a label for the notification. One timer rather than one per batch because a person opens one lid at a time, and the countdown notification and the melody are one each. It sits in the container for the reason `DataTransferController` does: the timer is set in a form and left behind — another sheet, another app, a pocket — and it has to end wherever the end finds it, then wait for the form that will take its minutes. The state is persisted in `device_prefs` (`AppSettings.airingTimer`, a flat `AiringTimerRecord` of primitives, written with `commit`) — an installation property, and pointedly so: a timer restored from someone else's backup would ring about an airing that never happened here. `MainActivity.onCreate` calls `refresh()`: a `Running` timer whose term passed while the process was dead settles into a silent `Done` (the result still reaches the form, but ringing an hour later is pointless), a `Running` one without a service gets its service back, and a `Done` older than `RESULT_TTL_MILLIS` (2 h) is dropped so yesterday's minutes never land in today's measurement. `AiringTimerTest` pins `settled` — including that a `ringing` flag older than `RING_TIMEOUT_MILLIS` is cleared, so a service restarted after a process death mid-melody does not play it again — `elapsedMinutes`, the chips and the record round trip. `start()` refuses while the state is anything but `Idle`: a pending `Done` is a result nobody has taken yet, and a new timer would overwrite it without a trace.
- **The background is `AiringTimerService`, a foreground service (`specialUse`) — not an exact alarm.** `setAlarmClock` needs `SCHEDULE_EXACT_ALARM`, which Android 14 turns off by default and only the user can enable in system settings, so the first timer would send them out of the form. A foreground service starts from the open app without a question, holds a partial wakelock for the countdown, shows a chronometer notification (`setChronometerCountDown` — the system draws the ticking, nothing updates every second) with «Завершить» / «Отменить» actions, and at the moment calls `controller.timeUp()`. Deep Doze, where wakelocks stop working, is half an hour of stillness with the screen off away; `MAX_MINUTES` (90) is a ceiling, not a norm. The service decides nothing itself: it collects `controller.state` and does what it says — wait, ring, leave — so notification buttons (`AiringTimerActionReceiver`, a receiver rather than `getService`, since `startService` from the background onto a service that may already have stopped is refused on Android 8+) and «Готово» in the form change the state the same way, and `START_STICKY` plus the persisted record let it resume after a process death. The manifest declares the type, the `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` reason, and `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`, `WAKE_LOCK`, `VIBRATE`. (`specialUse` is a type Google Play asks a justification for; the app ships through RuStore.) **A backup alarm covers the one failure the service has — the process being killed** (`AiringTimerAlarm`): `setAndAllowWhileIdle` for the term plus 1.5 s, no exact-alarm permission, scheduled with every `Running` write and cancelled with every other. It fires `AiringTimerActionReceiver.ACTION_TIME_UP`: with the service alive the state is already `Done` and `timeUp()` is a no-op; in a process the alarm just woke, `startForegroundService` from the background is refused on Android 12+ (`AiringTimerService.start` returns `false`), and the receiver rings through `insistentDoneNotification` instead — `FLAG_INSISTENT` repeats the channel sound until the notification is dismissed, `setTimeoutAfter` removes it after the melody's own timeout. That is why the «Проветривание окончено» channel carries the alarm ringtone after all; the service's own notification is `setSilent(true)` so the two never sound together.
- **The melody is the system alarm ringtone, played by the service itself, in a loop, with `USAGE_ALARM`.** Not the notification channel's sound: without `POST_NOTIFICATIONS` a channel is silent and the incubator is still open, while a `Ringtone` plays regardless; and alarm usage means alarm volume and the alarm exemption from «не беспокоить». It stops on «Готово» in the form, «Закрыл инкубатор» on the notification, or `RING_TIMEOUT_MILLIS` (60 s), with vibration alongside. Two channels: the countdown one is `IMPORTANCE_LOW` (it hangs for the whole airing and must never peep), «Проветривание окончено» is `IMPORTANCE_HIGH` with the alarm ringtone as its sound — used only by the backup path above; the service posts with `setSilent(true)`. A phone with no resolvable ringtone still vibrates for the whole timeout: `ring()` does not stop when there is no tone to loop. When the ring times out on its own the service leaves a plain «время вышло» notification behind (no actions — the service that would run them is gone); the controller cancels it when the state reaches `Idle`, since by then the service cannot.
- **`Done` waits until the measurement is saved, not until the minutes are filled in.** `BatchDetailViewModel.watchAiringTimer` / `IncubatorMeasurementViewModel.watchAiringTimer` collect the state; a `Done` for their own target writes `minutes` into `form.airingTime` once per result and form (`filledTimerId`, a private field reset by `Load(resetForm = true)` so a fresh form is filled again), and tells the controller nothing. The result is removed only by `resultSaved(target)` from the save path of «Замеры за сегодня», by «Готово» (`dismiss`), or by `RESULT_TTL_MILLIS`. **That was a real bug**: the result used to be marked `taken` at the moment of filling and dropped to `Idle` once silent, but the collector lives in `viewModelScope`, so a form opened before the app was minimised filled its field in the background — and the tap on the notification then navigates with `popUpTo`, recreating the screen and its ViewModel, and the new form opened empty with nothing left to take. There is no `taken` flag any more (the old prefs key is removed on the next write). The collector also runs the state through `settled(now)` and calls `refresh()` when that changes anything, because a ViewModel lives for hours and the TTL is only enforced where someone asks. Under automatic airing the field is locked and nothing is filled. The floating ring shows only while the timer runs or the melody plays: a silent result waits in the form's card, not on every screen for two hours. A timer that belongs to another form (`AiringTimerSlot.mine == false`) shows as one line with a «Выключить» button for the melody only — its minutes belong to the form it was set from, and a second timer is refused by `start()` while one runs. **Everywhere else the running timer is a floating ring in the corner** (`AiringTimerFab`, mounted in `MainActivity`'s root `Box`), hidden only on the form that owns it: `AiringTimerController.openForms` is the set of targets whose sheets are currently composed (`RegisterTimerForm`), and a tap on the ring reuses the `TimerTarget` launch path.
- **Tapping either notification opens the form the timer was set from** — `TimerTarget` in `MainActivity.kt`, checked before `ReminderTarget` in `LaunchTarget.from` because it carries the same extras plus `EXTRA_AIRING_TIMER`. The nav graph routes a batch target to `IncubatorDestination.routeFor(incubatorId, batchId)` and an incubator one to `routeFor(incubatorId, measure = true)`, both with `popUpTo` the start destination as the QR path does — the app is most likely already open, and the sheet must not land on itself; the intent is `singleTop` without `CLEAR_TASK`, so a running app gets it through `onNewIntent`. A cold launch by it skips the guide like a reminder does. AppMetrica: `AIRING_TIMER_STARTED` («Минут», «Из инкубатора»), `AIRING_TIMER_FINISHED` («Исход» = вовремя / досрочно / отменён, «Минут»), `AIRING_TIMER_OPENED`. The card's own rules are in `ui/CLAUDE.md`.

## Profile and VK ID

**The profile is the account.** «Профиль» (`ui/profile/`, see `ui/CLAUDE.md`) shows a name, a photo, a farm and a city only to someone signed in to the account (below); signed out, it is an invitation to sign in — by VK ID, by email, or to create an account — and every other screen of the app works identically either way, so signing in stays optional. There is no profile without an account any more: the name lives on the server, shared with «Моё хозяйство», and a second, phone-only name would be a second answer to «как меня зовут». `AccountRepository` owns the profile row, and every write to it goes through `AccountRepository.editProfile` under one lock, so a sign-in, an edit on screen and a photo arriving from VK cannot overwrite each other.

- **Where each field lives.** The name is `displayName` on `server_ferma` (`PATCH /me`); the `User` row (schema v19: name, farm, city, avatar JPEG, `vkUserId`) holds a copy of it next to the three phone-only fields. **At every sign-in and at the launch-time refresh the server's name wins** (`AccountRepository.syncProfile`); an edit sends the name to the server first and saves nothing if the server refuses, since a name written only on the phone would be overwritten at the next sign-in. For a VK account without a `displayName` the name is «имя фамилия» from VK. **A name left in the row by an older version** — when the profile lived without an account — is adopted at the first sign-in and sent to the server if the account has none, so it is not lost. A signed-in account with no name anywhere opens «Новый профиль» at once (`AccountEffect.SignedIn(needsName)` / `ProfileEffect.SignedInWithVk(needsName)`).
- **Signing out erases the profile** — logout, account deletion, and a session the server declares dead (`AccountRepository.clearLocal` writes an empty `User` row and logs out of the VK SDK). The next person to sign in on this phone must not see someone else's name and photo, and a profile exists only while signed in. The name comes back from the server on the next sign-in; farm, city and photo have to be entered again, and the logout dialog says so. «Удалить все данные» signs out too (`DataTransferController(signOut)`). While signed out, `ProfileViewModel` and `AnalyticsViewModel` show an empty `User` whatever the row holds (a leftover of an older version or an imported database), so nothing of a profile is visible without an account.
- **VK is a way to sign in to the account, not a separate link.** `ProfileIntent.LoginVk` opens VK's window, and its access token goes to `POST /auth/vk`, which checks it with VK itself and answers with the account's own tokens — the first VK sign-in creates the account, and it is the same account as in «Моё хозяйство» when the same VK was used there. The session remembers the method (`AccountSession.viaVk`), because such an account may have no password: **deleting it is confirmed by a fresh VK login** instead (`AccountRepository.deleteAccountWithVk`), and the fresh login must lead to the same user id, or a VK tied to another account would delete that one. The server needs `INCUBATOR_VK_CLIENT_ID` (or `VK_CLIENT_ID`) matching this app's VK ID registration to accept the token.
- **The VK token is never ours to store**: the SDK keeps it in its own `vkid_encrypted_shared_prefs`, encrypted with a Keystore key of this phone, and both that file and the SDK's default prefs (`<package>_preferences`, its device id) are excluded in `backup_rules.xml` / `data_extraction_rules.xml`. The token passes through `VkAccount.accessToken` exactly once, on its way to `/auth/vk` (its `toString` hides it).
- **Everything that imports `com.vk.id` lives in `vkid/`** (`VkId.kt`), the way AppMetrica lives in `analytics/`; `grep -rn "com.vk.id" app/src/main --include=*.kt` must return only that package. It exposes `isAvailable` (keys present **and** `VKID.init` succeeded — a failed init hides the button rather than showing one that fails), `init`, `login(): VkLoginResult` (`Success` / `Cancelled` / `Failed`) and `logout()`. `VKID.authorize` returns as soon as the window is open and delivers the result to a callback, so `login` waits on a `CompletableDeferred`, capped at ten minutes in case the SDK never calls back; `logout` is capped at 15 s. **Without keys the SDK's two activities are switched off in the app manifest** (`android:enabled="${vkidEnabled}"` with `tools:replace`): its redirect receiver is exported and would otherwise accept any `vk0://` link and crash on an uninitialised SDK.
- **Only the core SDK, `com.vk.id:vkid` 2.7.3**, from `artifactory-external.vkpartner.ru/artifactory/vkid-sdk-android` (a second VK repository in `settings.gradle.kts`, declared as **`exclusiveContent`** for `com.vk.id*` — those groups come from there and nowhere else, so a same-named artifact on Maven Central cannot win; the SDK's two outside dependencies, `com.vk:android-sdk-id` and `ru.ok.tracer`, live on Maven Central and resolve from there). Not `onetap-compose`: it pulls Coil, multibranding and group subscription for one button the profile screen draws itself. The SDK brings its own R8 keep rules.
- **The app registration is a build input, like the RuStore push project**: `vkidClientId`, `vkidClientSecret` and optionally `vkidRedirectHost` (default `vk.ru`) are read from `local.properties` first, Gradle properties second (`buildInput()` in `app/build.gradle.kts`), and become the SDK's manifest placeholders (`VKIDRedirectScheme` = `vk<id>`) plus `BuildConfig.VKID_CLIENT_ID`. **An empty id is a working state**: the placeholders get a dummy `0` so the manifest merges, `VkId.init` does nothing, and the profile screen shows no VK button — sign-in is by email only. That is what a fresh clone gets. Filling it in is done at id.vk.com: an Android app with package `ru.zaroslikov.incubator` and the SHA-1 fingerprint of the signing key (debug and release are different keys).
- **Photos**: the VK photo (`avatarUrl` from the server's user) is downloaded once after sign-in, in the background, and lands only if no photo was picked meanwhile and the same account is still signed in (`profile/AvatarImage.fromUrl`, https only, 10 s timeouts, 5 MB cap). Like a picked gallery photo (`fromUri`, streamed from the provider rather than buffered — camera shots run 10–15 MB) it is normalised — bounds read first, sources over 200 Mpx or wider than 8:1 refused before any pixel is decoded — to a centre-cropped JPEG ≤256 px with the EXIF rotation applied, stored as bytes in the row. Photos never go to the server.
- **AppMetrica**: `OPEN_PROFILE` («Откуда» = меню / аналитика), `PROFILE_CREATED` («Способ» = почта / VK — the first time a name is filled in for a signed-in account), `PROFILE_UPDATED` («Фото»), `VK_LOGIN` («Исход» = вход / отмена / ошибка), and the profile attribute «Профиль» = нет / почта / VK (removed in a build without a server). Only the fact — no name, farm, city, email or VK id reaches analytics. `VK_UNLINKED` and `PROFILE_DELETED` are no longer sent: there is no unlinking and no profile deletion apart from the account's.

## Account: email and password

**The app talks to the owner's server, `server_ferma` (`D:/Work/_Project/server_ferma`, Node + Fastify), which it shares with «Моё хозяйство».** One account serves both apps: registered in one, signed in to both, and deleting it deletes it for both. The server does far more (VK login, subscriptions, push, feed); this app uses email registration, VK sign-in and the account name, and the contract it relies on is at the end of this section. The farm itself still never leaves the phone. Signing in stays optional, and **the account is the profile** — see «Profile and VK ID» above.

- **Everything Compose-free is `account/`**: `AccountApi` (OkHttp + platform `org.json` — OkHttp because the name is changed by `PATCH /me`, which `HttpURLConnection` cannot send, and it costs nothing: AppMetrica already puts 4.12.0 into the APK, the catalog only names it; Retrofit for a dozen short JSON calls is not worth it; `parseTokens` / `parseError` are pure and pinned by `AccountApiTest`), `AccountStore` and `AccountRepository` (in `AppContainer` as `account`, for the reason `DataTransferController` is: logout must finish without the screen). The UI is `ui/profile/AccountSheet.kt` + `AccountViewModel.kt` (see `ui/CLAUDE.md`).
- **The session is an installation property, not user data.** Refresh token, user id and email live in `account_prefs`, one JSON value encrypted with AES-GCM under an Android Keystore key (hand-rolled, not `EncryptedSharedPreferences`, which is deprecated and alpha); the file is excluded from both backup rule sets. Never the database: the database travels in export files to messengers, and a refresh token there would be a key to the account in someone else's hands. A value that fails to decrypt (key lost, foreign file) reads as «signed out» and is wiped. The access token (15 min) lives in memory only. **Once per process, at launch, the session is checked with a refresh** — the account is shared with «Моё хозяйство», where it can be deleted or its password reset, and without the check this app would keep showing a signed-in account that no longer exists. A «dead session» answer (`AccountError.isSessionDead`) signs out locally; no network changes nothing.
- **Refresh tokens rotate, so every session change goes through one `Mutex`.** Two concurrent refreshes with the same token would be read by the server as token reuse and revoke everything. Logout clears the local session first (it must work offline) and revokes on the server in the background with a 15 s cap.
- **The server URL is a build input, like the VK keys**: `accountServerUrl` from `local.properties` (then Gradle properties) → `BuildConfig.ACCOUNT_SERVER_URL`. **Empty is a working state**: `AccountState.Unavailable`: the profile screen says the build has no account server, and the analytics attributes are removed rather than sent as «нет». Release is https-only (`res/xml/network_security_config.xml`); the debug copy in `src/debug/res/xml/` allows cleartext for `10.0.2.2` and `localhost` only, so `accountServerUrl=http://10.0.2.2:3000` reaches `server_ferma` running on the developer's machine (`npm run dev`, port 3000; without `SMTP_HOST` the codes are printed to its log) from the emulator.
- **Validation mirrors the server** (`AccountRepository.isValidEmail` / `isValidPassword`: trim + lowercase, ≤254, the same regex; the password 8–128 code points with at least one letter and one digit and not equal to the email) so a refusal known in advance never makes the trip. The server's list of ~200 common passwords is not copied — its `WEAK_PASSWORD` with `reason: common` comes back as «слишком распространён». Codes are 6 digits; `register` and `password/forgot` answer 202 whatever the email, and the UI says «если» accordingly — the server does not reveal which addresses exist, and the app must not either.
- **Confirming the code sends the registration password back** (`AccountApi.confirmRegistration(email, code, password)`, the password held only in `AccountFormState.pendingPassword`). `server_ferma` binds each registration code to the password it was requested with, so someone re-registering the same address cannot have the owner's code confirm their password. On this server the password is required, so the Verify step cannot be submitted (or resent) without it; since the form lives only in the ViewModel, reaching Verify always means having just registered.
- **Account deletion confirms who is asking by logging in again.** `DELETE /me` on `server_ferma` takes only a bearer token, yet anyone holding an unlocked phone could otherwise delete an account nobody can restore — **for both apps at once**, which the dialog says. So `AccountRepository.deleteAccount` calls `/auth/login` with the session's email and the typed password (for a VK account, `deleteAccountWithVk` — a fresh VK login through `/auth/vk`), checks that this login is the same user, and deletes under *that* token; a wrong password reads «Неверный пароль.», and a delete that fails afterwards revokes that extra login so it does not linger for two months. The phone's own session is untouched until the delete succeeds; then the profile is erased with it. Incubators and batches on the phone are untouched.
- **AppMetrica**: `ACCOUNT_REGISTERED` (code sent) → `ACCOUNT_VERIFIED` (account exists) — the gap is people lost at the code step; `ACCOUNT_LOGIN` with «Исход» = вход / ошибка; `ACCOUNT_LOGOUT`, `ACCOUNT_PASSWORD_RESET`, `ACCOUNT_DELETED`; profile attribute «Аккаунт» = да / нет. The email never goes into analytics.
- **The contract the client relies on** (`AccountApi`, base `<accountServerUrl>/api/v1`, JSON, **every request carries `X-App-Id: incubator`** — without it `server_ferma` treats the call as «Моё хозяйство» and the code emails arrive under the other app's name; errors are `{"error": {"code", "message", "details"}}`): `POST /auth/register {email, password}` → 202 `{expiresIn, resendAfter}` — the same for an already registered address, which gets a «вы уже зарегистрированы» letter instead of a code, and **repeating it with the same pair is the resend** (there is no `/auth/resend`; 429 `TOO_MANY_CODE_REQUESTS` inside 60 s); `POST /auth/register/confirm {email, code, password}` → 200 AuthResponse, 400 `INVALID_CODE` with `details.attemptsLeft`; `POST /auth/login {email, password}` → 200, 401 `INVALID_CREDENTIALS`, 429 `TOO_MANY_LOGIN_ATTEMPTS` with `details.retryAfter` (there are no unverified accounts — an account exists only after the code); `POST /auth/refresh {refreshToken}` → 200 (rotated), 401 `REFRESH_TOKEN_REUSED` / `REFRESH_TOKEN_EXPIRED` / `INVALID_REFRESH_TOKEN` / `SESSION_EXPIRED` / `USER_NOT_FOUND`; `POST /auth/logout {refreshToken}` → 204; `POST /auth/password/forgot {email}` → 202 always; `POST /auth/password/reset {email, code, newPassword}` → 200 AuthResponse (ends every other session); `POST /auth/vk {accessToken}` (the VK ID SDK token) → 200 AuthResponse, 401 `VK_AUTH_FAILED`; `PATCH /me {displayName}` with the bearer → 200 `{user}`; `GET /me` with the bearer → 200 `{user, subscription: {active, planId, expiresAt}, adsDisabled, apps}` — only `subscription` is read (`AccountApi.subscription` → `AccountRepository.subscription`, shown as the badge beside the name; `active` is the server's verdict, the client never compares dates); `DELETE /me` with `Authorization: Bearer <access>` and **no body** → 204; for Premium (`PremiumSheet`, `ui/CLAUDE.md`) `GET /subscription/plans` (public) → `[{id, title, price: {amountKopecks, currency, display}, durationDays}]`, `POST /subscription/checkout {planId}` with the bearer → 201 `{paymentId, status, confirmationUrl}`, and `GET /subscription/payments/{id}` with the bearer → `{status, subscription, …}`, polled until `succeeded` / `canceled`. The user also carries `displayName`, `firstName`, `lastName` and `avatarUrl` (`AccountApi.parseUser`). AuthResponse is `{accessToken, refreshToken, tokenType, expiresIn, isNewUser, isNewInApp, user: {id, loginEmail, email, hasPassword, hasVk, vkUserId, …, createdAt}}`; the app shows `loginEmail` (the confirmed login address), falling back to `email` and then to what was typed. `AccountError.isSessionDead` is the only place codes decide the session's fate; everything else is turned into a Russian sentence by `AccountApi.parseError` — the server writes some messages in English («Invalid or expired code»), so known codes get the client's own text with the `details` numbers in it, an unknown code keeps the server's text only if it is Russian, and otherwise the status decides. The server's own guide is `docs/CLIENT_INTEGRATION.md` in `server_ferma`.

## Stories on the start screen

**`server_ferma` serves stories, and the start screen shows them as a row of circles above the incubator list.** Everything Compose-free is `stories/`; the row and the viewer are `ui/stories/` (see `ui/CLAUDE.md`).

- **`GET /stories`, not `/feed`**: the app shows no news, and `/feed` would drag the first page of them along for nothing. Every request carries `X-App-Id: incubator` (the server keeps each app's stories apart) **and `X-Install-Id` = `AppSettings.installationId`**, plus the bearer when signed in (`AccountRepository.optionalAccessToken()` — `null` when signed out or when the refresh cannot be made). Signed in, the server keeps views per account; signed out, per installation. A 401 on the bearer retries without it: stories are public, and a session closed in «Моё хозяйство» a second ago must not blank the row.
- **`StoriesRepository` sits in `AppContainer`**: one feed per process, refreshed on every resume of the start screen only when it is older than five minutes or the signed-in user changed (another person has other views). A failed request keeps the old feed and says nothing — the app is offline-first and nothing depends on stories. An empty `accountServerUrl` means no stories at all.
- **A view is written twice**: `POST /stories/{id}/view` when the last slide finishes, and `AppSettings.viewedStories` in `device_prefs` (an installation property, excluded from backups like the rest of that file), so a story watched without network does not come back in a coloured ring. The local set cannot grow: after every server answer it keeps only ids the server still reports unviewed (`prune`). `StoryParser.withLocalViews` merges the two and orders unviewed first, stably — the server's order within each half.
- **Parsing is lenient** (`StoryParser`, pinned by `StoryParseTest`): an unknown slide type or a blank `mediaUrl` drops the slide, a story left without slides drops out, `durationMs` is clamped to 1–60 s (default 5 s). A button survives only with an `http(s)://` or `incubator://` URL — the server checks the same, but the tap is an `ACTION_VIEW`, and `intent://` must never open whatever the server says — and a URL without text gets «Подробнее». **Loopback media URLs are rewritten to the server address from the build** (`resolveMediaUrl`): without `PUBLIC_BASE_URL` the server builds `http://localhost:3000/uploads/…`, which on a phone points at the phone.
- **Images are our own loader, not Coil** (`StoryImages`: OkHttp with a 50 MB HTTP cache in `cacheDir/stories`, a network interceptor marking every answer cacheable for a week since the upload server sends no cache headers, `inSampleSize` down to the side needed, an `LruCache` of an eighth of the heap). The same reasoning as the VK button: a library with its own pipeline for two dozen pictures. **Video is the platform `VideoView`**, not ExoPlayer, for the same reason.
- AppMetrica: `STORY_OPENED` («История», «Просмотрена»), `STORY_COMPLETED` (the moment the view goes to the server), `STORY_BUTTON` («Ссылка» = сайт / приложение).
- **Locally**: `adb reverse tcp:3000 tcp:3000` is not needed for stories — the loopback rewrite sends uploads to `10.0.2.2` — but the picsum images the dev seed uses need the emulator's internet.

## Third-party SDKs

**AppMetrica goes through `analytics/`, and nothing else may import it.** `Analytics.activate` (called from `InventoryApplication.onCreate`, which runs in every process — including the one WorkManager starts for a reminder) holds the API key, and `Analytics.report` is the only reporting call in the app; `grep -rn "io.appmetrica" app/src/main --include=*.kt` must return only files under `analytics/`. The point of the funnel is not the wrapper but `Events`: **every event name in the app is listed there**, each tagged with the funnel step it belongs to. A name that cannot be enumerated cannot be put in a funnel, and before this file half the steps of «from install to first hatch» went unreported (a saved measurement, a saved candling — only *navigating* to those screens was counted, so an opened sheet looked identical to a filled-in one) while the other half reported under names that don't say what they are.

**Event names are never renamed.** Each one inherited from an earlier version continues a series of statistics years long, and a new name would restart it from zero and leave the old one a stump. Where a name lies about its meaning, it lies historically: `Events.BATCH_CREATED` is «закладка создана» and is spelled `"Инкубатор"` because before schema v2 batches lived in the `Incubator` table. The awkwardness is read once, in a comment, instead of every month in a report.

**«Итог инкубации» is the report about the device, and it fires down all three paths a batch can end.** `analytics/IncubationReport.kt` — `ItemsRepository.reportIncubationOutcomes(incubatorId, finished)` plus the pure `incubationReport(...)` behind it — carries the batch's own result (вид, порода, заложено / выведено / отбраковано, «Вывод, %», дней) and a nested `Инкубатор` block: название, бренд, модель, вместимость, «Загрузка, %» and **«Эффективность, %»**. That nesting is why `Analytics.report` sends a JSON string rather than the `Map` overload — the latter's documented value types are strings, numbers and booleans only, so a nested map would arrive as its own `toString()`, a `{Бренд=Несушка, …}` string nothing can group or filter by; for a flat event the two are identical, since AppMetrica converts the map to the same JSON internally. Three things about it are load-bearing. It is **one event name for all three endings** — the batch sheet's «Завершить инкубацию», its «Завершить досрочно», and the incubator archive, which stops a whole device's worth of batches without showing either dialog — because «which model hatches best» has to count all three, and batches stopped by the archive are exactly the ones that say something is wrong with the device. It is sent **after the write and before `onDone()`**: the efficiency is computed over the batches as they now stand in the database, so a batch whose result was not yet written would drag it down with its own zero, and `onDone()` closes the sheet, taking the ViewModel's coroutine scope — and the report's database reads — with it. And efficiency is `incubatorStats(...).hatchRate` from `:domain`, the same number the «Статистика» tab prints: a second count of it would drift, and the report would start disagreeing with the screen. `IncubationReportTest` (`app/src/test`, plain JVM) pins that number against a device holding one finished and one running batch, since letting the running one into the denominator halves it without breaking anything visible.

**Cohorts and segments are the profile, and the profile is recomputed from the database, not accumulated from events.** `analytics/AnalyticsProfile.kt` reads the whole household at every launch (from `MainActivity.onCreate`, beside `reminderSync` and for the same reason — the reminder process must not do it) and reports `UserProfile` attributes: инкубаторов, закладок / идёт / завершено / прервано, яиц, птенцов, «Эффективность», «Основной вид», «Бренд», «Модель», своих видов, напоминания, тема, версия, «Первая версия» (`withValueIfUndefined`, so it stays the cohort «arrived on version X») and the predefined `notificationsEnabled`. An event-counter (`+1 batch`) would part ways with the database at the first import — the file arrives from another phone carrying batches this installation never reported — which is the same reason the reminder schedule is derived rather than stored. A missing number is *removed* (`withValueReset`), never sent as zero: «неизвестно» and «ноль процентов» are different answers, and zero would mix beginners in with people whose eggs never hatched. Retention itself AppMetrica counts from sessions with no help from us; what it cannot know is what an installation *is*, and that is all these attributes are for.

The profile needs an id to hang on, and that is `AppSettings.installationId` — a random UUID minted on first read and passed to `withUserProfileID` at activation (not `setUserProfileID` later, or the very first session of every install would fall outside its cohort). Not a device or advertising id: the app has no need to know whose phone this is, only to not confuse two installations. It is written with `commit = true` because `Application.onCreate` happens in every process and the second one must read a finished value rather than invent its own.

`Events.REMINDER_SHOWN` («Напоминание показано») is reported by `ReminderWorker` and is the denominator for `REMINDER_OPENED` — the notification response rate, which for an offline app is the only retention lever there is. It fires **even when the notification did not go out** (no `POST_NOTIFICATIONS`), with a `Показано` parameter saying which happened: that is why `showReminder` returns `Boolean` now. Skipping the event instead would silently inflate the rate by exactly the people who never saw a reminder.

**Ads are back, and they go through `ads/` the way AppMetrica goes through `analytics/`** — Yandex Mobile Ads `8.2.0` (`libs.mobileads`, pinned in the catalog at the version the owner asked for — the catalog briefly said 8.3.0, whose public API is identical, so raising it is a one-line change; `grep -rn "com.yandex.mobile.ads" app/src/main --include=*.kt` must return only files under `ads/`). The ad unit ids are the ones the app always had — `R-M-12856457-1` for banners, `-2` for the app-open ad, both in `MobileAdsSdk` — because new ids would start a new series in the cabinet. Two surfaces, and neither is the old sticky `bottomBar` (`ui/Banner.kt` is not coming back; every screen still takes `contentPadding: PaddingValues`, which now carries system-bar insets only):

- **`AdBanner` is a card, not a strip.** A white 22 dp card with the same border as its neighbours, holding an *inline* banner sized to the card's width (`BannerAdSize.inline`, up to 120 dp tall), placed as the last item of a scroll wherever a screen has one — the start list (first page only, never under the empty state), the «Закладки» tab under the dashed button, the «Статистика» page of «Аналитика», the bottom of «Настройки» and «О приложении». Never in the guide or in a sheet. **One card per screen, held by `rememberBannerAdHost()` at screen level**: a `LazyColumn` item or a pager page is thrown away off screen, and a view living inside it would re-request the ad on every scroll past and every swipe — six requests for two impressions — so the `BannerAdView` belongs to the screen and the card only borrows it; and since one `View` cannot sit in two parents while a swipe has two pages composed, the incubator screen shows it on «Закладки» only. **Until the ad has loaded, the card has no height and no border** — an empty white card reads as broken, and «no ad» is an ordinary state (no network, no fill, emulator); the view sits at zero height so it has somewhere to load into, and the card expands with `animateContentSize`.
- **The app-open ad is `AppOpenAdController`, owned by `AppDataContainer` and driven by `ProcessLifecycleOwner`**, not by `MainActivity.onStart` — that fires on every rotation and would put an ad over a freshly turned screen. Cold start: raise the waiting notice (`AdLoadingNotice`, driven by `waitingForAd`), load, and show the ad as soon as it arrives. **That notice is the whole definition of «при запуске»**: while it stands the user has been told what is coming and is waiting for it, and once it goes — on a load failure, or after `NOTICE_TIMEOUT_MS` (7 s) — the launch moment is over and a late ad is kept for the next foreground rather than dropped on someone already working. It also holds the screen, which is why no separate «has the user started working» check is needed. Return from background gets **no** notice: it happens a dozen times a day and nobody signed up to wait each time — the ad shows only if already loaded and less than `AD_TTL_MS` old, otherwise it is merely fetched for next time. **The first version had a five-second window measured from the foreground event and no notice, and the ad never appeared at all**: SDK initialisation happens inside that window and takes seconds on its own, so the ad always arrived late (measured on an Android 15 emulator: init ~4.6 s, ad in hand at 5.86 s — and that measurement is what sets the 7 s timeout). It shows on the host `MainActivity` tracked through `ActivityLifecycleCallbacks` and filtered by class, since the ad's own screen is an activity of the same process. **`mute()` silences it for the whole process, and `MainActivity.onCreate` calls it on the first launch of an installation and the first launch of every new version** (`shouldMuteAppOpenAd`, pinned by `AppOpenAdPolicyTest`): `AppSettings.adsVersionCode` remembers the last `BuildConfig.VERSION_CODE` seen, `null` meaning never, and the guide being on screen mutes too, since a process killed mid-guide would otherwise come back «seen». The consequence for releases: **bump `versionCode` with every version**, or an update is indistinguishable from an ordinary launch. Muting also skips loading — the SDK is not raised for a show that will not happen.
- **Premium switches every ad off, and `ads/AdFree` is the one switch** — a process-wide `StateFlow<Boolean>` like `MobileAdsSdk.ready`; `ads/` knows nothing of accounts, `AccountRepository` sets it. While it is up, `AdBanner` returns before even starting the SDK, and `AppOpenAdController` neither loads, shows nor raises the «загружаем рекламу» notice (and drops a pending order and a loaded ad the moment it goes up mid-process). The source is `adsDisabled` from `GET /me` (`AccountSubscription.adsDisabled`, falling back to `active` where the flag is absent, e.g. a payment answer), and **its term is cached on the phone** — `AccountStore.adFreeUntil` in `account_prefs` (plain, not a secret; the file is excluded from backups, so another phone does not inherit it) — because the app-open ad is ordered at the first `ON_START`, before any server answer: `InventoryApplication.onCreate` reads the cache synchronously and sets the switch (`adFreeAt(until, now)`), then every subscription answer rewrites it (`applySubscription`) and logout, a dead session or no session at load clear it (`forgetAdFree`). A term that runs out simply reads as ads on at the next launch; offline, the cached term holds. `MainActivity.onCreate` touches `container.account` explicitly so the launch-time check (which also refreshes the subscription) happens on every open. `PremiumTest` pins the parsing and the term arithmetic. Verified on an emulator: first launch after purchase — the notice is withdrawn when the server answers; every cold start after — no notice and no banners at all.
- **The SDK initialises on first demand, not in `Application.onCreate`** (`MobileAdsSdk.start`, idempotent): that method runs in the process WorkManager starts for a reminder too, where there is no screen and no banner. The first foreground or the first banner on screen raises it.

Analytics calls with Russian event names sit in navigation and save paths — they go through `Analytics.report(Events.…)` (above), and the names stay as they are when code moves.

**RuStore is the third SDK family, and it goes through `rustore/` the way AppMetrica goes through `analytics/`** — `grep -rn "ru.rustore.sdk" app/src/main --include=*.kt` must return only files under `rustore/`. Three things live there, and they share exactly one property: every one of them is allowed to fail silently, because the app is offline-first and RuStore may simply not be on the phone. Versions are in the catalog — `appupdate` and `review` move together on the 10.x line, `pushclient` on its own 7.x; both pull `ru.rustore.sdk:core`, and Gradle resolves it to the higher one (10.5.0 against the 8.0.0 the push client was built with — checked that the newer core removes nothing the older had). The artifacts are not on Maven Central: `settings.gradle.kts` adds `artifactory-external.vkpartner.ru`, **last and behind a content filter**, so a chance miss in google() or mavenCentral() does not send every dependency in the project through someone else's server.

- **`AppUpdateController` offers the update, and it is the deferred kind (`AppUpdateType.FLEXIBLE`) on purpose.** RuStore also has an immediate mode, where its own progress screen stands over the app until the install finishes; for this app that is the wrong trade. It is opened *because* a reminder said to check the incubator, and a blocking update screen between the notification and the batch is exactly where a person closes the app and walks to the incubator without it. The deferred flow downloads in the background and asks about installing when the file is already there. Hence four states rather than «есть / нет» (`AppUpdateState`): agreed → downloading → downloaded → installing are separate moments the person has to see, and the card at the bottom of the screen (`AppUpdateNotice`, in the root `Box` of `MainActivity`, under `AdLoadingNotice` and over everything else) says which one it is. Two details are load-bearing. **The check is skipped while the guide is on screen** — telling someone who has just installed the app to update it says they installed the wrong thing — and **«Позже» is remembered for the process** (`dismissed`), because repeating a declined offer on every screen change is not hearing the answer; only the manual check from «О приложении» clears it. The automatic check runs **once per process** (`checkedInProcess`) for a duller reason: `MainActivity.onCreate` also happens on every rotation, and the check is a round trip to the store. The controller lives in `AppContainer`, not in a ViewModel, for the same reason `DataTransferController` does: the download is in RuStore and outlives the screen, the rotation and the backgrounding.
- **`ReviewController` asks for a rating, and it asks in exactly one place: when the person closes the «Поздравляем!» dialog after a batch has been carried to term and the chicks counted — and only if there are any** (`IncubatorScreen`, the `onDismiss` of `HatchCelebrationDialog`, which itself exists only for `hatched > 0`). That is the one minute in this app when a person has something to be glad about, and the one that is known in advance not to be a bad moment. It used to fire from the finish dialog's confirm button; it moved *after* the celebration because a RuStore window over the fireworks would have been a window over the party, and because the celebration is already the one funnel point every on-time finish passes through — the batch sheet, the card menu, the prompt for one batch and for a party. The usual «on the fifth launch» would land on the person who opened the app to find out why the reminder never came, and would collect an honest rating of that. **Not more than once per version** — `AppSettings.reviewAskedVersion`, written *before* the window is shown rather than after it succeeds: if RuStore had nothing to show today it will have nothing tomorrow either. RuStore has its own limit (`RuStoreRequestLimitReached`) and it is not enough on its own — it is their rule, not ours, and a second window after the second hatch of the week is no longer a request. The manual «Оценить приложение» in «О приложении» has no conditions and, if the in-app window cannot be shown at all, **falls back to opening the app's RuStore page**: a button that is pressed must do something.
- **Push notifications get their own channel, and that is the whole design.** `RuStorePush.init` runs from `InventoryApplication.onCreate` — the SDK requires it, which means it also runs in the process WorkManager starts for a reminder, so nothing heavy may happen there. The channel is `Новости` (`PUSH_CHANNEL_ID`), **not** the reminders' `Инкубатор`: reminders are what the app was installed for and ring at `IMPORTANCE_HIGH`, while news about a new feature must be silenceable on its own — with one channel for both, someone tired of news would switch off the reminders, that is, the app. The id is **repeated verbatim in the manifest** (`ru.rustore.sdk.pushclient.default_notification_channel_id`), because the SDK draws the notification itself and the manifest cannot see Kotlin constants; the same rule as the `device_prefs` filename in the backup rules — let them drift and nothing shows at all on Android 8+. `IncubatorMessagingService` therefore draws nothing: it exists because the SDK needs a declared service to deliver into, and it reports `Events.PUSH_RECEIVED` — with no server of its own, that event is the only evidence a broadcast was ever delivered. `RuStorePush.logToken()` prints the device token to logcat, which is the only way to send a test push to your own phone.

**All four of those are switched off at once by the version name, and the switch is `IS_RUSTORE_BUILD` in `rustore/RuStoreBuild.kt`** — a `versionName` ending in «r» («1.1.0r») means the build goes to RuStore, anything else («1.1.0») means it does not. Off go the «Оценить приложение» / «Проверить обновление» card in «О приложении», the automatic update check with its `AppUpdateNotice`, the review request after a hatch, and `RuStorePush.init`. **Not a `productFlavor`**, deliberately: flavours multiply build variants, ProGuard runs and the list of things a person has to install and open before a release, while the whole difference here is whether four doors are drawn — and the suffix is visible inside the app, on «О приложении», so an installed build says which kind it is. It is a different question from «is RuStore on this phone»: the SDKs already survive that silently (`AppUpdateController`, `ReviewController`), but offering an update from a store the app was not taken from is wrong even where the store is installed. `isRuStoreVersion` is the rule apart from `BuildConfig`, pinned by `RuStoreBuildTest`; the case of the letter does not matter. **The consequence for releases: the suffix is part of the version, not decoration** — publish «1.1.0» to RuStore and the store half of the app is gone from it.

**The push project id is a build input, not a constant** — `rustorePushProjectId`, read in `app/build.gradle.kts` from `local.properties` first and from the ordinary Gradle property second, and handed to the code as `BuildConfig.RUSTORE_PUSH_PROJECT_ID`. **An empty value is a working state, not an unfinished one**: `RuStorePush.init` then quietly does nothing and the app behaves exactly as it did before push existed, which is what a fresh clone of the repository gets. Filling it in is done in the RuStore console («Push-уведомления» → «Проекты»), and the console wants the SHA-256 fingerprint of the signing key that the uploaded build carries — `keytool -list -v -keystore <ключ>.jks`.

**Opening the app for the first time is two questions, not one, and each has its own flag.** «Show the guide?» is `AppSettings.guidePending`, **which defaults to `true`, so the walkthrough greets the updating user as well as the fresh install** — it explains the app, not the release, and someone with three incubators needs «what is a batch» and «which screens swipe» exactly as much. While it holds, the nav graph starts at `GuideDestination` — «Как пользоваться» in `ui/guide/` — instead of `Start`. «Open the incubator form afterwards?» is `AppSettings.addIncubatorPending`, raised only when `isFirstLaunch()` in `MainActivity` finds `app_prefs` / `is_first_launch` still unset: an empty app has nothing to work with and takes the first step for the user, while the same form over a list of existing devices would read as an invitation to add a fourth. So the two of them part ways at exactly one moment — the end of the guide, where `MainActivity` passes `showGuide` and `openAddIncubator` down through `InventoryApp` to `InventoryNavHost` (`openAddOnStart`).

Both flags outlive the process because `is_first_launch` does not: it is cleared by the very read that returns `true`, so a phone killed mid-guide would come back as an ordinary launch, with the walkthrough unseen and the form unopened. `guideFinished()` lowers both in **one** `SharedPreferences.edit`, and that matters more than it looks: two separate writes with a death between them would strand `addIncubatorPending` raised forever, since the guide that clears it would never appear again, and the incubator form would then open on every single launch. Finishing or skipping also requests the notification permission (moved here from the first frame, so the system prompt no longer lands before the user has seen anything).

**A launch that came from a reminder skips the guide** (`showGuide = guidePending && target == null`) and lowers `addIncubatorPending` on the way past: the person tapped a specific batch, and neither a walkthrough nor an empty form belongs on top of it. The flag stays up, so the guide meets them at the next ordinary launch. Re-reading it later is «О приложении» → «Как пользоваться» (`GuideDestination.routeFor(revisit = true)`, which closes back to where it was opened and touches no flags). Per-screen details are in `ui/CLAUDE.md`.
