# UI (`app/src/main/java/ru/zaroslikov/incubator/ui/`)

Screen-by-screen guidance for the Compose layer. Split out of the root `CLAUDE.md`
so it loads only when working under `ui/`. The naming rules, domain-model semantics
and architecture conventions it depends on stay in the root file.

## Theme and the start screen

The theme lives in its own Gradle module, **`:design`** (`design/src/main/java/ru/zaroslikov/incubator/design/`, package `ru.zaroslikov.incubator.design`), together with every composable that knows nothing of the domain — the sheet primitives, the tab switcher, chips, tiles, the loader, the status bar, `SheetDraft`, `formatCount`. What stays in `ui/components/` is what depends on a batch or a setting: `ScheduleTable.kt` (it edits `ValueUiState`) and `IncubatorTabParts.kt` (`formatMoney` needs `Currency`). The rule for a new component: if its signature can be written without importing `:domain` or `settings/`, it goes to `:design`; otherwise it is part of a screen and stays here. `design/theme/` holds a hand-written Material 3 color scheme (`Color.kt`) with light/dark/`dynamicColor` variants in `Theme.kt`, and downloadable Google Fonts via `ui-text-google-fonts` + `res/values/font_certs.xml`. The medium/high-contrast schemes the Material generator emitted were deleted: nothing selected them.

The **light** scheme and the typography were rebuilt from the Figma mockup
([node 5:682](https://www.figma.com/design/B48q96fOq7Nsy569AXrbWY/Untitled?node-id=5-682), file `B48q96fOq7Nsy569AXrbWY`):

- Fonts are Fraunces (display/titles), Inter (body), JetBrains Mono (`monoFontFamily` — eyebrow and figures). The mockup sets Fraunces' `SOFT`/`WONK` variation axes; downloadable fonts cannot carry those, so the rendered face is plain SemiBold.
- **A paragraph that explains what a feature does is `DesignType.Note` — `Micro` in italics — and it is the only italic in the app.** A card under «Настройки» has three kinds of text: the title, the subtitle beside it («Знак у стоимости яиц, птенцов и инкубатора») and, under the control, a sentence about how the setting behaves («Меняется только знак. Суммы по курсу не пересчитываются…»); the third used to be set exactly like the denominator under a statistics tile, and read as one more label rather than as the app speaking. The same paragraph stands elsewhere — the disclaimer over the batch form's table, the note under «Взять за основу» in the species constructor, the picture caveat in the candling sheet, «Остальные параметры необязательны» in the incubator form, the privacy line on «Настройки» and «О приложении», «Цену не указали у …» on «Аналитика» — and all of them take `Note`. What does *not*: a caption to a number («из 550 завершённых»), a hint on a money row («22 ₽ за яйцо»), an error under a field, an empty state, a dialog's body text — those are data or state, not explanation, and stay `Micro` / `Caption` / `Body`. The italic face is a fourth `Font` in `bodyFontFamily` (Inter, `FontStyle.Italic`); without it Compose would synthesise a slant from the upright face, which works but looks worse.
- **An empty-list placeholder is `DesignType.Placeholder` — Inter Bold 13 / 19.5 — and it is the only bold body text.** A freshly created incubator shows its name, «2 места» under it and then «В этом инкубаторе пока нет закладок»; set in `Caption` like the subtitle, that line read as one more caption rather than as the answer «there is nothing here». Bold makes it the third voice. It goes on every «nothing yet» line: the batch list under its filter chips (`emptyBatchesText`), `EmptyNote` in `IncubatorTabParts.kt` (the «Статистика» and «Финансы» cards, «Пока ни одного своего вида» in the settings), and the start screen's «Добавьте инкубатор…» / «Все инкубаторы в архиве…». The insight card at the bottom of «Статистика» is not one of them even when it says «Завершённых закладок пока нет» — it is the verdict card in its empty phrasing and keeps `Body` in accent.
- `DesignType` (in `Type.kt`) and `DesignPalette` (in `Color.kt`) hold the values that have no Material slot — chip fills per species, the progress track, the emphasised hatch date. Use those instead of inlining hex in composables. The Figma file defines no variables, so every value was read off the raw hex in the mockup.
- **`DesignPalette` is no longer an `object` — it is a `@Composable @ReadOnlyComposable` getter returning the `DesignColors` of the current theme**, read from `LocalDesignPalette`, which `IncubatorTheme` provides as `LightDesignColors` or `DarkDesignColors`. Every token kept its name, so the ~300 call sites did not change; what did change is that it can only be read inside composition — a plain helper that wants a colour now takes it as a parameter. Three tokens were added for the dark theme: `Surface` (the white card / field / pill, raised warm dark in the dark theme), `OnAccent` (what stands on `Accent` — white in light, deep green in dark, because the dark accent had to lighten to keep contrast and white on it would not) and `TabPill` (the switcher's sliding pill). **`Color.White` in the UI is now reserved for exactly one thing**: content on a filled `DesignPalette.Expense` — the red is dark enough in both themes, and the only place left is «Удалить все данные». Anything else that says «white» means `Surface` or `OnAccent`. Switch thumbs used to be the second case and are not any more: an unchecked white thumb on a cream track inside a white card was invisible, and in the dark theme it came out brighter than the checked one, so «off» read as more active than «on» — see `accentSwitchColors()` below.
- **There is still no dark mockup; `DarkDesignColors` is derived, not designed.** The rule it was built by: same meaning, inverted lightness — the cream plashki (#F2EDE3) become warm dark greys (#2A2622), white cards sit one step above the #161411 background (#201D19), accent and red lighten (#6DB48C / #E07B66), the header stays a deep green (#2E5C44) because its three text colours are white and stay white, and the chart bars / lines are the same hues one step brighter. The M3 `*Dark` scheme in `Color.kt` was rewritten to the same family; the old generated greenish-black one had never been seen by anyone. `res/values(-night)/themes.xml` paint the window background in the matching colour so the first frame does not flash — and because those resources follow the *phone's* night mode, `AppSettings.syncNightMode()` pushes the user's choice into `UiModeManager.setApplicationNightMode` on Android 12+ so they agree (see the root file). The system splash is the one thing that lever does not reach — it is drawn before the process exists, from the phone's own night mode — so `windowSplashScreenBackground` is the brand green in both `themes.xml` files rather than a per-theme background: one colour that argues with neither cream nor dark. The one literal that survived the sweep by not being white — `Color.LightGray` behind the reminder `TimePickerDialog` — now takes `MaterialTheme.colorScheme.background` like every other dialog.
- **Which theme is active is the user's choice, not only the system's** — `ThemeMode` (`SYSTEM` / `LIGHT` / `DARK`) in `Theme.kt`, chosen on «Настройки» → «Оформление» with the same `SlidingTabSwitcher` the tabs use (its pill position is animated by `animateFloatAsState`, since there is no pager for it to follow), stored in `AppSettings.themeMode` and collected by `MainActivity`. `SYSTEM` is the default and answers `isSystemInDarkTheme()` live, so the app follows the phone's night mode as it switches. The three icons are `ic_theme_{auto,light,dark}_design.xml`, drawn in the `ic_chart_design` stroke style.
- **The status bar takes the colour of the screen's header, and `StatusBarAppearance` in `design/components/SystemBars.kt` is the single way to ask for it.** `IncubatorTheme` calls it once with the screen background and dark icons — the default, right for the start screen, which wears its header on that very colour — and the screens with a coloured header (`IncubatorScreen`, `MenuScreen`) call it again with theirs and light icons. It is a `DisposableEffect` precisely so the second call undoes itself: a screen that painted the bar green has to give it back on the way out, and the nested call wins while it lives because effects apply parent-first. **What it gives back is `LocalStatusBarDefault` — the theme's current default — not a snapshot of the window taken on entry.** The snapshot version broke on exactly one path: switching the theme while standing on a green-headed screen re-ran the theme's effect and the screen's in the same recomposition, each «remembered» what the other had just set, and leaving the screen then put light-theme icons over a dark background. The theme applies its default through `DefaultStatusBar` (no restore — there is nothing below it) and provides the same value as a composition local; the default is also one of the screen effect's keys, so on a theme switch the screen repaints after the theme has. **It paints from two sides on purpose**: before Android 15 the window will not let content under the bar and `window.statusBarColor` is the only lever, while with `targetSdk` 37 on Android 15+ that field is ignored under forced edge-to-edge and the header itself reaches the top edge instead. One call covers both; the half that does not apply costs nothing.
- **That reach is `contentPadding.withoutTop()` plus a `headerInset` on the header** — the same file's `PaddingValues.withoutTop()` strips the top system inset off the screen and it goes into the header's own top padding, so the green (or grey) block starts at the very top of the display instead of below a cream strip. Screens whose header already sits on the background colour need none of this: what shows behind the bar is the same cream either way.
- **A species is drawn through `SpeciesGlyph` / `SpeciesText` (`ui/start/SpeciesGlyph.kt`), never as `Text(speciesEmoji(…))`.** Four birds are their emoji; the quail is `ic_species_quail.xml`, a coloured vector drawn for the app (owner's request, 2026-10-03), because Unicode has no quail and «🐦» renders on Android as a blue songbird. The glyph is sized in `sp` like the emoji it replaces (1.2 em), so call sites pass a font size and do not care which it is; `SpeciesText` puts it inline into a line that wraps and ellipsizes with its text (the finish prompt, the celebration's breed list). `ProgressRing` takes `species`, not an emoji string. A string with `speciesEmoji()` inside would bring the blue bird back.
- `isAppearanceLightStatusBars` is `!lightIcons`. It used to be `darkTheme`, which painted white status-bar icons over the (now cream) light background — invisible.

**Three screens are `ModalBottomSheet`s, not navigation destinations** — their mockups
([node 9:2738](https://www.figma.com/design/B48q96fOq7Nsy569AXrbWY/Untitled?node-id=9-2738) for the incubator form, [node 12:3555](https://www.figma.com/design/B48q96fOq7Nsy569AXrbWY/Untitled?node-id=12-3555) for the batch form, [node 14:4893](https://www.figma.com/design/B48q96fOq7Nsy569AXrbWY/Untitled?node-id=14-4893) for the batch itself) show a rounded top, a drag handle and a close cross, so they must appear *over* whatever screen is behind them. Each is therefore hosted by the screen that opens it: `AddIncubatorSheet` by `StartScreen` for creating (`incubatorId = 0`, also auto-opened on first launch) and by `IncubatorScreen` for editing; `AddBatchSheet` and `BatchDetailSheet` by `IncubatorScreen`. Because they have no nav entry, the id arrives as a `Load` intent (`viewModel.onIntent(…Intent.Load(id))`) from a `LaunchedEffect`, not through `SavedStateHandle`, and the state resets on every open; «saved» comes back as an effect (`CollectEffects`), which is where the host closes the sheet — see the MVI paragraph in the root file. **Two more sheets have since joined them without a mockup of their own, hosted from inside `BatchDetailSheet` rather than by a screen** — `BatchAnalyticsSheet` and `CandlingSheet` — and both are written as *siblings* of the `ModalBottomSheet` call, never inside it, so each lands in its own window above the batch instead of inside it. `viewModel(factory = …)` in a sheet must stay a default parameter for the same reason it already is: evaluated at the call site it resolves against the host's `ViewModelStoreOwner`, which is the nav entry. The parts they share — drag handle, header row, `FieldLabel`, `SheetTextField`, `SheetPickerField`, the 20/16/48 dp constants — live in `design/components/SheetForm.kt`; put anything a second sheet would need there rather than copying it.

**`SheetTextField` is built from `BasicTextField` + `OutlinedTextFieldDefaults.DecorationBox`, and must stay that way.** The ready-made `OutlinedTextField` pins itself to `defaultMinSize(minHeight = OutlinedTextFieldDefaults.MinHeight)` — 56 dp — which `heightIn` cannot reduce, so every field stood 8 dp taller than the 48 dp `SheetPickerField` and the «за яйцо / за всё» switch beside it. The decoration box takes `contentPadding` with zero vertical padding, so `heightIn(min = FieldHeight)` alone sets the height and the field still grows instead of clipping when the system font is enlarged. Anything placed next to a field in a `Row` should use `FieldHeight`, not a literal.

**Two colour sets in `SheetForm.kt` serve every accent control in the app, and both exist because a copy per call site had already drifted.** `accentButtonColors()` paints the main button — «Создать инкубатор», «Заложить яйца», «Записать замер» — and decides how it goes out: **the fill fades, the label does not.** The mockup dims the whole thing to 40 % and left the label white, which is a contrast under 2:1 — enough to see that something is written there and not what. That does not read as «disabled», it reads as a button that failed to draw, and both of those buttons are disabled exactly when the screen is first looked at. The fill now drops to a hint of green (16 %) and the label takes the full accent. `accentSwitchColors()` does the same job for the two `Switch`es (the incubator form's automation flags, «Напоминания» in the settings): the unchecked thumb is `onSurfaceVariant` rather than white — dark on cream, light grey on dark — and the checked one is `OnAccent`, by the theme's general rule that what stands on the accent is painted with it.

**`SheetPickerField` is tappable across its whole frame**, because its inner `Row` is `fillMaxWidth()`. Without that the row wraps its content, and a picker with no `trailing` — the value is `weight(1f, fill = false)` — offered only the width of the text plus padding: on a full-width «08:00» that is a third of the frame, and tapping the empty right-hand side did nothing. It changes no layout, since the value is left-aligned either way.

**Нажатие мимо поля снимает фокус, и это один модификатор на всё приложение** — `Modifier.clearFocusOnTap()` в `design/components/FocusClear.kt`. Он ловит тап через `detectTapGestures` в основном проходе, то есть только тот, который не забрали себе поле, кнопка или карточка: касание по соседнему полю переводит фокус в него, а не гасит его на полпути, и ни одна кнопка не теряет свой клик. Вместе с фокусом уходит и клавиатура — отдельный `SoftwareKeyboardController` для этого не нужен. **Ставить его надо в каждом окне отдельно**: `Scaffold` в `InventoryApp` покрывает все экраны навигации, но шторки и диалоги живут в собственных окнах, куда события корневого `pointerInput` не доходят, — поэтому он же стоит на корневой колонке `AddIncubatorSheet`, `AddBatchSheet`, `BatchDetailSheet`, `CandlingSheet`, `CustomSpeciesSheet` и в теле обоих диалогов завершения (`FinishBatchDialogs`). Новая шторка с полем ввода — новая строчка с этим модификатором. В форме инкубатора он стоит **до** `padding` и в паре с `fillMaxHeight()`: иначе тап ловила бы только площадь под содержимым, а не вся шторка.

**Brand and model suggest previously used values.** `SuggestingSheetTextField` (`design/components/SheetForm.kt` — shared with the batch form’s breed field, see below) wraps the ordinary sheet field in an `ExposedDropdownMenuBox` fed by `getUsedBrands()` / `getUsedModels()` (`SELECT DISTINCT … WHERE … != ''`). Typing stays free — a new brand is always allowed — and the dropdown chevron appears **only when the list is non-empty**, so it never promises a menu that has nothing in it. The list narrows to entries containing what has been typed; **once the field holds one of the entries whole — the one just picked — it shows all the others**, so a wrong pick is fixed by a second pick rather than by clearing the field. **Both placeholders are a plain «—»**, matching «Стоимость, ₽» beside them: an example brand and an example model ("Rcom, Блиц…", "72 Turbo") read as the value of a device somebody already owns, and next to a *real* suggestion list — which is what the chevron offers — an invented example is the one entry that is not the user's own. The dash says the same thing the caption above says, that the field may be left empty. **«Вместимость (яиц)» wears the same dash**, and so does «Количество яиц» in the batch form: a quantity is read off the device or counted into the tray, and an example there — «48», «24» — read as a value already entered rather than as a hint. The one-line cap with an ellipsis stays in place for the same reason it was added: with the chevron taking space, a longer placeholder wraps and makes the field taller than its neighbour. **The name field's placeholder counts**: «Инкубатор 3» for someone who already has two — `AddIncubatorViewModel.nextNumber`, backed by `ItemDao.countIncubators()` (`SELECT COUNT(*)`, a number rather than `getAllIncubators()` mapped to domain models on every change to the table). Archived devices count too: they still exist, and suggesting the name one of them already wears suggests confusion. Two cases have no number, and both say the same thing — a number that would be wrong is worse than no number. Until the database answers, `nextNumber` is `null` and the field reads plain «Инкубатор»; «Инкубатор 1» there would be an assertion, and a false one for the owner of three. And editing has no number at all: that device is already counted, so «следующий» would name one that does not exist — clearing the name of the second of three devices is no reason to read a hint about a fourth. The count is the literal rule the number follows, so a deleted device frees its number; the placeholder is a hint, not a reservation.

**Only the name is required.** The mockup marks `Название *` alone and states outright that the rest is optional, so `isValid` checks the name only — this deliberately overrides the earlier spec where capacity was mandatory. A device saved without capacity shows only «N яиц в инкубации» (eggs of its running batches) on the card — no percentage, no bar, and no «укажите вместимость» request; in the archive it shows nothing at all there (removed at the owner's request, 2026-10-02: an optional field should not nag from every card).

`ui/start/StartScreen.kt` follows the mockup: a large title (the app-menu icon sits in that row — the mockup has none, so its placement is an invention; it used to be an info icon opening `InfoBottomSheet`, and both are gone, see «The app menu» below), then cards. **The mockup's two stat tiles — «Активных закладок» and «Яиц в работе» — were removed**: both restated in the largest type on the screen what the cards under them already say device by device, and they cost ~100 dp of the permanent chrome above a list that is the reason the screen is opened. The same two figures still stand where they answer something — in the green header of an incubator, about that incubator — and the household totals live in «Аналитика». `StartUiState` therefore carries no `activeCount` / `eggsInWork`. **The mockup's eyebrow above the title — «МОЯ ПАСЕКА», wording inherited from another app — was dropped**: it named the wrong domain, and «Инкубаторы» already says what the screen is. `DesignType.Eyebrow` stays in the theme, unused, so a correct надзаголовок is one line away. Card geometry worth preserving: the progress bar clamps at 100 % while the percentage label shows the true ratio — the mockup's first card is 108 of 72 places, i.e. 150 % with a fully-filled bar.

Cards degrade for pre-migration rows, and must keep doing so: `model` falls back to the species when blank, and `capacity == 0` hides the percentage and the bar. Every project that existed before v2 is in exactly that state until its owner edits it.

**The list is ordered by how many batches are running in each device, most first** (`StartScreenViewModel`, `sortedByDescending { it.activeBatches }`). The DAO returns incubators by `_id`, i.e. in the order they were added, and that order answers a question nobody asks: the device bought first stayed at the top for years after it went quiet, while the three in use sat below the fold and had to be scrolled to on every launch. **The sort is stable, and that is the whole tie-break** — within one count the order of addition survives, so cards with the same number of batches do not reshuffle between answers from the database. Archived cards go through the same sort and are unaffected by construction: archiving stops every batch a device holds, so their key is zero across the board.

**The capacity block is `CapacityBlock` in `ui/incubator/IncubatorCapacity.kt`, shared with the batch form** (see the batch form section) — one composable so that the form promises exactly what the card shows after the save. **Over 100 % the capacity block goes red, all of it** — the egg icon, «80 / 72 места», the percentage and the bar (`overfilled = eggs > capacity`, `DesignPalette.Expense`, the same red as «Удалить» and «Завершить досрочно»). Overfilling is ordinary — eighty eggs go into a tray rated for seventy-two — so nothing is blocked and no warning is shown; what is not ordinary is learning about it from a line coloured exactly like a half-full incubator. The bar still clamps its fill at 100 % (the mockup's first card is 108 of 72, i.e. 150 % with a full bar), so the colour is the only thing left that can say «больше, чем влезает».

**The name and the «бренд · модель» line are capped at two lines each, and a truncated one shows itself whole in a tooltip on tap** (`TruncatedText`, now in `design/components/TruncatedText.kt` — the tiles' figures are its second caller, see «A figure in a tile is one line» below). Both are what the user typed, so their length is unbounded: «Инкубатор в летней кухне у бабушки» ran to five lines and pushed the species chips, the occupancy and the hatch date — everything the card is looked at for — below them. The tap is needed because the part that gets cut is exactly what tells two devices apart («Инкубатор на веранде (левый)» vs «(правый)»). **A `PlainTooltip` rather than expanding the text in place**: the card then keeps its height, the cards under it do not shift, and the answer needs no putting away — a tap anywhere else dismisses it. `isPersistent = true` for the same reason — the ~1.5 s a plain tooltip lives by default is the lifetime of a label on an icon, not of a sentence someone is reading — and `maxWidth` is raised from Material's 200 dp to 280 dp (`TooltipWidth`), which at 200 broke a long name into a column of three-word lines on a screen twice that wide. It is attached **only when the text actually overflowed** (`hasVisualOverflow` from `onTextLayout`, keyed by the text because a lazy list reuses cards): the card carries its own `onClick` into the incubator and a child tap wins over it, so taking that tap away from names that fit would cost half the card for nothing. No ripple on the tap: what is pressed is the text finishing itself, not a button.
  - **`enableUserInput = false` — `TooltipBox`'s own gestures are replaced, not merely disabled.** They are built for a label on an icon: the tooltip comes up on long press and goes down the instant the finger lifts. On a name someone is *reading* that looked like a fault — hold the text, it flashes and vanishes — and worse, it contradicted the quick tap beside it, which raised the same tooltip for good. One gesture now, an ordinary tap, behaving the same however long it lasts.
  - **That tap toggles — show, then hide — and it is a hand-written gesture rather than an `onClick` for one reason.** The popup does not swallow touches outside itself, so the second tap on the same text arrives in two windows at once: the tooltip gets `ACTION_OUTSIDE` and closes itself, while the anchor gets an ordinary tap. Which lands first is not defined, so an `onClick` asking «is it visible now?» answers itself differently from run to run, and the toggle fires every other time. The visibility is therefore read at the **press** (`awaitFirstDown` on the `Initial` pass), when the tooltip is by construction still on screen — it cannot have closed before the touch that closes it — and the answer no longer depends on the race: visible then, so hide; not visible, so show. `up.consume()` on the same pass keeps the tap from also opening the incubator: the card parses the gesture on `Main`, after us. The a11y path is a `semantics { onClick(...) }` beside it, since the anchor no longer carries a `clickable`.
  - **The colours come from the app palette, not from Material's `inverseSurface` pair.** That pair inverts the theme by design — a dark tooltip on a light screen, and a *light* one on a dark screen, i.e. a white rectangle popping up in the one place everything else went dark. The tooltip uses the same `DesignPalette.Surface` and `CardBorder` as the card beneath it, so it follows the theme instead of arguing with it, and a shadow (`shadowElevation = 6.dp`) is what separates the two rather than a colour change.

**The card's «⋮» stands where the mockup draws a chevron, and it replaced it rather than joined it.** The menu holds two items — «Убрать в архив» / «Вернуть в список» and «Удалить» — and neither the mockup nor any other screen offers a way to them, while a card the whole width of the screen is already tappable: a right-pointing arrow beside the menu would repeat what the tap already says and make both targets need aiming. It is the same arrangement `BatchCard` inside the incubator arrived at, and the same `MoreVert` + white 16 dp `DropdownMenu`. The cost is 12 dp of card width, added back as an `end` padding on the title column and on everything below the header row, so the capacity bar still ends where it did in the mockup.

**An archived card keeps the capacity and drops the fill.** `CapacityBlock(archived = true)` prints «22 места» and nothing else — no «0 /», no percentage, no bar. Those three answer «насколько он сейчас занят», and a device out of service is not occupied and will not be: archiving stops every batch it holds. An empty bar under «0%» reads as an idle incubator, i.e. as a reproach, where capacity is simply a property of the device and is still true. Same decision as the header figures on the incubator screen, one level down. A capacity of zero leaves the archived card without the block at all (owner's request, 2026-10-02) — there are no eggs to count and no capacity to print; the card no longer says «вместимость не указана».

**Archived devices live behind a second tab, and the tab is `SlidingTabSwitcher` — the same component the incubator screen switches its three tabs with.** It replaced `ArchiveToggle`, the bordered «Архив (N)» row that expanded the archive in place under the list. Two things were wrong with the row: the archive appeared *below* the list, so on a farm with more than a screenful of incubators it had to be found by scrolling, and an expanded archive interleaved with the working list — the same card shape, one after another, with only a row between them saying where the boundary was. Tabs make the two halves exclusive, put the way in above the content, and cost nothing new: the switcher, its sliding pill and the swipe between pages are already the screen-inside-an-incubator idiom.
- **The switcher appears only when the archive holds something** (`hasArchive`), and the pager's `pageCount` follows the same flag. A two-tab indicator with one permanently empty side is a signpost pointing nowhere. Returning the last incubator from the archive therefore removes the tab under the user's feet, and a `LaunchedEffect(hasArchive)` scrolls the pager back to page 0 — the same fallback the batch filter chips make when the selected category empties out.
- **It arrives and leaves animated** — `AnimatedVisibility` with `expandVertically` + `fadeIn` / `shrinkVertically` + `fadeOut` over `TabsSlideMillis` (180 ms), the same duration as the batch filter row, because it is the same movement: a strip above a list coming and going. Both events happen while someone is looking at the screen — the first incubator archived creates the tab, the last one returned destroys it — and a switcher that pops in reads as the screen having jumped. **The 16 dp spacer under it lives inside the `AnimatedVisibility`**, or the block would collapse by only half its height and the list would still jump the rest.
- **The labels are adjectives without counts — «Активные» / «Архивные».** Not «Инкубаторы» / «Архив»: the screen title has already said what these are, and repeating it spends half a tab's width on a word that separates nothing; as adjectives both halves are named the same way, by the state of the device. Counts were tried and dropped — a figure beside the label changes under the finger (archive one incubator and both numbers move at once), while the pill answers «where am I», not «how many are there». How many are on each side is what the list itself shows, which is what one switches tabs to see. The archive tab keeps `baseline_archive_24`, the same icon as the read-only notice and the batch «Архив» chip.
- **The header and the switcher do not scroll.** They sit in a fixed `Column` above the pager and each page scrolls on its own — again the incubator screen's anatomy, and required by it: a pill indicator that scrolls away stops indicating. The chrome used to be ~290 dp; without the stat tiles it is about a hundred less, and the list starts that much higher.
- **`fillMaxSize()` on each page's `LazyColumn` is load-bearing**, not decoration: a pager page centres content shorter than itself, so with `fillMaxWidth()` a two-card list floated in the middle of the screen with equal gaps above and below it, ~50 dp clear of the switcher.
- When *every* incubator is archived the first page reads «Все инкубаторы в архиве — они на соседней вкладке.» instead of the welcome text: «Добавьте инкубатор» would be advice to do the wrong thing, and an empty page under a switcher asks «а где всё» — the answer belongs where the question is.

**Archiving asks first too, because it ends the batches inside.** `Incubator.hidden` used to be a pure list decision — the card left the screen, its clutches went on incubating — and the press was silent for exactly that reason. It is not that any more: `StartScreenViewModel.setIncubatorHidden` stops every running batch of the device (`stoppedEarly`, reason «Инкубатор переведён в архив», reminders cancelled), so the same tap now writes a zero hatch into records that will not undo themselves. `ConfirmArchiveIncubatorDialog` therefore names all of it — how many batches, under what reason they will be found afterwards, and the half that surprises people: **the incubator comes back out of the archive, the batches do not** — each is returned by its own «Вернуть в инкубацию» inside. Its confirm button is red, the same `DesignPalette.Expense` as «Удалить» and «Завершить досрочно», because that is the company this action now keeps. **The dialog appears only when `activeBatches > 0`** — on a device with nothing running the archive is still the harmless list move it always was, and a question about consequences that will not happen only teaches people to confirm without reading. «Вернуть в список» stays silent in both cases: it takes nothing away.

**Deleting asks first, and the question names the number of batches** (`ConfirmDeleteIncubatorDialog`, wording parallel to the batch one). It is the largest cascade the app can start — every batch of the device with its days, measurements, candlings and reminders — and «Удалить инкубатор?» on its own reads like «take this card off the list», which is what the *other* menu item does. The reminders themselves are cancelled in `StartScreenViewModel.deleteIncubator` before the row goes, one batch at a time: WorkManager is not reached by any foreign key.

## The incubator screen

`ui/incubator/IncubatorScreen.kt` follows mockup [node 5:547](https://www.figma.com/design/B48q96fOq7Nsy569AXrbWY/Untitled?node-id=5-547): a green (`DesignPalette.HeaderSurface`) header with three figures, then a cream sheet carrying three tabs — **Закладки** (`IncubatorScreen.kt`), **Статистика** (`IncubatorStatsTab.kt`), **Финансы** (`IncubatorFinanceTab.kt`). The tabs are a `HorizontalPager`, so swiping between them is part of the design, not a bonus; the pill switcher only calls `animateScrollToPage`. That switcher is `SlidingTabSwitcher` from `design/components/SlidingTabs.kt`, the same composable the batch sheet uses — the screen owns only the tab list and the outer padding, so any change to the animation lands on both at once.

- **In the header the name comes first and the model line under it** — the mockup's order was the reverse, an eyebrow «BLITZ 72 TURBO · 72 МЕСТ» above the title, but the device's own name is what the user gave it and what they look for, and the model is a detail about it. Moving it also cost it the eyebrow's typography: it is `DesignType.Caption` (Inter 12) in mixed case, not mono capitals with 2.16 sp of tracking — that treatment reads as a label *over* a title and fights the name when it sits under one. `DesignType.HeaderEyebrow` stays in the theme unused, next to `Eyebrow`, so the mockup's version is one line away. `headerModelLine()` **returns an empty string when neither brand nor model is filled in — then the line is not drawn at all**, capacity included: «· 72 мест» on its own reads as the tail of a sentence whose beginning is missing. `modelLine()` in `StartScreen.kt` returns blank for the same case rather than the old «Модель не указана» placeholder, and the incubator card hides its line too — an empty optional field is not news worth a row of text. The card keeps `DesignType.Mono` from the mockup; the two places differ because one sits under a 30 sp display title and the other under a 21 sp card title. **Both lines are capped at one line here, not two as on the card, and a truncated one shows itself whole in a tooltip on tap** (`TruncatedText`, the same composable and the same gesture — see «A figure in a tile is one line»). The card can afford two: it is one item in a list, and a name that takes an extra line pushes only its own card's contents. The header stands above the entire screen, so every line the name grows costs the figures, the tab switcher and the list below them the same height on every incubator — and «Инкубатор в летней кухне у бабушки» is a length the user chooses, not one the screen does. What gets cut is exactly what tells two devices apart, so the tap gives it back. **Nothing separates the «Все инкубаторы» row from the name — no spacer, and the first line's top leading is trimmed away too** (`LineHeightStyle.Trim.FirstLineTop`). The emptiness was already there twice over: the back row is 48 dp tall because that is the minimum touch target, while the label inside it is 21, so a dozen-odd points of air sit under it before anything is added — and a 4 dp spacer plus the 30/37.5 leading were stacked on top of that. Only the **first** line is trimmed, so the leading inside a wrapped name and the gap down to the model line stay as the mockup has them. The row itself is not the place to save: 48 dp is where the finger lands, not how big the icon looks.
- **The sheet's `offset(y = -17.dp)` is load-bearing.** The mockup tucks the tab block 17 dp into the green header, and the 24 dp top corner radius is what lets the green show through at the edges. Drop the offset and the notches fill with cream, killing the effect. The 24 dp of background the offset leaves at the very bottom is the same cream, so the seam is invisible.
- The header **stays, but its figures collapse while the list is scrolled down** — `statsCollapsed` in `IncubatorScreen`, a `NestedScrollConnection` on the screen's outer column reading the sign of `onPreScroll`'s `available.y` against the same `ChipsScrollThreshold` the filter row uses, and the same 180 ms `AnimatedVisibility`. It is the filter row's trick one level up, and it sits on the screen's column precisely so that it hears all three pages without any per-page plumbing. What goes is the row of three figures **with its 20 dp spacer inside the same `AnimatedVisibility`** — outside it, the block would collapse by only part of its height. The name and the model line never move: they answer «where am I». The reason is arithmetic — on a 2400 px screen the header held a fifth of the height for three numbers, one of which is «0 · Выведено» for most of a working incubator's life, and the list got a little over half the screen. The collapsed header is **exactly the geometry an archived incubator already had** (name, model line, no figures), which is what says it looks like something. Each pager page still scrolls on its own: «Статистика» and «Финансы» get that scroll from `ScrollingPage`, the shared page wrapper holding the 20 dp side padding; «Закладки» repeats the same padding inside a `Box`, because it has to hang the floating «+» over its own scroll.
- **The three figures are «Яиц в работе», «Выведено» and «Эффективность», left to right.** «Активных закладок» was the first of them and was dropped at the owner's request: the batch list right under the header already counts the running batches, while how well the device hatches was nowhere above the tabs. «Эффективность» is `IncubatorUiState.stats.hatchRate` — the very number of the «Статистика» tab's tile, percent hatched over finished batches — printed «87%», and «—» both while loading and while nothing has finished yet (`null` is «неизвестно», not «0%»). The paragraphs below that still name «Активных закладок» describe the reasoning, which holds for any three captions.
- **The three figures stand in one row of equal thirds — a `Row` with `weight(1f)` on each, not a `FlowRow`.** They are read as one summary and against each other, and wrapping broke that: the third figure dropped under the first and «Выведено» became a second caption to «Активных закладок». The thirds are equal because the mockup's columns are, and because sizing by content would hand the width to the captions instead — «Активных закладок» is wider than any number that can stand above it, so the longest figure would be squeezed in favour of the longest word. **A fixed row has to fit the screen itself, and it does it the way the rest of the header does**: the figure is one line, with an ellipsis and a tooltip on tap (`TruncatedText`, `maxLines = 1`), and the caption wraps to two lines instead. The split is deliberate — the figure is data whose low digits are its precision, so it truncates and offers them back on a tap; the caption is three words the app wrote itself, so «Активных закладок» over two lines still reads, while «Активных зак…» would read on every incubator and not just on a seven-figure one. A wrapped caption grows the whole row at once, evenly, rather than one column. **The price is the enlarged system font**, which is what the `FlowRow` used to absorb: at 200 % the first caption is two stacked words and a seven-digit figure is finished by its tooltip. Verified on a 1080×2400 / 460 dpi emulator at both 100 % and 200 %.
- **The dashed «Добавить закладку» keeps its place under the list, and a mini «+» stands in for it while it is off screen.** With a dozen batches the button left the bottom of the screen, and laying a new one meant scrolling the whole incubator past first. It is still inside the scroll, exactly where the mockup puts it — a fixed footer would eat the same 90 dp of list on every incubator, including the ones with two cards — and `AddBatchFab` — a 48 dp `SmallFloatingActionButton`, `DesignPalette.Accent` on white, the same pair as `StartScreen`'s «+ Инкубатор», but round and with no label, because that one stands on empty background and this one hangs over cards — fades in over the list once the dashed one is out of view. **Which is answered by the list, not by counting cards**: the dashed button is an item with a key of its own, and `listState.layoutInfo.visibleItemsInfo` says whether that key is on screen. It used to read `boundsInWindow()` through `onGloballyPositioned`, which worked only while the button was built even when scrolled away — in a lazy list an off-screen item does not exist, so there is nothing to measure. An empty `layoutInfo` is the first frame, before measurement: the button counts as visible then, or the mini one would flash over an empty screen. Counting batches would have to guess screen height, card height and whether the archive is expanded; this stays right on every device and in every state.
- **While anything is running in the incubator, that dashed slot is split in two: a wide «Внести замер» and a square «+».** The reading is the daily action — the reason the screen is opened at all — and a new batch is a monthly one, so the width goes to the first and the second keeps only its plus (`DashedIconButton`, the same dashed surface, height and radius as `DashedButton` next to it, so the pair reads as one button cut in two; the plus alone already means «новая закладка» here, since the mini FAB in the corner draws exactly that). With no running batch there is nothing to measure and «Добавить закладку» stands alone at full width again, as in the mockup; an archived incubator draws neither. **Both variants are one list item under `AddButtonKey`**, so the floating button keeps asking the list whether that item is on screen and fades in and out exactly as before. **What floats is split the same way**: with running batches it is `MeasurementSplitFab` — a Material 3 split button at the bottom centre, `DesignPalette.Accent` on white, a wide «Внести замер» segment with the thermometer and a «+» segment, 2 dp apart, outer corners at half the height and inner ones at 8 dp so the cut reads as one button cut in two — and without them the old mini «+» in the bottom-end corner. Centre rather than corner because a wide button in the corner would cover the «⋮» of two cards at once; hand-built rather than `SplitButtonLayout`, which is experimental and shaped around a trailing menu. `DashedButton` took an `icon` parameter for this — a thermometer, because a plus in front of «Внести замер» would promise the wrong thing. The tap opens `IncubatorMeasurementSheet` (below) and reports `Events.OPEN_INCUBATOR_MEASUREMENTS`.
- **That mini button sits in the bottom-right corner, the same one `StartScreen`'s «+ Инкубатор» uses, and that is where it is wanted.** The «⋮» of every card lives at the same right edge, so a card that comes to rest directly under the button has its menu covered — which is why the button is 48 dp and круглая rather than an extended FAB: it hides one card's menu at a time, and any scroll frees it. It was briefly at `BottomStart` for exactly that reason; the corner is a deliberate choice, so keep the button small if it stays there.
- **The screen no longer nests its own `Scaffold`.** The root `Scaffold` in `InventoryApp` already supplies system-bar insets through `contentPadding`; adding another one double-counted the status bar. **The status bar is no longer cream above the green, though** — it used to be, on the reading that the mockup draws it over the cream body, but a cream strip above a full-width coloured header reads as the header having been pushed down rather than as a design. It now takes the header's own colour, grey included, through `StatusBarAppearance`; see the theme section for how, and for why the top inset moves into the header's padding.
- **The header goes grey in the archive and drops all three figures**, keeping only the name and the model line. Green means «в работе» everywhere in this app — the accent, the «Инкубация» chip, the finish button once the term is up — so a device taken out of service under the same green reads as still running; `DesignPalette.HeaderSurfaceArchived` (#6E675C) is the warm grey relative of `StatusDoneText`, dark enough that the three header text colours stay as they are and only the ground under them changes. The figures go together rather than one at a time: the strip answers «что здесь происходит сейчас», and in the archive nothing does. Two of them are zero by construction anyway — archiving stops every running batch (see the root `CLAUDE.md`) — so «0 · Активных закладок» and «0 · Яиц в работе» would describe the archive rather than this incubator, in the largest type on the screen. «Выведено» is a real recorded outcome, but left standing alone under the name it reads as the headline figure of a working device; the same number, with everything it is made of, is one tab away in «Статистика», which the archive does not touch. The 20 dp spacer goes with the row, so the grey block is simply shorter — the sheet's `-17.dp` overlap and its corner radius work against any header height.
- **An archived incubator turns the whole screen into a reader, and it does it by subtraction.** `IncubatorUiState.readOnly` (i.e. `Incubator.hidden`) removes the «⋮» from every batch card, both «Добавить закладку» buttons (the dashed one and the mini FAB), and the «Инкубация завершена» prompt; `BatchDetailSheet` opens with `readOnly = true`. Nothing is greyed out instead: a menu whose every item is dead, or a form that cannot save, reads as a broken screen rather than a locked one. What replaces them is one line — `ReadOnlyNotice`, a bordered row above the list — because a control that silently vanished is a control the user will look for. The status chips, the filter row and the archive button all stay: they are ways of reading a list. **The pencil in the header stays too** — it edits the device, not its batches. **So does the QR icon beside it** — the code is a property of the device, and a sticker is printed before the device goes back to work. Deliberately there is no «вернуть из архива» here: the archive is put on and taken off on the start screen, and a second door into that decision would make «where do I un-archive this?» a question with two answers. **«Статистика» and «Финансы» of an archived incubator open with the same row** (`ArchivedTotalsNotice`, `ReadOnlyNotice` with its own text; owner's request, 2026-10-02): the figures on these tabs still count the device's batches, but «Аналитика» of the farm no longer does (root `CLAUDE.md`), and that has to be said where the figures are read. It replaced a notice inside each batch sheet, which the owner rejected — the totals are the subject, so the note stands over the totals.
- **The old archive toggle — the one that split the list in two — is gone.** Finishing a batch no longer takes it off the screen: it stays in the same list with a «Завершено» chip, exactly as the mockup's duck card does. The «Архив» button over the list is not that toggle: it holds only the batches someone chose to put away, one by one, via the card menu. Editing the device moved to the pencil in the header row — the mockup has no such control, so its placement is an invention, same as the icons on `StartScreen`.
- **A batch card is tapped through `Card`'s own `onClick`**, the way `StartScreen`'s `IncubatorCard` already was, not through a `Modifier.clickable` handed in from the list. The ripple then follows the 22 dp corners instead of the rectangle around them, and the «⋮» inside keeps its own press — a child click still wins over the card's.
- **The status chip has three states, not two: «Инкубация», «Завершено», «Не завершено»** — `StatusChip(status)` in `ui/batch/StatusChip.kt`, fed by `Batch.status` from `:domain` (see the root `CLAUDE.md`). It is shared with the batch sheet's summary card, which shows the same chip opposite the species line — one word in one colour for one clutch, wherever it is looked at. The third one is a batch someone stopped before its term, and it is red — `DesignPalette.Expense` on `ExpenseSurface`, the same pair as the «Завершить досрочно» button and its «в расход» tile, so the chip is recognisable as the outcome of that action. It deliberately does *not* get its own palette entry: one red in the app is the point. A neutral «Завершено» on such a batch was the previous behaviour and read as «прошло как надо», which is exactly what did not happen — and the card says nothing else about it, since `endReason` is only visible inside.
- **«Архив» is a fourth chip that stands *beside* one of those three, never instead of it** — `ArchiveChip()`, rendered next to `StatusChip` whenever `batch.hidden`. The two answer different questions: the status says how the clutch ended, the archive says where the card is kept, and collapsing them would lose the first. That matters precisely where it shows: hidden batches appear only behind the «Архив» button, and there the status is the only thing separating a clutch taken to hatching from one pulled on day five. It is **outlined** rather than filled — the three statuses are outcomes and own the fills, this one is a note about the list and should read second; the two neutral fills were taken by «Завершено» and «Не завершено» anyway. And it is the **word**, not the box icon the filter chip uses: there the icon stands alone and reads as a place to go, here a picture beside text would read as an icon *of the status*.
- **That title row is a `FlowRow`, and it has to be.** With a plain `Row` the chips are unweighted and get measured first, so they take their full width before the `weight(1f, fill = false)` title sees anything left: «Не завершено» + «Архив» is about 156 dp of a 206 dp row on a 375 dp screen, and the name was reduced to an ellipsis — the archive became a list of nameless cards. In a `FlowRow` the title is measured against the whole row instead and the chip group, kept together in its own nested `Row` (6 dp gap), drops to a second line when it cannot fit beside it. The name always wins, because that is what the card is found by; a status reads fine from the line below. Verified on a 1080×2400 / 460 dpi emulator: both «Завершено» + «Архив» and «Не завершено» + «Архив» wrap, and the name shows in full. **An active batch with a short name still keeps its single chip on the title line**, exactly as the mockup draws it — only a name long enough to crowd the chip pushes it down now, which is the trade the ellipsis used to make invisibly.
- **A stopped batch also gets its own progress line, and its ring is not full.** `batchProgress` branches on the status: the day comes from `dateEnd` (`daysBetween(start, ended) + 1`, clamped to the species' term), so a clutch pulled on day 5 of 21 shows «День 5/21» with the ring at a quarter, and the caption reads «Прервано 12 авг.» instead of «Выведено 12 авг.» — nothing was hatched, and `trailing` stays null because `eggAllEND` is zero by construction. Drawing it the old way — full ring, «День 21/21» — claimed an incubation that never happened. A batch whose `dateEnd` will not parse falls back to a zero ring and a bare «Прервано».
- **«День N/M» stands under the ring, not in the stat line beside the egg count.** The ring is the picture of that number — the filled arc *is* «шестой из двадцати одного» — so the label reads as its caption rather than as one more figure in a row; the two sit in one `Column` centred on the ring so «День 6/21» and «День 21/21» do not shift against it. The stat line keeps only the egg count. A batch with no day (no parseable start date) gets no caption and no spacer, so the ring stays where it was. **On the last day the hatch line reads «Вывод 30 сент. · завтра», not «через 1 дн.»**: the hatch date is `start + term`, the calendar day *after* day M, and «через 1 дн.» beside «День 21/21» read as a day beyond the term.
- **Under the title the card names the bird and its breed** — «Курицы · Ломан Браун»: `batch.type` only when the batch has a title of its own (a nameless batch already shows the type *as* its title), then `batch.breed`, and the line is absent altogether when both halves are blank. Before it the breed appeared nowhere on the card, though two trays of the same bird differ by exactly that. It is a one-line `TruncatedText`, like the title, and takes the same 40 dp `end` padding so it stops where the «⋮» starts.
- **The ring also has a colour, and it answers the same two questions the chips do** — `progressRingColor(status, archived)` beside `ProgressRing` in `IncubatorScreen.kt`. Four answers, because the questions are «чем кончилась» (`BatchStatus`, three of them) and «лежит ли в архиве». Accent green while it runs; **`DesignPalette.ProgressDone` — the same green a step darker — once it has hatched**, since a full ring in the running colour said nothing to tell a recorded result from a clutch sitting on the last day of incubation, and the outcome is a good one, so red and grey are the wrong way to say it; `DesignPalette.Expense` for a stopped one — the red of its «Не завершено» chip, since a green arc on an interrupted clutch says «идёт как надо» exactly where it did not; `DesignPalette.StatusDoneText` grey for anything `hidden`. **Archive wins over the outcome**: a batch put away was put away on purpose, and behind the «Архив» button the list should read calmly rather than shout red about what has already been dealt with; the outcome is not lost, because the status chip stands beside the «Архив» one. The grey is `StatusDoneText`, not `HeaderSurfaceArchived` — the latter is a ground for white header text and in the dark theme (#4A453E) the arc would all but vanish into the card; `ProgressDone` is #2E5C44 on light (the dark theme's own header green) and #3F7D5C on dark (the light theme's accent), which is ≈3.4:1 against the dark card — enough for a 6 dp arc. **The batch sheet's summary ring asks the same two questions** (`BatchDetailUiState.status`, derived from `finished` + `stoppedEarly` exactly as `Batch.status` is derived in `:domain`, and `hidden`, carried for this and nothing else), because it is the same ring about the same batch as the card it was opened from.
- **Each batch card carries a «⋮» menu** — `BatchCardMenu`, another invention: without it edit, archive and delete are all behind opening the batch first, and those three are wanted precisely while looking at several cards at once. It is **not** in the title row: the title there is `weight(1f, fill = false)`, and a second weighted child beside it would cap a long name at half the width. **It lies over the card in a `Box`, `align(Alignment.TopEnd)` with a 16/8 dp inset — it used to stand in the card's outer `Row`, and that is what cut the hatch date off.** In the row it took its 56 dp (48 dp button plus the 8 dp the card's right padding drops to, compensating the icon button's own 12) out of the whole text column, down to the bottom of the card, though it is only needed level with the name. On a 375 dp screen that left the bottom line about 190 dp for «Вывод 4 окт.» beside «через 28 дн.», and the date — the content of that line — ellipsized to «Вывод 4 …». Overlaid, the button occupies only the empty corner above the стат-строки, the two lines below get the full width, and the title `FlowRow` hands those same 56 dp back as an `end` padding of its own (16 dp of card padding + 40 dp), so a long name still stops where the button starts. In the archive, where there is no menu, the padding is zero and the title uses the whole width.
- **The hatch line is a `FlowRow` too, for the same reason the title row is one.** With a plain `Row` the unweighted «через 28 дн.» is measured first and eats the date's width; on a narrow screen or an enlarged system font it still would, however much room the menu gives back. `SpaceBetween` keeps the mockup's arrangement while both fit and drops the срок onto a second line when they do not — the date is what the line is written for, and «через N дн.» reads perfectly well from below it.
- **«Убрать в архив» means two different things, on purpose, but both end in the archive.** On a batch whose chip reads «Инкубация» it opens `FinishBatchHost` — the real finish dialogs — because a running batch cannot be filed away without saying how it ended; a silent flag flip there would be the second finish path that was just removed. **That path passes `hide = true`, so the same save both finishes the batch and sets `hidden`**: the item promises the archive, and a batch that only turned into a «Завершено» card in the list demanded a second identical press to actually get there. It is one write, not two — `BatchDetailViewModel.archive(finished, hide, onDone)` puts both flags into the one `updateBatch`, so the list never flickers through an intermediate state, and an already-raised `hidden` is never cleared. **Which of the two statuses the batch lands on is the dialogs' own fork, and it stays that way**: mid-term the early dialog runs, the reason is obligatory and the card comes out «Не завершено» — archiving a running clutch *is* interrupting it — but on the last two days the on-time dialog asks for chicks instead and the card reads «Завершено». Making the menu item unconditionally «Не завершено» was considered and rejected: it would zero `eggAllEND` on a batch archived the day it hatched, and «средний вывод» would count that clutch as 0 %. **Archiving the whole incubator does exactly that unconditionally, and the difference is that it has no one to ask**: a device with three running clutches cannot open three chick-count dialogs in a row, so it stops them all with one reason and warns before the press instead — see «Archiving asks first» on the start screen. Here, with one batch in hand, the dialogs are affordable and the fork stays. On a batch whose chip already reads «Завершено» or «Не завершено» the result is recorded, so the item asks nothing and just sets `hidden` — the outcome chip stays and «Архив» joins it — undone by «Вернуть в список» in the same menu. The rest: «Редактировать» (the `AddBatchSheet` form, hosted by the screen like every other sheet), «Вернуть в инкубацию» on finished batches only (`reopened()` — a statement about the batch, not about the list, hence a separate item), and «Удалить».
- **«Экспортировать расписание» is the one menu item that reads instead of writes, and it is the one item an archived incubator keeps.** It appears only on a batch with `Batch.exportable` (hatched, chicks > 0 — the rule and its reasons are in the root file under «Schedule files»), and it is absent rather than disabled on the others: a greyed item promises to light up some day, and a stopped batch's never will. It opens `ExportScheduleDialog` (`ui/incubator/ScheduleExportDialogs.kt`) — the same «на устройстве / отправить» pair as the database copy in «Настройки», for the same reason two buttons and not a guess — whose text says what leaves and what does not (the day table, the average of the measurements, the species, and for reference the breed and the incubator’s brand and model; not the name, eggs, the readings themselves or reminders); then either `ACTION_CREATE_DOCUMENT` with `ScheduleTransferController.fileNameFor(batch)` or the share chooser; `ScheduleTransferDialog` reports the outcome. The batch is looked up by `exportBatchId` when the system window answers, like every other id-held action on this screen. **In a read-only incubator the «⋮» is drawn anyway on an exportable batch, and `BatchCardMenu(readOnly = true)` holds only the reading items** — this one and «В «Моё хозяйство»»: the archive lock is about changing the batches, and copying out a regimen changes nothing.
- **«В «Моё хозяйство»» stands under «Экспортировать расписание» on a batch that hatched chicks, whenever the farm app is on the phone** — the celebration's farm button for later, since the party is one minute and the chicks move to the farm whenever their owner gets round to it (root `CLAUDE.md`, «Моё хозяйство»). `farmStatus` is read once per screen and on every resume (`LifecycleResumeEffect`) and serves both the party and the menu; an outdated farm keeps the item and answers it with `FarmUpdateDialog`, which counts as an overlay for the «Инкубация завершена» prompt. A send that fails to open re-reads the status, so an uninstalled farm takes the item with it. The house icon is `baseline_cottage_24`.
- **The list is filtered by a row above it: a dropdown of statuses — «Все · Инкубация · Завершённые · Не завершённые», each with its count — and, beside it, an «Архив» toggle button, and that button is how the archive is reached** (owner's request, 2026-10-02; it used to be a `FlowRow` of five `ChoiceChip`s, which wrapped onto a second line on a narrow screen and took that height out of the list). The dropdown is `SheetDropdownField` from `SheetForm.kt`, the button `ArchiveToggleButton` — the same `FieldHeight` / `FieldRadius` as the field, the box icon and the archive count, filled with the accent while the archive is shown, so the row says which list is under it. The row stands between the tab switcher and the scrolling list, outside the scroll. `IncubatorUiState` still carries two lists, `batches` and `hiddenBatches`; the figures above the list and the «Статистика» / «Финансы» tabs are computed from everything **except** the hidden ones (the archive is set aside from the statistics too — root `CLAUDE.md`), and the row only chooses what the list shows.
- **The statuses are a partition, not overlapping queries, and they work inside the archive too** — they are exactly `BatchStatus`, computed by one `groupBy { it.status }` per scope (`statusGroups`, once for the main list and once for the archive). «Завершённые» means *дошла до срока* and does not count the stopped ones, so the counters add up to «Все». The archive is not a status: `hidden` is about the list, not about how the batch ended, which is why it is a separate button and not a dropdown item, and why `BatchFilter` is its own enum rather than a `BatchStatus?`. With the archive shown, the dropdown lists the archive's own statuses (its «Все» reads «Весь архив») — there is still a «Завершённые» / «Не завершённые» split to make there.
- Three details of that row are load-bearing. **The dropdown lists only non-empty statuses**, so it never offers a category that shows an empty list. **The row appears only when there is something to separate**: `archived.isNotEmpty() || statusGroups > 1`, where `statusGroups` counts the non-empty ones of the three statuses of the main list — so a young incubator keeps the mockup's plain list, an incubator where one batch runs and another was stopped gets the row, and an incubator where *everything* has been put away still shows the way in; the archive button itself is drawn only while the archive holds something. And **the selected status and the archive mode both fall back when their category empties out** — return the last batch from the archive and the list goes back to the main one with the button gone. The fallback also writes the state back (`LaunchedEffect`), because a merely-displayed fallback left the stored choice waiting: putting the next batch away then jumped the screen into the archive on its own.
- **Every change of what the list shows is animated, and the whole list moves as one layer.** Entering the archive slides it in from the right, leaving it brings the main list back from the left, and a status picked in the dropdown makes the list rise 16 dp from below — all fading in over 260 ms (`listSwitch`, an `Animatable` read only inside `graphicsLayer` together with `switchKind`, so its frames do not recompose the tab). Sideways means «another place», the short rise means «the same list, narrowed»; when both change in one frame (the archive opened and the chosen status is not there) it counts as entering the archive. Not `Modifier.animateItem()` per card: a lazy list keeps disappearing items composed beside the arriving ones, and an ad slot's single `BannerAdView` would then be wanted by two cards at once. The «Архив» button itself expands in from the end of the row with the first archived batch and shrinks away with the last (`AnimatedVisibility`, the 8 dp gap inside it, the count held so the leaving button does not read «0»).
- **The row hides while the list is scrolled down and comes back on the first pull towards the top** — a `NestedScrollConnection` on the tab's outer column reads the sign of `onPreScroll`'s `available.y`, and `AnimatedVisibility` collapses the row vertically (180 ms) so the list closes the gap rather than jumping. The direction comes from the scroll event, not from a diff of `scrollState.value`: it arrives already signed and before the list has moved. `ChipsScrollThreshold` (3 px) throws away the finger's jitter, which would otherwise blink the row in place. **At `scrollState.value == 0` the row is shown unconditionally** — at the very top there is nothing to win by hiding it, and a screen returned to its start should look like its start.
- The choice is kept in `rememberSaveable` as an **ordinal**, not the enum — `Bundle` does not take enums — and it survives rotation on purpose: browsing the archive is a mode you entered deliberately, unlike the old expand-in-place row, which reset every time you left the screen.
- **Switching a filter scrolls the list back to the top, and that is not politeness.** A lazy list remembers its place by item number, so a short result was shown from wherever the long one had been left: switching to «Архив» with one batch in it opened on an empty screen, the card sitting above the top edge. The plain scrolling column hid this only because its scroll clamped itself to the end of the shortened content.
- **The list itself is a `LazyColumn`, and the statuses behind the chips are computed once per answer from the database, not per frame.** The body of the tab recomposes on every finger movement — the chip row hides and returns on scroll — and a `groupBy` over every batch plus five `buildList` calls used to ride along with each of those frames; `batchGroups` now sits behind a `remember`. «Are we at the top», which decides whether the chips are shown unconditionally, goes through `derivedStateOf`: the list position changes every frame, that answer twice per gesture. What forced the list to be lazy is the ads: every third slot is a live `BannerAdView` with a `WebView` inside, and a plain column built all of them at once — measured on an Android 15 emulator, an incubator with eleven batches held 18 `View`s on entry against 12 now, and the four ad slots were requested before anyone had scrolled to them.
- **`FinishBatchHost` owns its own `BatchDetailViewModel` under `key = "batch-finish"`.** The batch sheet on this same screen holds one under the default key; without the explicit key they would resolve to a single instance and the card menu would reload the sheet underneath it. The key is constant rather than per-batch — `load()` resets the state anyway, and a key per batch would pile one ViewModel per card into the store.
- **Entering the incubator with an overdue batch opens the «Инкубация завершена» prompt** — `ui/incubator/FinishedBatchPrompt.kt`, off-mockup. The result of a batch — how many chicks hatched — is entered by hand and by nobody else, so a batch whose term ran out while the app was closed just hangs in «Инкубация» and stays out of средний вывод until someone remembers it. The prompt only announces and offers: its button opens `FinishBatchHost`, the same two dialogs the card menu and the batch sheet use, rather than asking for the count itself. Details worth keeping: **the due check runs in composition, not in `IncubatorViewModel`** (the answer depends on the current clock, not only on what the flow emitted); **the term expires at the laying hour of the hatch date** (`batchFinishMoment()` — the one and only reader of `Batch.time`; blank time falls back to that day's midnight); **overdue batches keep being offered**, not just today's, because the app may not have been opened for a week; **one prompt at a time**, the oldest, since two stacked dialogs cannot be read; and **«Позже» is a real answer** — chicks do not pip by the clock, so the batch stays in incubation and the prompt returns on the next visit to the screen. Tapping «Внести птенцов» also sets the dismissed flag, or cancelling the finish dialog would bounce straight back into the prompt with no way out of the pair. **It opens the host with `hide = false`, unlike the card menu**: the prompt asks for a result, it does not file anything away, and a вывод just entered by hand is exactly what one wants to see in the list. The same goes for «Завершить инкубацию» at the bottom of the batch sheet — only the menu item that says «в архив» archives. `FinishedBatchPromptTest` in `app/src/test` pins the timing rules.
  - **The prompt reads in three voices, not one paragraph**: the fact on two lines — «Срок инкубации — 21 день», then «Истёк **19 сент., 10 дней назад в 06:48**» with the moment in accent (appended to the first line, the date broke in the middle), then the batches as a white bordered card like the list's (`DueBatchesCard` — a party's name and species over one row per breed with its egg count in mono; a single batch as one row with «вид · порода» under it), then the request in `Body`. The italic explanation that followed it — archive, average hatch, «Позже», leave a breed blank — was removed at the owner's request (2026-10-02); the buttons say enough. It was one continuous text with the breeds listed inside a sentence, and there was nothing for the eye to catch on. The group dialog's intro follows the same split: the question plain, the «оставьте пустой» rule in `Note`.
  - **A tray laid for several breeds is prompted as one party, not breed by breed.** The form lays it as one batch per breed, so their terms run out in the same minute — and «one prompt at a time» plus the dismissed flag meant the person was asked about the first breed and saw the second only on the next visit. `groupDueToFinish()` takes the oldest due batch and every due batch `laidTogether()` with it: same incubator, species, date, laying hour and title up to the breed tail (`baseBatchTitle`, the inverse of `splitBatchTitle`). There is no party column and none is needed — the form copies exactly those fields into each batch; two batches of one day under different names («Для себя» / «На продажу») stay separate on purpose. A party of one keeps the old path (`FinishBatchHost`); two or more open **`FinishGroupHost`** (`FinishBatchDialogs.kt`, own `FinishGroupViewModel` under `key = "batch-finish-group"`) — one dialog with a hatched field and a chick price per breed, the same `FinishRow` / `ChickPriceField` / `hatchedHint` as the single dialog, and each batch written through the same `finishedOnTime`. **A blank breed is «not yet», not zero**: only the filled rows are finished, the button reads «Завершить 1 из 2» and a caption names what stays in incubation, and the prompt comes back to the rest on the next visit — by then a party of one, i.e. the ordinary dialog. The rows are keyed by batch id (a breed finished elsewhere while the dialog is open drops out without shifting the others' input); `FINISH_ON_TIME` fires once per finished batch with an extra «Партия» parameter, `INCUBATION_REPORT` goes out for all of them in one `reportIncubationOutcomes`, and the celebration (below) lists every finished breed. The batch sheet's own «Завершить инкубацию» and the card menu still finish one batch — they were opened on one batch.
- **Every on-time finish with chicks ends in `HatchCelebrationDialog`** (`ui/batch/HatchCelebrationDialog.kt`) — a full-screen `Dialog` (`usePlatformDefaultWidth = false`, like the chart's) with `Fireworks` from `:design` behind a white card: 🐣, «Поздравляем!», one line saying what finished and how many hatched of how many laid (`celebrationLine`, pinned by `HatchCelebrationTest`: a batch by its name, a party by `baseBatchTitle` and its number of breeds), then the figures as the `StatTile`s of «Итог по замерам» (`MeasureTile` fill, no border) — «Заложено · Выведено · Вывод», then only what there is to say: «Отбраковано» when there was a cull, «Срок инкубации» when the species is known. **Money is not a tile but its own block under them, «Прибыль»** (`ProfitBlock`, owner's request, 2026-10-02): a large figure — how much was earned on the chicks, `HatchSummary.profit`, green on `IncomeSurface` or red on `ExpenseSurface` — and under a hairline its parts, «Выручка за птенцов +X», «Яйца −Y», «Электроэнергия −Z» with kWh. With no egg price the figure is the revenue and says so, with no chick price it is «—» over the listed expenses (the rules are `HatchSummary`'s, root `CLAUDE.md`). **For a party it is counted breed by breed (`profitView`), not from `combined()`**: that summary drops a price missing from any one breed, so a party with the egg price typed for one breed only used to say «стоимость яиц не указана» outright. Now the lines sum what is known, and the large figure is a profit only when every breed has both prices. **Every explanation sits behind an «i» (`HintIcon`), not in text** (owner's request, 2026-10-02): beside «Прибыль» — how it is counted, or which breed lacks which price; beside «Выручка за птенцов», «Яйца» and «Электроэнергия» — where that sum comes from (kWh for the light) and whose share is missing. Under the figure stays only a short caption («заработано на птенцах» / «выручка за птенцов» / «заработок неизвестен»). `HatchCelebrationTest` pins it. A party gets a breed-by-breed list above the totals, the zero breed included and greyed. **The screen hosts it, not the sheet**: `IncubatorScreen.celebration` is set from `BatchDetailSheet(onSummary)`, `FinishBatchHost(onFinished: (HatchSummary?))` and `FinishGroupHost(onFinished: (List<HatchSummary>))` through one `celebrate` lambda, which reports `HATCH_CELEBRATED` and refuses a party with no chicks — **except a stopped batch, which gets the same dialog as «Инкубация прервана»** (`HatchSummary.stopped`, owner's request, 2026-10-02): no `Fireworks` at all, 🥚 instead of 🐣, `stoppedLine` («остановлена на 6-й день из 21»), the reason on the red `ExpenseSurface` plate of `EndReasonCard`, tiles «Заложено · Отбраковано · Оставалось» and «День остановки · Срок инкубации», `ProfitBlock(title = "Расходы", view = lossView(…))` — the same block fed a view with no revenue and a negative headline — no farm offer, «Понятно» for the button, and no event or review request on dismissal (`HatchCelebrationTest` pins the line and the money view). **A zero hatch on time is the third face, «Птенцы не вывелись»** (`empty`: not stopped and no chicks in total, so a party only when every breed is zero): `emptyHatchLine`, the ordinary `BreedResults` / `HatchTiles` with the «Выведено» zero in plain colour rather than accent, and the same «Расходы» `lossView` instead of «Прибыль» — equally without fireworks, farm, event or review; the sheet closes first, so the party stands over the list where the «Завершено» card already is. It counts as an overlay for the «Инкубация завершена» prompt, so the next due batch is offered only after «Отлично» — which is also where the RuStore review request now lives (root `CLAUDE.md`, «ReviewController»). **When «Моё хозяйство» can take them, a `FarmOffer` block stands between the tiles and «Отлично»** — secondary-coloured (`IncomeSurface` / accent, the pair of «Отправить в другое приложение») so it does not argue with the card's own button, one button per batch with chicks (a party: «Хайсекс, 22 птенца → в «Моё хозяйство»», nominative, because «добавить 22 птенца» is shaky Russian — `farmButtonLabel`, pinned by `HatchCelebrationTest`), never greyed after a press (the farm's «куда» sheet can be dismissed by accident, and a dead button would strand the chicks), and a `Note` line saying the farm will ask «new project or existing» and add the group there. `IncubatorScreen` asks `FarmApp.status` on every showing and on every resume (`LifecycleResumeEffect`) — «Обновить» sends the person to the store, and coming back with the new version must turn it into «Добавить» without closing the party. An outdated farm gets `FarmUpdateOffer`: one button for the whole party and a `Note` saying why. The contract is in the root `CLAUDE.md`, «Моё хозяйство».
- **Reopening a batch clears its result** — `Batch.reopened()` in `:domain`, reached from the card's «⋮» menu, which is now the only door to it. `IncubatorUiState.hatched` sums `eggAllEND` over *all* batches, so a batch back in incubation carrying its old count would show chicks that have not hatched yet. It clears `hidden` too: a running batch has to be on screen. **Reminders come back with it**, rescheduled from the batch's own `Batch_time` rows — finishing cancelled the scheduled work, never the rows, so there is somewhere to restore them from. They used not to, on the reasoning that only the batch form knew the times; that reasoning was simply wrong, and a batch marked as running again while staying silent was indistinguishable from a bug. See «Notifications» in the root `CLAUDE.md`.
- **The header shows «Выведено» and «Эффективность», not «Прибыль», and it stays that way now that finances exist.** The mockup asks for profit, and `IncubatorFinance.balance` could supply it — but all three money fields are optional, so a hatchery that never types a price would get a header reading `0 ₽` forever, which is exactly the breakage the original swap avoided. The profit lives one tab away, under a card that can explain itself when there is nothing to show; the header cannot.
- `IncubatorViewModel` derives every figure from existing rows — no new columns. Note that **средний вывод counts only archived batches** (`sum(eggAllEND) / sum(eggAll)`): active ones still have `eggAllEND = 0` and would drag the percentage down. «Всего яиц» on the «Статистика» tab counts finished batches only, like the species chart.
- Chart bar colours (`DesignPalette.ChartBars`) are picked **by position** in the descending-sorted list, not by species — that is how the mockup assigns them.

### The «Статистика» tab

`IncubatorStatsTab.kt` grew past the mockup's two tiles and one chart: it now answers «сколько», «насколько хорошо», «за счёт чего» and «когда» in that order — four summary tiles, the species chart with breeds inside it, efficiency — by species, again with breeds inside it — and the hatch history. Everything still comes out of the batches already in the database; **no column and no table was added for any of it**.

- **The arithmetic lives in `:domain` (`domain/stats/IncubatorStats.kt`), not in the composable.** `incubatorStats(batches, candlings)` returns the whole tab's numbers, and `IncubatorStatsTest` pins them with a plain JVM test — `gradlew :domain:test` runs in seconds with no emulator. The screen only lays the numbers out. The `IncubatorUiState.hatchRate` / `eggsBySpecies` pair that used to be computed inline in the ViewModel is gone; `IncubatorUiState.stats` replaces both.
- **Two different denominators, and mixing them is the bug this is shaped to prevent.** `eggs` in every slice spans *all* batches of that slice, including running ones — «сколько яиц этого вида прошло через инкубатор» is a question about what was laid. `rate` spans *only* finished ones (`StatsSlice.finishedEggs` / `finishedHatched`), because a running batch has `eggAllEND = 0` and halves the percentage without breaking anything visible. A slice with nothing finished yet has `rate == null`, rendered as «—»: that is «неизвестно», not «ноль».
- **The four summary tiles carry no captions and count finished batches only, and «Отбраковано» there is the remainder** (owner's request, 2026-10-01) — `finishedEggs`, `finishedHatched`, and `finishedEggs − finishedHatched` for the cull, so «Всего яиц = Вылупилось + Отбраковано» always holds: eggs that reached the hatch and did not pip count as culled too, as do the leftover eggs of a stopped batch. This tile alone departs from the two-ledger sum (`Batch.eggRejected` + candlings), which the species, breed and history rows still use; eggs still in the incubator are simply not in that figure. The captions that used to explain the gap («10 закладок · 150 в инкубации», «429 из 550 завершённых», «из 700 заложенных») are gone. `IncubatorStats.totalEggs` / `rejected` (all batches) are unchanged; `totalEggs` still feeds the AppMetrica profile. One level down `sliceFooter` still appends «(2 заверш.)» to a slice's batch count whenever some of its batches are still running.
- **«Отбраковано» adds two ledgers on purpose** — `Batch.eggRejected` (typed by hand, for eggs lost between candlings) and the sum of that batch's `Candling.rejected`. This is the same sum «Осталось» uses in the batch sheet, and for the same reason: neither field replaces the other. It needs candlings for the whole incubator, hence the new `ItemsRepository.getCandlingsFor(incubatorId)` — one JOIN query rather than one subscription per batch, the same trade `getBatchMeasurements` makes.
- **Породы come from `Batch.breed`, not from `Species`.** `Species` rows are the extra *species* chips on a card; the breed is one field of the batch, and a breed row of the statistics is the batches of that species wearing that name — a tray laid as «Ломан Браун» and «Хайсекс» is two batches, and each feeds its own breed its eggs, its hatch and its whole cull (typed-in plus candlings). A batch with a blank breed collapses into a «Без породы» row (`NO_BREED` in `:domain`) — **one per species, not one for the incubator**, since breeds are now counted inside their bird — and it is excluded from the «лучшая порода» line in the insight card: it is not a breed but several batches whose field nobody filled, and recommending it would be nonsense.
- **There is exactly one breed cut, `SpeciesStats.breeds`, and both cards render it.** The chart legend expands it a species at a time, the efficiency card lays all the groups out at once, and `IncubatorStats.breeds` flattens it for the best-breed line. The flat `byBreed` that used to be computed separately is gone: two counts over the same batches drift, and the same breed would eventually show two different percentages in two cards of one screen.
- **«Эффективность по породам» is no longer a card of its own — breeds now expand inside their species' row, on tap.** It stood directly under «Эффективность по видам» showing the same thing: the same bars, the same percentage, the same colours — and the species was named a second time by a group header (`BreedGroupHeader`) that deliberately carried no numbers so as not to read as one more breed. There was nothing to keep them both open with: a species routinely has five or six breeds, and the whole page between «Эффективность» and the hatch history turned into a wall of bars in which the ratio *between species* — what the card is opened for — could no longer be read. `SpeciesEfficiencyGroup` is now the species row plus an `AnimatedVisibility` holding its breeds' bars. **It is exactly the fold the chart legend above uses** (`SpeciesLegendRow`), deliberately: two different ways to expand a species' breeds on one tab would be counted as two different actions. Hence the shared details — the «›» chevron rotating 90° through `animateFloatAsState`, `rememberSaveable` keyed by species name (a rotation or a swipe to the next tab does not collapse what was opened), and the «nothing to expand» rule: a species whose only «breed» is `NO_BREED` does not expand at all, since the row inside would repeat the species' own figures under a name that names nothing. Breed rows are indented 8 dp (and all rows of the card stand 8 dp apart — reduced from 20 / 12 at the owner's request, 2026-10-02) so a group cannot be mistaken for a continuation of the species list, and each takes **that species' `barColor`** — the same colour its bar has in the chart and its row has in the legend, so the cards read as one conversation. The whole species row is the tap target, not the chevron alone: a chevron is a state indicator the size of the type, and there is no reason to aim a finger at it on a full-width bar. `StatsSlice.species` survives as a plain `String` for one caller only: the insight card's best-breed line, where a breed stands alone, pulled out of its group, and needs «(Курицы)» in brackets.
- **Breeds hide behind the species legend row, and a species with only «Без породы» does not expand at all** — its one child row would repeat the parent's number under a name that names nothing. Expansion state is `rememberSaveable` keyed by species name, so rotating or swiping to «Финансы» and back does not collapse it.
- **The bar chart row is 190 dp, not the mockup's 160.** The egg count printed above each bar is off-mockup (otherwise the height has to be read off the legend), and at 160 dp the tallest bar pushed its emoji out of the row.
- **The bar row scrolls sideways when the species do not fit.** The mockup has three species spread across the card; «Аналитика» counts the whole farm — five built-in species plus any number of the user's own — and the bars past the card's edge used to be simply clipped, silently. `MinBarGap` (16 dp) is the whole rule: a `BoxWithConstraints` gives the content either the card's width, in which case `SpaceEvenly` lays the bars out exactly as the mockup does and there is nothing to scroll, or the width the bars actually need, and then the gaps shrink to that minimum and the row starts moving. **One code path, not two** — a separate «and if there are many of them» branch would have parted ways with the first at the next change to a bar. The bar cannot be narrowed to make them fit instead: an emoji stands under it and a figure over it.
  - **No card on this tab has a subtitle under its title** — the chart, «Эффективность по видам» and «История выводов» used to carry «Нажмите вид…», «По завершённым закладкам», «Завершённые закладки, свежие сверху»; the owner asked for all of them to go. `CardHeader`'s `subtitle` is optional for that (`null` draws the title alone); «Финансы», «Настройки» and «О приложении» still pass theirs.
  - **The `BoxWithConstraints` wraps the header and the chart but not the legend.** The legend expands its breeds with a height animation, and keeping it inside a subcomposition would mean measuring it afresh on every frame of that expansion. The width is also captured into a local before the inner `Column`: inside it `ColumnScope` becomes the implicit receiver and `maxWidth` is no longer reachable.
- **Прерванные закладки stay in the history and in every average.** They are the "сорвалось" half of the record, and an incubator whose failures were quietly dropped would read better than it is. The row shows a red 0 % and «не завершено» instead of «N из M», using the same `DesignPalette.Expense` as the batch card's «Не завершено» chip.
- **A history row of a custom species names the species in its subtitle**, before the breed — a built-in bird is named by its emoji, a custom one only gets the generic 🥚. «Custom» is «not in `SpeciesCatalog.BUILT_IN`», so a deleted custom species is still named; skipped when the row's title already is the species (an unnamed batch).
- **A history row does not print its cull; a tap unfolds it** (owner's request, 2026-10-02). The collapsed row is «what, where, when, how many hatched»; the cull is wanted when working out what went wrong, so `CullBreakdown` under the row — full width, no indent (owner's request) — lists «Отбраковано вручную» (`Batch.eggRejected` — on a hatched batch that includes the eggs that did not pip), one line per recorded candling by day with its ordinal («Первое овоскопирование · день 7», `stageTitle`; a zero cull stays in — «checked, all fine» answers «на каком» too) and «Всего отбраковано». The parts come from `HatchRecord.manualRejected` / `candlingCulls` in `:domain`; the ordinal is `SpeciesCatalog.candlingStage`, so both ViewModels pass `incubatorStats(…, catalog = …)` and a day the catalog does not know reads «Овоскопирование · день N». The fold is the same «›» and `AnimatedVisibility` as the species rows, `rememberSaveable` per batch id; a row with nothing culled and no candlings does not fold at all.
- The history shows five rows before «Показать все (N)»: the card sits in the middle of a scrolling page, and years of batches unrolled by default push everything under it off the screen.
- **In «Аналитика» each history row also names its incubator, and it comes first in the subtitle** — «pp · 2, Hisex · 11.09.2026». First because in a history of the whole farm «where was this» is asked before «which breed», and because the end of the line is what a clip takes off, while the incubator is the new thing the line is read for. **On the incubator screen the same row does not name it**, and that is decided in one place rather than by a branch in the UI: `HatchRecord.incubator` is filled from an `incubatorNames: Map<Long, String>` handed to `incubatorStats`, which only `AnalyticsViewModel` passes. Empty name, nothing printed — so a column of one repeated device name never appears where every row is about that device anyway, and it does not push the breed and the date out. An id missing from the map (a deleted device) reads as the same ordinary «no name», not as a fault. `IncubatorStatsTest` pins all three cases. The name is a map rather than a field on `Batch` because the device's name is not a property of a clutch, and putting it there would carry it through the whole domain for the sake of one caption.
- Icons exported from the mockup live in `res/drawable/ic_*_design*.xml` as stroke-only vector drawables; `Icon(painter, tint = …)` recolours them, so the hex baked into `android:strokeColor` is only a fallback.

### The «Финансы» tab

`IncubatorFinanceTab.kt` used to be a stub — the mockup's layout over hardcoded zeros, an empty operation list and an inert «Добавить операцию» button. It is real now, and **it got there without a migration**: the app already stores three money facts, and the whole tab is derived from them. `Batch.price` / `pricePerEgg` is what the eggs cost, `Batch.chickPrice` / `chickPricePerHead` is what the chicks fetched, `Incubator.price` is what the device cost; electricity, added later, is a fourth that nobody types — it is computed from the power and tariff fields (below). There is no operation entity, no ledger, and the dashed button is gone — there was nothing for it to add.

- **The arithmetic lives in `:domain` (`domain/stats/IncubatorFinance.kt`)**, next to `IncubatorStats` and for the same reasons: `incubatorFinance(incubatorPrice, batches)` returns the whole tab, and `IncubatorFinanceTest` pins it with a plain JVM test. It reaches the screen as `IncubatorUiState.finance`.
- **«Расход» is eggs plus the incubator, and the caption under it is load-bearing.** `IncubatorFinance.expense` sums two things of different natures — consumable stock and a one-off equipment purchase — so the tile is captioned «инкубатор + яйца», and the incubator card below writes the addition out in numbers (стоимость инкубатора + вложено в яйца = общий расход). Without that, anyone who totals their own batches finds the expense bigger than their arithmetic and concludes the app miscounts. With no price on the device the caption falls back to «вложено в яйца»: promising a term the sum does not contain is worse than promising nothing.
- **«Вложено» is the eggs half of that расход** — `IncubatorFinance.invested`, stored as `eggsExpense`. Both figures were asked for and both are real questions; they differ by exactly the price of the device. The per-unit metrics divide the eggs half, never the total: equipment is bought per neither egg nor chick, and folded in it would make the first chick of a hatchery cost as much as the incubator.
- **«Потери» are part of the расход, never added to it.** They are the price of the eggs that did not become chicks — a slice of what was already spent — and adding them to expense would charge the same eggs twice. Both the summary tile and the per-batch breakdown label them «часть расхода».
- **Losses count eggs, not money divided by an average.** `IncubatorFinance.lostEggs` sums the actual unhatched eggs of finished priced batches, because `lost / expensePerEgg` is nonsense the moment two batches were bought at different prices — with 150 ₽ goose eggs beside 15 ₽ quail eggs it overstates the count by half.
- **Every average has its own denominator, and the denominator is printed under it.** Same discipline as «Статистика», same reason. `expensePerEgg` divides by `pricedEggs` (eggs of batches that actually have a price — a batch without one contributes zero to the numerator and would drag the average down), `avgChickPrice` by `pricedChicks`, and `chickCost` by `hatchedWithCost` — **finished batches only**, exactly as `StatsSlice.rate` is: a running batch has spent its money and produced no chicks yet, and alone would send the cost per chick through the roof.
- **A blank price is «не спрашивали», not «бесплатно», and the tab repeats that three times.** Under the balance («1 закладка без цены»), in the tiles' hints, and in the closing insight. It is not redundancy: a missing price makes the balance look better than it is, and each of those three places is where someone decides whether to trust the figure. With no prices anywhere, `hasMoney` is false and the whole tab collapses into one card naming the three places the prices are entered — zeros in every tile would read as an answer.
- **The incubator's own price is inside the balance, and `payback` is therefore computed from `profitOnBatches`, not from `balance`.** The balance already has the equipment subtracted; dividing it by that same price would deduct it twice, and a hatchery that had exactly broken even would read as 0 % instead of 100 %. `profitOnBatches` (`income − (eggsExpense − activeInvested)`) is the pre-equipment profit **of finished batches only** (owner's request, 2026-10-01): laying a new batch used to drop the payback at once, since its eggs were paid for and its chicks not yet sold. The percentage clamps below at zero («минус 40 % окупаемости» means nothing) and deliberately **not** above 100, since exceeding it is the whole point. **While nothing is running the balance crosses zero exactly at 100 % payback** — `IncubatorFinanceTest` pins that pair, and also that a running batch moves the balance and not the payback. The footer under the bar uses `profitOnBatches` while it is still climbing and `profitOverEquipment` once it is past 100 % — not `balance`, which the eggs of a running batch can hold below zero under a bar that says «окупился».
- **The incubator card is «Детализация расходов» (`ExpenseBreakdownCard`) and it is always on the tab** (owner's request, 2026-10-02) — also under `NoMoneyCard` when no price is entered anywhere. Its three addends are always listed: «Стоимость инкубатора» reads «не указана» and «Электроэнергия» «не посчитана» in grey when missing, then «Вложено в яйца» and «Общий расход»; only the payback bar and its footer need the device's price, and without it they are simply absent while an «i» beside «Стоимость инкубатора» (`PaybackRow(hint = …)`) says where to enter it. No subtitle under the title. It used to be titled «Инкубатор» / «Инкубаторы» (`TabScope.equipmentTitle`, removed) and to show the missing-price sentence alone, hiding the addition that is still true without the equipment.
- **Per-batch, «Итог» is `null` while the batch runs.** `BatchFinance.profit` is null for an active batch — money is in, chicks are not out, and any number there reads as a loss that has not happened. The collapsed row then shows the invested sum with the caption «вложено» (a batch about which something *is* known should not display a dash); the breakdown under it has no «Итог» line of its own.
- **The money column of a batch row has a fixed width and a 2 dp end padding.** Both are load-bearing. Fonts arrive from Google Fonts after first measurement, so a column sized to its content is sized by the wrong face and loses its last letter; and a glyph flush against the column edge loses its final pixel column, which is how «нет цен» renders as «нет це».
- Rows show five batches before «Показать все (N)», and at most one is expanded at a time — four figures per batch across ten batches is a wall no one reads.
- **Electricity has its own card, «Электроэнергия», right after «Детализация расходов»** (`ElectricityCard`; it stood before it until 2026-10-02, owner's request): the sum and its kWh, its share of the whole expense, then up to two `Note` lines — how much of it is still growing on running batches and how many batches had no power or tariff to count from. That shared hours are split equally is an «i» beside the card's title (`CardHeader(hint = …)`, the settings screen's `HintIcon`; owner's request, 2026-10-02): a rule read once, not a figure. With nothing counted the card stays and says where to enter the figures, since otherwise nothing on screen says electricity can be counted at all; `NoMoneyCard` lists it as a fourth place too. The expense tile's caption is built from what is actually in the sum — «инкубатор + яйца + свет», any part missing drops out (`expenseHint`, `TabScope.equipmentWord`) — the incubator card adds an «Электроэнергия» row to the addition, and the balance note's «в работе ещё» counts the running batches' electricity with their eggs. A batch's breakdown is two levels: «Доход» and «Расход» stand at the card's edge, and the parts of «Расход» — «Яйца» (`invested`, «N яиц по X ₽»), «Электроэнергия» (kWh, «к этому часу» while running, «общие часы поделены с соседними закладками» when they were) and «Потери» (a slice of the eggs, not a third addend) — are indented 12 dp under it (owner's request, 2026-10-02). «Расход» itself carries no caption: its composition is the lines below it. There is no «Итог» line: the profit already stands in the collapsed row right above the breakdown. The rules behind the numbers are in the root file.
- **The power fields themselves are `PowerFields` in `ui/components/PowerFields.kt`, one composable for both forms** — «Потребление, Вт» and «Тариф, ₽/кВт·ч» side by side, a «Два тарифа — день и ночь» `ToggleRow` that unfolds the night price and two `TimePicker` fields («Ночной с» 23:00 / «до» 07:00 by default), and a caption with the cost of a day («≈ 2,4 кВт·ч и 14,4 ₽ в сутки») so watts typed as kilowatts show at once. `PowerFormState.twoTariffs` lives only in the form: switched off, the night price and hours are dropped on save rather than hidden, or a hidden night price would go on being charged. In the incubator form they stand after the automation switches; in the batch form after «Автоматика инкубатора» and, unlike it, also when editing — they do not touch the schedule. A new batch takes the device's values once the incubator is read (unless something was typed already); editing shows the batch's own fields over the device's (`PowerSettings.over`), so a batch laid before the fields existed shows what it is actually counted by — and a save writes back as blank whatever part the batch did not own and nobody touched — watts on their own, the tariff as a whole, the parts of `over` (`PowerSettings.withoutInherited`, pinned by `PowerSettingsTest`; fed by `AddBatchViewModel.shownPower`) — so editing the name, or the watts alone, does not freeze the device's tariff into the batch.
- **Every finish dialog asks when the incubator was switched off** — «… или вынули птенцов» in both on-time dialogs, «… или убрали яйца» in «Завершить досрочно» (`FinishMomentFields(label = …)`) — `FinishMomentFields` in `ui/batch/FinishMoment.kt`, a date and a time picker defaulting to now, one moment for a whole party; it ends the batch's electricity bill (`Batch.dateEnd` + `Batch.timeEnd`). Before the laying moment or in the future is an error that disables «Завершить». The edit form of any finished batch shows the same fields — right under the locked «Дата закладки» / «Время закладки» row, so «когда заложили» reads before «когда завершили» (owner's request, 2026-10-02), with the stopped wording for a stopped one; there a **blank hour is left blank («—») and not validated** — substituting the laying hour once blocked saving an old batch finished on its hatch day before that hour — with a caption saying the bill then ends at the laying hour. The celebration prints «Электроэнергия» and «Потреблено, кВт·ч» when they are known (`HatchSummariesSaver` carries both through rotation).
- `TabCard`, `CardHeader`, `EmptyNote`, `MetricCard`, `plural` and `formatMoney` moved to **`IncubatorTabParts.kt`**: both tabs are columns of the same white cards, and two copies of the card would part ways at the first change to a corner radius. `formatMoneySigned` is the signed variant, used for figures that can genuinely go either way (balance, a batch's profit) and not for income, expense or losses, which are positive by nature.

## The batch form

`ui/batch/AddBatchSheet.kt` follows mockup [node 12:3555](https://www.figma.com/design/B48q96fOq7Nsy569AXrbWY/Untitled?node-id=12-3555) on its «Закладка» page: name, a 3-across grid of species tiles under its own «Вид птицы» label, a separate «Порода» block — breed rows (one by default, see below), each a dropdown of previously used breeds — two rows of paired fields — count + cull, date + time — price with a за яйцо / за всё switch and two derived tiles, reminder cards, note, «Заложить яйца».

- **«Вид птицы» and «Порода» are two blocks with two labels, not one «Порода / вид птицы» over the grid with the breed field hanging under it.** They answer different questions — the species decides the term and the regimen, the breed only whose eggs are in the tray — and under a shared label the breed field read as a continuation of the grid, so «Курицы» looked like the answer to both. The mockup drew them as one block; the split is a deliberate departure.
- **The breed field is `SuggestingSheetTextField` — the brand/model dropdown of the incubator form, moved to `SheetForm.kt` and used in both — and its list holds the breeds already entered for this bird.** `AddBatchState.knownBreeds` (recomputed by `withKnownBreeds()` on the database answer and on a species change, over every batch of the household, subscribed for the life of the ViewModel like `catalog`) is `knownBreeds(batches, type)` from `:domain` — that species only, most recent batch first, duplicates folded case-insensitively to the newest spelling — and `BatchUiState.breedSuggestions(known, index)` removes from it only what already stands in *another* row (one tray is not laid as two batches of one breed); narrowing by what is typed and re-showing the rest once a pick is complete are the field's own rules, the same ones a brand gets. `BreedCard` takes the same `suggestions` list per card. It was chips under the field first, and they were replaced: a household accumulates dozens of breeds over the years, and a wall of chips under every field — two walls on a split tray — moved the count and the price half a screen down, while a dropdown holds any number and takes no space closed. `BatchOutcomeTest` in `:domain` pins the ordering and folding, `BreedSuggestionsTest` in `app/src/test` the exclusion of other rows.
- **A batch has one breed, and the form's breed list is a list of batches to create.** With one row it is the mockup's single «Порода» text field, and it goes into `Batch.breed` as is. The dashed «Ещё одна порода — отдельной закладкой» adds a second row, and from there (`splitByBreeds`) each row becomes a `BreedCard` — the same white bordered card the reminders use — holding the breed name, its narrow «Яиц» field, its «Стоимость, ₽» with the «за яйцо / за всё» switch, and a cross; **pressing the save button then lays one batch per row** (`BatchUiState.toBatches()`, each through its own `insertBatchWithSchedule` with its own copy of the day rows and reminder rows), and the button says so — «Заложить 2 закладки». The card holds exactly what the batches of one tray differ by; everything else — title, species, date, time, note, automation, the regimen table, the reminders — is typed once and copied into each. Their titles get the breed as a tail, «Весенняя партия — Хайсекс» (`splitBatchTitle`), because two cards in the incubator list would otherwise differ by one small caption and a reminder notification would not tell them apart at all; `splitNotice()` under the cards prints the count and those titles before the press, since the tail is the one thing the form itself does not show. Why split rather than one batch with rows inside: a breed's hatch, cull and money are then the batch's own — `Batch.eggAllEND`, `Batch_candling`, `Batch.price` — and nothing in the app keeps a second ledger inside a batch; the three schema versions that did (15–17, `Batch_breed`) are gone, see the root `CLAUDE.md`.
  - **The cross stands in a line of its own above the fields, not beside them.** In the field row it took the width of a button plus its gap out of «Порода» — the one field of the card whose content the user writes and whose length is therefore unbounded — so «Ломан Браун белый» ran into it while the numbers beside it kept their fixed width. Its line's left half carries the card's number («Закладка 2»), because a cross alone on an empty line does not say what it removes; the field below keeps its own «Порода» label, which is what the required star hangs on.
  - **That cross is `SheetRemoveButton` in `SheetForm.kt`, and the reminder card below uses the same one.** Both are «убрать эту карточку» in one form, one under the other, so two sizes of one control would read as two different actions. **Both are `SheetCircleButton` — a 36 dp circle drawn inside a 40 dp button** (`SheetCircleSize` / `SheetCircleTouchSize`) rather than being the button, as the reminder's 32 dp one was — and `SheetHeader`'s cross is the same composable, so the two round crosses of one sheet are one size by construction. **Drawing the circle inside is not a style choice, it is the only way to get 36.** `IconButton` puts `minimumInteractiveComponentSize()` on itself, which reports 48 dp whatever constraints arrive from outside, and a `.clip().background()` hung on the button's own modifier sits *outside* that node and paints those 48: the header cross used to be written as `IconButton(Modifier.size(36.dp).clip(CircleShape).background(…))` and rendered as a 48 dp circle spilling 6 dp past its slot on every side — visibly larger than the remove cross in the breed card, though both said 36 in the source. A nested `Box` is measured at its own size; the button around it keeps the target whole while the picture is sized freely, and centring it there is also what lifts it off the corner: 10 dp of card padding plus 2 dp of slack on each side, where the old one sat against the border.
  - **The two batch fields that a split tray makes derived are «Количество яиц» and «Стоимость, ₽».** Each shows the sum through `DerivedCountField` — cream ground, «всего по породам» beside the figure — and stops being typeable, because a second place to enter the same number is a number that will disagree; the caption says «всего» because the figure is the sum over the batches about to be created, not any one batch's. The money sum is in roubles and the summary tiles below it therefore read it as «за всё»: two breeds priced differently add up to a total and to nothing else. Each batch still stores its own row's price literally, per egg or per tray.
  - **What was already typed is not lost at either switch**: `addBreed()` moves the count and the price into the first row (until that moment they described the whole tray, and the tray was that one breed), and `removeBreed()` down to one row hands the survivor's numbers back to the batch fields.
  - Validation grows one clause: with a split tray every row needs a name and at least one egg (`AddBatchViewModel.isValid`) — a nameless row is a batch the statistics can say nothing about, an eggless row a batch with nothing in it. A single row with a blank name is «no breed» and writes an empty `breed`.
  - **Editing never shows the dashed button, and `addBreed()` refuses while `isEditing`.** The breed can be renamed — it is one text field — but not added: the batch already has its eggs, its regimen and its measurements, and splitting those in two after the fact is not possible. Another breed is another batch, laid through the incubator's own «Заложить яйца». This is the third creation-only rule of the form, beside the species and the automation switches.
  - **AppMetrica's `BATCH_CREATED` fires once per batch laid**, with that batch's «Имя», «Порода», «Кол-во» and «Стоимость», plus «Закладок» — how many one press produced — so «do people split trays at all» can still be asked.
- **Under «Количество яиц» the form shows how full the incubator will be with this batch — the same `CapacityBlock` the incubator card draws, not a copy of it.** «5 / 2 места», the percentage and the bar, red past 100 %, exactly as on the start screen — **and nothing at all when the capacity is unset**: a bar without a ceiling answers no question, and capacity is optional — neither the card nor the form asks for it; the number is the eggs already in the device plus what the field holds (`AddBatchState.occupiedEggs`, summed from `neighbours` — the running batches the form already watches for the schedule tint — and `capacity`, read with the incubator’s automation flags in `load`). Both are state fields, not getters: the fields page recomposes on every character. A caption under the bar splits the sum — «2 яйца уже в инкубаторе, с этой закладкой — 5» (`fillCaption`, pinned by `IncubatorFillTest`) — because «5 / 2» over a field holding «3» would read as an error otherwise; an empty incubator gets no caption, and a split tray says «с новыми закладками». **Creation only**, like the switches and the species: while editing the batch is itself among the running ones and would count twice. Overfilling is still not blocked — the tray takes what it takes — the point is that it is seen while the number can still be changed, rather than on the card after the save.
- **The mockup's single «количество + дата» row is now two rows of two, and one of the four fields is edit-only.** «Дата закладки» and «Время закладки» face each other because they are one moment split across two inputs; «Отбраковано яиц» faces «Количество яиц» because it is subtracted from it. **The date row sits directly above «Напоминания», below «Стоимость»** — the two blocks are the same «ЧЧ:ММ» from the same dialog, and the hour the eggs went in is the moment the reminders are read against; the count row stays up with the breeds, whose eggs it sums. The cull field appears only in edit mode — a batch that has not been laid yet has nothing to cull — and while creating the count simply takes the whole row: nothing holds the empty half open, because a blank half-row reads as a field that failed to load rather than as one that does not apply. **The time picker is the reminders' `TimePicker` dialog**, not a text field: a hand-typed «ЧЧ:ММ» can come out in a shape nothing parses. That dialog now tolerates a blank argument (`FALLBACK_HOUR`), because batches created before schema v10 carry no time at all and would otherwise crash it on `toInt()`. `ic_clock_design.xml` was drawn to match `ic_calendar_design` — same 14 dp, same 1.05 stroke, same `#8A8072` — since the mockup has no such field and therefore no icon for it.
- **The time is where each incubation day begins.** A running batch counts its days from the laying moment (`batchStartMoment` + `incubationDay`, root `CLAUDE.md`), the same clock `batchFinishMoment()` uses for the term, so «День 21/21» is exactly the last 24 hours before the hatch. That is also which row a reading lands in: at 08:00 on a batch laid at 10:00, «Замеры за сегодня» is still yesterday's row, and the schedule's current-day caption says so — «20 сент. с 10:00 · сегодня» (`BatchDetailUiState.startTime`).
- **«Отбраковано яиц» does not replace candling, it complements it** — see `Batch.eggRejected` in `:domain` and `BatchDetailViewModel.rejectedTotal`, which sums the two. Candling records a cull as an event with a day; the column records the eggs lost between candlings. Both are subtracted from «Заложено». **In the edit form «Отбраковано яиц» shows the total of both and is not an input** (owner's request, 2026-10-01): a `SheetPickerField` holding `BatchUiState.rejectedTotal` (`eggRejected`, the manual part, plus `candlingRejected`), with no caption under it — the breakdown lives in the dialog. Tapping it opens `RejectedDialog`: «Отбраковано вручную», (locked as the remainder «заложено − вывелось − овоскопирования» on a hatched batch with chicks entered — the chicks are primary, `fixedHatch`), then «На овоскопировании» — one row per candling day of the species the batch has already lived (`candlingEditRows` in `CandlingEdit.kt` — the whole term for a hatched batch, up to the stop date for a stopped one, up to today for a running one, by the same `incubationDay` as the sheet), plus any day that already holds a record, so a stray row stays fixable — and «Итого» with what is left of the eggs laid at the bottom. Blank means «not done» and deletes the record, `0` means «done, nothing culled» — the dialog does not spell this out, at the owner's request. The dialog edits a `RejectedDraft` held in `AddBatchState.rejectedDraft` (survives rotation; «Отмена» and back drop it, «Готово» copies it into the form), and **the total cannot exceed the eggs laid**: every field is clamped to the eggs left after all the others (`AddBatchViewModel.updateRejectedDraft`), and since «Количество яиц» can be lowered afterwards, `isValid` also requires `rejectedFits`, with a red caption under the field. Saving writes only changed candling rows (`candlingWrites`) together with the batch in one transaction, `ItemsRepository.updateBatchWithCandlings`, because the total the person confirmed is the two together. Storage and every other reader are unchanged. `CandlingEditTest` and `HatchLimitTest` pin the rows, the writes and the sums.

- **One form does both create and edit** — `batchId == 0` creates, anything else edits — because the file has no separate mockup for editing and the fields are identical. `StartScreen`-style hosting applies: `IncubatorScreen` opens it both to create and — from the card's «⋮» menu — to edit. The old `BatchEditScreen` / `BatchEditViewModel` and the `BatchEdit` route are gone; `BatchUiState` and its mappers moved to `BatchUiState.kt`.
- **Editing rewrites the reminders wholesale** rather than diffing them, and a finished batch does reach this form — «Редактировать» in the card's «⋮» menu is offered whatever the status, so a mistyped name or hatch count can still be corrected after the fact. What protects it is one level down, and it is no longer a rule anyone has to remember: the form writes the `Batch_time` rows and asks for a recompute (`refreshReminders`), and the schedule is derived from the database, where a finished batch simply does not appear. The check used to live here as `arhive != "0"` inside `rewriteReminders` — and before that it did not live anywhere, which is how saving the form of a finished batch used to bring its notifications back. The **tap** on such a card is a different door and always was: it opens `BatchDetailSheet` on просмотр, never this form.
- **The form has two pages, «Закладка» and «Расписание», swiped between in a `HorizontalPager`** — the same `SlidingTabSwitcher` from `design/components/SlidingTabs.kt` that the incubator screen and the batch sheet use. The second page is the day table: one row per incubation day, columns «Температура», «Влажность», «Переворот» and «Проветривание», every cell editable. The mockup draws neither page tabs nor a table; before this, the regimen a batch was about to run with could not be seen at all until the batch existed, and it depends on the species picked on the *other* page — a swipe is cheaper than saving, opening the batch and coming back.
- **A warning stands above the table, not under it and not in a dialog.** The `:domain` regimen is an averaged reference and every incubator reads differently; that has to be known before the numbers are believed, not after. `ScheduleDisclaimer` also says the regimen stays editable after the batch is laid, so nobody feels the table has to be perfect now.
- **The whole page is one `LazyColumn`, and the table's header row is its `stickyHeader`.** The disclaimer (or the source card), the action buttons and the legend are its first item and scroll away with the rows: they used to stand fixed above a scrolling table, and on a phone with the archive card, three buttons and the legend showing they took nearly the whole sheet, leaving two rows of the table visible. The header scrolls up with them and then pins to the top edge — up to thirty-one rows go past, and column labels that scrolled away would leave four columns of numbers meaning nothing. It is painted with the sheet's `background`, or the rows would show through under it. The rows carry no `key`: the list never reorders, all input lives in the ViewModel, and a key on `day` would crash the list on a batch that somehow holds a day twice.
- **The header names its columns with icons, and tapping one shows the name.** Written out, «Проветривание» does not fit its share of the width even across two lines, and a clipped «Проветр…» names nothing; an icon fits always. It buys no height — a `CellHeight` tap target is slightly taller than two lines of label, and that is the deliberate price of icons you have to hit with a finger. The name is not lost — it is the tooltip and the `contentDescription`, so TalkBack reads it either way. `ic_turn_design.xml` and `ic_airing_design.xml` were drawn for this in the same stroke-only 16 dp style as `ic_temperature_design` / `ic_humidity_design`; the airing one keeps curls on its three strokes because three bare horizontal lines read as a menu button. The tooltip is `TooltipBox` with `enableUserInput = false` — its own gestures are hover and long-press, and nobody guesses a long press, so the plain tap handler calls `show()` itself. The whole cell is the tap target, not the 16 dp of icon: in a quarter-width column, missing the picture would look like a broken control.
- **The column's share of the width sits on the header cell's own `Box`, never on its `TooltipBox`, and that is not a style choice.** `BasicTooltipBox` draws `Box { … WrappedAnchor(modifier = modifier …) }` — the outer `Box` takes no modifier, so a `Modifier.weight()` handed to `TooltipBox` lands on a nested node, where `RowScope.weight` means nothing and is dropped without a word. The header then loses every column width, the first cell's `fillMaxWidth()` swallows the row, and all that is left of the header is the temperature icon. The tooltip therefore wraps only the icon — which is also where it should point.
- **Columns are weights, not fixed widths with a horizontal scroll.** The table has to fit any phone whole — otherwise editing «Проветривание» would cost a separate gesture on each of thirty rows. **Since v9 every column is numeric**, and the widths went the other way than they used to: the counters are the narrow ones now and temperature/humidity the wide ones. Temperature and humidity go through `filterMeasureInput()`, turning through `filterCountInput()`; an empty counter cell means «no quota» (a day on the incubator's automation), a zero means «do not do it».
- **Airing is one cell for two numbers, written «2×15», and the cell is a mask.** The plan stores the times and the minutes of one airing separately, but two columns for them left every cell about a digit wide, and the pair reads as one value anyway — that is how the day pills and the counters print it. `filterAiringInput()` in `ValueFormat.kt` keeps only digits: the first is the times, the next two are the minutes, and the «×» appears by itself with the second digit — **never earlier**, or «2» would immediately become «2×» and `Backspace` could not remove a separator the filter puts straight back. `parseAiringCell()` / `airingCellText()` are the two halves of the round trip, and `ValueFormatTest` walks a whole typing-and-deleting sequence through them. «Не проветривать» collapses to a single «0» — half the days of some regimens look like that, and a column of «0×0» is harder to read than a column of «0» — but only when the minutes are zero too, since a «0» that swallowed the next digit would make the minutes untypeable.
- **When the incubator already holds running batches, the temperature and humidity cells are tinted by how far they stand from those batches' plan on the same calendar day — green «совпадает», amber «допустимо», red «расходится» — and only on the days the neighbours are still in the device.** One incubator is one air: two clutches in it share a thermometer, so laying turkeys beside chickens on their eleventh day gives the first ten turkey days not two regimens but one compromise, and the table is where that has to be seen, while it is still being edited. The arithmetic is `overlapVerdicts()` in `ui/batch/ScheduleOverlap.kt`, Compose-free and pinned by `ScheduleOverlapTest`: a neighbour's day on the date of the new batch's day N is `N + daysBetween(neighbour start, new start)` — one subtraction per neighbour, the same whole-day arithmetic as `incubationDay`, and deliberately not a `plusDays` per row, which would go through `Calendar` thirty times per keystroke and would count calendar days where `daysBetween` truncates milliseconds, so the two halves would part by a day across a daylight-saving switch — its `Value` row for that day is its plan, and a day past its schedule means it is not in the device — no verdict, white cell, exactly as before. `Severity`, `severityOf` and `deltaOf` moved out of `BatchDetailSheet.kt` into `ValueFormat.kt` for this: the JVM test must not load a three-thousand-line Compose file's static initialiser to compare two doubles. The target is the mean over the neighbours that set the field, the rule `averagePlan` uses in the incubator measurement sheet, and the thresholds are the batch sheet's own (±0.2 / ±0.5 °C, ±3 / ±7 %) so «в норме» there and «совпадает» here are one question; the delta is rounded to two decimals first, because 38.0 − 37.8 is a hair over 0.2 in binary and the boundary case is the common one in a one-decimal table. **Turning and airing are deliberately not compared** — the air is shared, the hands are per tray. `AddBatchState.neighbours` is a flow subscription (`watchNeighbours`, `getBatchesFor` → Active → `combine` of `getBatchValues`), live so that a neighbour finished from another screen takes its colours with it; `overlap` and `overlapShown` are **fields of the state, not `get()`s**, recomputed by `withOverlap()` in exactly the branches that change its inputs — a typed cell (this is the «динамически»: the cell changes colour under the finger), the date, a species change, «Взять из архива», «Из файла», «По умолчанию» and the neighbours' answer — and never on a typed name. **Creation only**: while editing, the batch is itself among the running ones, and comparing it to itself would paint a green table about nothing. The colour goes into `SheetTextField`'s new `containerColor` — fill only, frame and text unchanged, so the cell still reads as an input — through `Severity?.overlapColor()` in `ScheduleTable.kt`, **and the same verdict goes into the cell's `stateDescription`** («расходится с 2 закладками», `overlapDescription`), because three pastel fills are nothing to TalkBack and little to a colour-blind eye; `CellVerdicts.neighbours` exists for that sentence and three new palette tokens (`ScheduleMatch` / `ScheduleTolerable` / `ScheduleConflict`, the green of `IncomeSurface`, an amber derived from `ChartTurn`, the red of `ExpenseSurface`). `OverlapLegend` — three swatches and one line saying what is compared and that a white cell means there is nothing to compare with (no neighbour that day, or a value nobody set) — stands between the action buttons and the header row, **only while some cell is actually tinted** (`overlapShown`, not «some day has a verdict»: a day whose neighbours set neither temperature nor humidity has a verdict and no fill), because without neighbours the table is white and a legend over it would explain a colour that is not there; a green cell would otherwise read as «the right value», where it means only «the same as the neighbours», who may themselves be wrong.
- **The save button moved out of the form's scroll into a fixed footer under the pager.** With two pages, a button reachable only by scrolling the first one to the end would be a lie — the same press saves the table too.
- **That footer is hidden while the keyboard is up** — `if (!WindowInsets.isImeVisible)` around `SaveFooter`, the one place in the app that reads IME state. The sheet's window shrinks to the strip above the keyboard, and everything outside the pager keeps its height: header, tab switcher and footer together left one or two fields visible on a 1080×2400 screen. The pager is the only child with `weight(1f)`, so whatever else stands in that column is taken straight out of the form — and the save button is the one thing nobody needs mid-word. This is *not* the same as `imePadding()`: the footer is not being lifted, it is being removed, and it comes back when the keyboard closes. Note the check is «is the IME visible», not «how tall is it»: on a device with a hardware keyboard the IME can report `visible=true` at zero height, and the footer will hide there too — harmless, and the alternative (measuring the inset) reads zero under an already-resized window, which would break the real case.
- **Neither deleting nor finishing lives in the batch form.** The mockup draws no such buttons, and both are gone: «Завершить закладку» only flipped `arhive`, silently losing the result the batch sheet asks for, and «Удалить закладку» duplicated the card menu on the incubator screen. Deleting still exists there, and still asks first — `ON DELETE CASCADE` takes the day rows, reminders and species chips with it. Editing a batch is now only editing.
- **Creating a batch is one step.** The button saves immediately: `AddBatchViewModel.save()` hands the batch, the species chip, the `Value` rows **as the table holds them** and the reminder times to `ItemsRepository.insertBatchWithSchedule` — **one transaction, not thirty-odd separate inserts** — and the nav graph opens the new batch. Separately they were twenty to thirty commits with nothing promising that the last would happen: a batch interrupted midway is already in the list with half a schedule behind it, and every reader of that schedule treats row N as day N. `idPT` is stamped inside the transaction, which is why `setIdPT` in `:domain` is gone; editing writes its days through `updateSchedule` for the same reason, minus the risk. `AddBatchScheduleScreen.kt` — the old, unreachable two-step version of this very table — was deleted along with `AddBatchScheduleForm`, `MyRowIncubatorAdd`, `AlertDialogExample` and `ArhivIncubatorChoice`; nothing had navigated there since the form became one step.
- **A new batch ends in «Добавить даты в календарь?»** — `AddToCalendarDialog` (`ui/batch/`), hosted by `IncubatorScreen` over the batch sheet that just opened, like the celebration: `calendarOffer` in `rememberSaveable` with `CalendarOfferSaver`; its logic is `CalendarOfferViewModel` (MVI, one instance per offer), and it counts as an overlay for the «Инкубация завершена» prompt. The dates travel in `AddBatchEffect.Saved.calendar`, computed by `AddBatchViewModel.calendarOfferOf` from what the form already holds — **creation only**, since a question on every save of the edit form would be noise, and `null` when the date does not parse, the term is unknown or every date is past. A split tray gets one offer under the base title: the date, species and regimen are shared. The rows are checkboxes, all ticked; the permission is asked on «Добавить», not on open; several writable calendars add a radio step, one writes at once. **Refusal, no calendar or a failed write fall back to «по одной»** — each date opens the calendar app on a filled `ACTION_INSERT` event — because a pressed button must do something. The arithmetic and the Android half are in `calendar/`; see the root `CLAUDE.md` («Calendar»).
- **Editing now writes the day rows too, and it updates them — it never recreates them.** Measurements hang off `Value.id`, so a recreated row would tear the fact off the plan. That is also why the table is loaded through `getBatchValues(batchId)` (which has `ORDER BY day`) **with the ids intact**, and why `applyArchiveSchedule` refuses to run in edit mode: archive rows arrive with `id = 0`, and an update against that would silently write nothing.
- **The table is regenerated whole when the species changes, and only while creating.** A goose and a quail do not have the same number of days, so keeping the old rows would be litter in a new regimen rather than care. `resetSchedule()` — the «По умолчанию» button — is create-only for the same reason.
- **The species grid shows the five built-in tiles, a dashed «Свой вид» tile, then the user's own species — not the mockup's six.** «Цесарки» would need a full regimen in `IncubationSchedule` plus entries in `IncubationPeriod` and `Candling`, and none of that is written; instead of one missing bird the form lets the user describe any bird through `CustomSpeciesSheet` (below). The tile order is `SpeciesCatalog.allNames` — built-ins in mockup order, custom ones after — and the day counts under each tile come from `catalog.incubationDays()`, so a bird appears there the moment the catalog knows it, code or database. A custom species is drawn with the same tile and the generic 🥚 from `speciesEmoji()` in `StartScreen.kt`: there is nowhere to get a picture for an invented name, and for a batch it is a bird like any other. **The «Свой вид» tile is dashed**, like «Добавить напоминание» further down, because it is a door, not a choice, and must not read as one more bird. **A species the grid is asked to select but the catalog does not know still gets a tile**, without a day count — otherwise the grid would show nothing selected above a form that has a species, and the first tap would silently replace it (a custom species deleted from «Настройки» while the form stands on it is the remaining way to get there). **The tile grows under its name, and the name ends in an ellipsis on the third line.** A built-in bird is one short word; a custom one is called whatever it is called, and against the old fixed `TileHeight` a longer name pushed the incubation term out of the tile and was then clipped by the corner radius without a mark — «[Дракон] (365». `heightIn(min = TileHeight)` plus `maxLines = 2` on the name fixes both, and the row became a `TileRow` so the other two tiles keep up with the tall one. The term is the only thing besides the name that a tile says, and it must not be the part that gives way. **A species saved from this form is selected at once**: `AddBatchViewModel.selectNewSpecies` puts it into the catalog by hand before the database flow answers, because `update()` regenerates the table immediately and the flow is a frame or two behind — the table would have drawn the fallback regimen of an «unknown» bird first.
  - **Folded, the grid is exactly two rows, and «Показать все виды» opens the rest.** There are five built-in birds and there can be any number of one's own: at a dozen the grid is taller than the screen, and a form opened to lay eggs starts with a list of birds to scroll past. Two rows are the five built-ins plus one cell, and everything else — every own species and, usually, the «Свой вид» tile — waits behind the button. **It is a real button** (`ScheduleActionButton`, the white outlined one from above the schedule table, full width), not the accent text line the hatch history unrolls with: it stands under a grid of tiles, and a line of text there would read as a caption to the bottom tile. **No count in the label**: behind it are species *and* the «Свой вид» door, and a counter that numbered the door among the birds would be off by one. **The tail rides in its own `AnimatedVisibility`** — `expandVertically` + `fadeIn` against `shrinkVertically` + `fadeOut`, over the same 180 ms (`SpeciesGridExpandMillis`) as the start screen's filter row and archive switcher, since it is the same movement: a block above a list arriving and leaving. Two or three rows appearing at once move everything under them — the breed field, the count, the price — half a screen down, and unanimated that reads as the form having jumped rather than as birds having opened. **It replaced an `animateContentSize` on the whole grid, and the difference showed on the way back**: with the size animated but the content not, folding made the rows vanish at once and then slid the empty space they had left, which looks like no animation at all. The rows are therefore split into a fixed head and an animated tail (`SpeciesRows` draws both), and the 8 dp gap above the tail lives inside the animated block — outside it, it would hold a slot open under the second row while folded.
  - **The sixth cell is the «Свой вид» door, or the selected own species when there is one.** A grid showing nothing selected above a batch that has a species lies more dangerously than a hidden door: the door is one tap away, while a species can be replaced by accident and in silence — the same failure the «species the catalog no longer knows» rule above exists to prevent. That swap happens only while a custom species is selected — after «Свой вид» has just been saved, or when one is picked from the tail; the rest of the time the door is in place.
  - **While editing, the grid is not drawn at all: the species stands in a locked field** (`LockedSpeciesField` — the cream `DerivedCountField` with the emoji, the name and the term, under a `FieldLabelWithHint` that says why). The species is chosen once, when the eggs go in, for the same reason the automation switches are creation-only and stronger: the schedule was generated for that bird and its day rows hold the measurements, while another bird has another term — a «Курицы» batch switched to «Утки» read «День 7/28» over 21 rows of the chicken regimen, with no row at all for days 22–28, and the `Batch_species` chip still said «Курицы». Regenerating the table is ruled out by the rule `save()` already states (day ids carry measurements), so the only honest fix for a wrong species is a new batch, and the hint says so. **`AddBatchViewModel.updateForm` refuses the change itself** (`requested.copy(type = previous.form.type)` on `isEditing`), and `selectNewSpecies` returns early — the form hides the tiles, but a composition can outlive the state it was built from, the same reason `setAutoTurn` refuses on its own. A grid with one selected tile and four disabled ones was rejected: five birds under the finger invite the tap that then does nothing.
- **«Автоматика инкубатора» — two switches on the create form, and they are not in the mockup.** `load()` used to copy `autoAiring` / `autoTurn` off the parent `Incubator` and that was the end of it, so a tray turned by hand this time had no way of saying so: removing «на автомате» from one batch meant switching the automation off on the device itself, which is a lie about the device. The device's answer stays the **default** — an incubator with auto-turn lays a batch with auto-turn — but it can now be overruled for one clutch. The block stands **last on the page, right above «Заметка»**: everything above it is what the form was opened for — what was laid, at what price, when, what to be reminded of — while this is a correction to the device's own settings, wanted on the rare occasion rather than every time. Its explanation lives behind the «i» beside the label (`FieldLabelWithHint` in `SheetForm.kt`), because a three-line caption is read once and takes up room always. Three rules hold the block together.
  - **The switch works in both directions, and `scheduleBase` in `AddBatchViewModel` is what pays for it** — the regimen as it arrived from `:domain` or from the archive, before the automation went over it. Switching automation on erases the quota to `null` (`setAutoIncubator`), and there is nowhere else to take the erased numbers back from. The snapshot is taken **before** that call — `setAutoIncubator` edits `Value` in place, the model's fields are `var` — and only those two columns are restored, so hand-typed temperature and humidity survive the press. «Взять из архива» follows the same rule: the taken regimen becomes the new base and is brought to the flags at once, otherwise an «Автопереворот» switched on would stand over a column of somebody else's turns.
  - **Creation only.** The quotas are written once, together with the schedule, and the days of a laid batch already carry measurements; erasing or restoring a quota after the fact rewrites not the plan but what the person has been working to. `setAutoTurn` / `setAutoAiring` refuse on `isEditing` themselves rather than trusting the form to have hidden them.
  - **A press outranks the database** (`autoTouched`): the incubator is read asynchronously, and without the flag its answer would switch back on what was just switched off — the toggle would spring back by itself.
  - **A column given to the automation is locked, not merely empty, and it reads «Авто»** (`AutoCellText`, `ScheduleRow(autoTurn, autoAiring)`, `SheetTextField(enabled = false)`). An empty cell that still accepts typing invites the one entry that contradicts the flag beside it: `Batch.over` / `Batch.airing` mean «there is no quota, the incubator holds it», and a number typed under that flag would be a plan nobody is ever shown — the sheet prints «на автомате» over it regardless. The locked cell is cream, like the derived fields of the form, rather than the Material grey of a disabled input: the value in it is not unavailable, it is simply not the user's to set. **The same lock covers the sheet's `DayEditor`** — the other place the day plan is edited — for the reason its own comment already gave about the airing mask: one regimen edited in two places must not be edited by two different rules.
  The old «другие виды в закладке» chips are still gone — `Batch_species` exists and still gets the leading species.
- **`ArchiveScheduleDialog` is off-mockup and deliberate, and it now opens from a button over the table rather than by itself on save.** It seeds the day-by-day regimen from a finished batch of the same species (`getValueArchive`, sorted by day here since that query has no `ORDER BY`). It used to ambush the save press, which was the only moment it could: the regimen was invisible until then. With the table on screen that would overwrite edits made seconds earlier behind the user's back, so the choice sits next to what it replaces and the replacement is visible immediately. Both it and «По умолчанию» appear only while creating, and the archive one only when the archive holds something.
- **The dialog asks two questions, and the second one is the point: which batch, then *what out of it* — its plan or the average of its measurements** (`ArchiveScheduleSource.Plan` / `.Fact`, both in `AddBatchViewModel.kt`). The plan is the numbers the batch was generated with and may never have been corrected; the readings are what the regimen turned out to be on this particular incubator, and that is usually why an old batch is opened at all. `averagedScheduleOf()` in `BatchAnalytics.kt` does the arithmetic — see the analytics section — and `applyArchiveSchedule(sourceId, source)` zeroes the ids only *after* it, since a measurement finds its day through `Value.id` alone.
- **«Среднее по замерам» is disabled on a batch that has none, rather than quietly equal to the plan** — otherwise the two options would produce the same table and nothing would say why. `ArchiveOption` therefore carries `hasMeasurements` next to each batch, filled by `ItemsRepository.countMeasurements(batchId)`: a `COUNT(*)` per finished batch of the species, not a list of rows loaded to be measured for emptiness. Picking a batch without readings also snaps the selector back to the plan, so the confirm button never stands on an unavailable choice. Each row's caption is «дата · вывелось из заложенных · есть/без замеров», because batch names of one species repeat («Курицы», «Курицы 2») and those three facts are what the choice is actually made on. **The hatch rate stands to the right of the row, not at the end of that caption** (`archiveBatchHatchRate`, accent `DesignType.MonoEmphasis`): percentages line up in a column and are compared at a glance, while at the end of captions of differing length they would have to be hunted for. It is the same integer arithmetic as «средний вывод» on the incubator screen, and a batch stopped early honestly shows 0 % — that is a reason not to take its regimen, not a missing figure. **The dialog's opening line no longer says «Введённые данные останутся как есть»**: it answered a question nobody asks now that the table is on screen and the replacement is visible the moment it happens.
- **Once a regimen is taken from the archive, `ScheduleDisclaimer` above the table gives way to `ArchiveSourceCard`** — the summary of the batch it came from. The two say different things about the same numbers, and only one of them is true at a time: the disclaimer («цифры справочные, сверяйтесь с инструкцией») is about the `:domain` reference regimen, while a regimen lifted from a finished batch has already been through somebody's incubator, and the question about it is *whose*. The card names the source («Режим из архивной закладки» / «Среднее по замерам архивной закладки»), the batch and its breed, then сроки, «60 заложено · 3 брак · 45 вывелось (75%)», the measurement count as a **number** (three readings across three weeks average into anything, so «есть замеры» would be the wrong answer) and — only when non-blank — `endReason`, the one line that says this regimen may not be worth copying. `AddBatchViewModel.appliedArchive` (an `AppliedArchive`: the whole `ArchiveOption` plus the chosen source) holds it, and **`regenerateSchedule()` clears it**, so «По умолчанию» and a species change bring the disclaimer back together with the reference regimen. `ArchiveOption` keeps `measurementCount` and derives `hasMeasurements` from it; `countMeasurements` returned the number all along. **The two swap through an `AnimatedContent`, not an `if`**: the blocks are of different heights, and an instant swap yanks the whole table under them — on screen that is indistinguishable from the day list itself having scrolled. The `SizeTransform` runs longer (280 ms) than either fade, and the outgoing block fades faster (120 ms) than the incoming one arrives (220 ms), so two half-transparent texts never sit on top of each other mid-transition.
- **The batch list inside that dialog scrolls in its own box, capped at `ArchiveListMaxHeight` (200 dp).** It used to grow with the archive inside the dialog's single scroll, and by the tenth finished batch of a species the «Что из неё взять» selector stood below the fold: the source choice — the point of the dialog — was invisible, so every use silently took the plan. The cap is deliberately not a whole number of rows (a row is a 48 dp `RadioButton` plus padding, ≈56 dp), so half a row shows at the bottom and says the list continues. The outer scroll stays for small screens.
- **«Из файла» is the third button over the table, beside «Взять из архива» and «По умолчанию», and the three go two to a row.** It is the same question as the archive button — where does the regimen come from — with the source outside this household, so it stands where that choice is made and where its result is visible, not on the «Закладка» page; and only while creating, like its two neighbours. Three buttons in one row on a 360 dp phone squeeze «Взять из архива» into a mid-word break, so `SchedulePage` builds the list of available actions and chunks it by two. The pick is `ACTION_OPEN_DOCUMENT` with `*/*` — an `.incs` file has no MIME type any provider knows. **Nothing is written into the table by the pick itself**: `AddBatchViewModel.importFile` reads and decodes the file and raises `importPreview`, and `ImportScheduleDialog` stands between the file and the table. It shows what `FileSourceCard` will show afterwards (species, term, measurement count, the source batch’s breed and its incubator’s brand and model when the file has them, «Файл от …»), then the same «Режим той закладки / Среднее по её замерам» pair of `ArchiveChoiceRow`s as the archive dialog — the second disabled when the file carries no `fact`, for the same reason (two rows, one table) — and up to two `ImportNotice`s: an **emphasised** one when the file's species differs from the form's («после импорта закладка станет по виду «Утки» … если яйца не этой птицы, файл не подходит») — accent border and full-strength text, because it is the only place where «Заменить» can be a mistake — and a plain one when the species will be created in «Свои виды». Its last line says what the import does *not* touch, since someone who knows «Взять из архива» may expect the same from a file and someone who does not may expect more. A file that is not a schedule file, is damaged, or comes from a newer version ends in `ImportErrorDialog` with the codec's own sentence.
- The dashed «Добавить напоминание» button is a local copy, not `IncubatorScreen`'s `DashedButton`: this mockup draws it at 41 dp with a 16 dp radius and 13 sp text, the other at 58 / 22 / 16.

## The custom species constructor

`ui/species/CustomSpeciesSheet.kt` is where a user describes a bird the app does not
know — «Цесарки», a local cross, anything. It is a `ModalBottomSheet` like the batch
form and built from the same pieces, with no mockup of its own: name, an optional
«Взять за основу» row of the five built-in species, then the day table.

- **The table is no longer the batch form's private property.** `ScheduleHeaderRow`,
  `ScheduleRow`, `ScheduleCell`, `ScheduleActionButton`, `DashedAddButton` and the
  geometry around them (`SchedulePadding`, `CellHeight`, the column weights) moved to
  `ui/components/ScheduleTable.kt` as `internal`; `AddBatchSheet` imports them and its
  page looks exactly as before. A second copy of those cells would drift from the first
  at the first change of a column width, and a species described here has to mean the
  same numbers as the batch that runs by it. `SaveFooter` moved too, as
  `SheetSaveFooter` in `SheetForm.kt`, for the same reason and with the same IME rule.
- **A sixth column is the only thing that differs** — `ScheduleHeaderRow(candling = true)`
  and `ScheduleRow(candling = …, onCandlingToggle = …)`, a `CellHeight` box filled with
  the accent when the day is marked. `candling` is nullable and not `false`-by-default
  because «no such column» (the batch form) and «this day is not a candling day» are
  different answers. `CandlingWeight` is 0.7 — the narrowest column, since it holds a
  mark rather than a value, and on 360 dp the six columns still leave temperature enough
  room for «37.55».
- **«Добавить день» copies the previous row's four values.** A hen sits at the same
  37.8 / 55 for three weeks, and retyping twenty-one identical rows is precisely what
  would make the constructor unusable. The candling mark is not copied: it belongs to
  one day, and carried down it would mean «every day», which never happens.
- **At least one row always remains.** «Убрать последний» is disabled rather than hidden
  at one day, and a species read back from the database with no days still gets an empty
  first row — the header over an empty table offers no way back into it.
- **There is no «срок инкубации» field, and there must not be**: the term is the number
  of rows, and a second place to state it would start disagreeing with the table
  immediately. The hint card above the table says so, and `summary` («21 день ·
  3 овоскопирования») repeats it as a figure.
- **Uniqueness is asked of `SpeciesCatalog`, not of the custom list** — `isNameTaken`
  covers the built-in names too, since a batch refers to its species by name and two
  tiles reading «Курицы» could not be told apart. The error appears while typing, not on
  save: learning that a name is taken after filling in thirty rows means filling them in
  again. «Введите название» waits until the field has been touched and emptied — over an
  untouched form it would be a reproach for something nobody has failed to do yet.
- **Days are renumbered 1..N by position on save**, and their ids go out as zero:
  `saveCustomSpecies` rewrites the whole species in one transaction, so there is nothing
  to match old rows against. Editing a species does **not** rewrite the schedules of
  batches already created from it — those `Value` rows were baked at creation, exactly as
  with a built-in bird.

## The batch sheet

`ui/batch/BatchDetailSheet.kt` follows mockup [node 14:4893](https://www.figma.com/design/B48q96fOq7Nsy569AXrbWY/Untitled?node-id=14-4893) on its «Обзор» page: a summary card, «Замеры за сегодня» (two stat tiles, deviation bars, a four-field entry form and the day's log) and «Завтра — День N» with four mode pills. **Tapping a batch on `IncubatorScreen` opens this sheet — any batch, whatever its chip says** — and creating one opens it too, instead of navigating. It replaced the old full-screen `BatchScreen` as the tap target, and then `BatchArchiveScreen` as well: finished and interrupted batches used to route there, so a tap on «Не завершено» dropped the user out of the new design into the old one, to see the same сводка and the same schedule drawn worse. That screen, its route, its `BatchViewModel` and the old day row `MyRowIncubatorSettting` are all gone; the «Убрать из архива» / «Удалить» pair it carried lives on in the card's «⋮» menu, which is where every other action on a batch already was.

- **An archived batch (`hidden`) opens with `ArchivedBatchNotice` above the summary** (owner's request, 2026-10-02) — the incubator screen's `ReadOnlyNotice` row (border, archive box, grey `Caption`) saying the batch counts in neither the statistics nor the finances, as if it never existed, and that «Вернуть в список» in its card menu brings it back into the totals. The sheet otherwise looks exactly like any other batch's, and someone opening it to read a result has to know that result no longer enters anything.- **The summary card's first line is the species, not the batch name.** The name already stands in `SheetHeader` directly above, and repeated five centimetres lower it said nothing new, while the species was represented only by the emoji inside the ring. So the `SectionTitle` line reads «Курицы» (falling back to «Закладка» while `type` is blank), the day line stays second, and the breed line stays third — the card now answers «what bird, what day, which breed» and leaves «which batch» to the header.
- **The mockup's four info tiles live inside the summary card, as a figure strip.** «Заложено яиц», «Осталось сейчас», «Заложено» and «Вывод» were a 2×2 grid under the card; two rows of tiles pushed «Замеры за сегодня» — the reason the sheet is opened at all — below the fold. `SummaryCard` now carries them as one row of figures under a hairline: the two counts, then the two dates merged into a single «Сроки» cell reading «8 авг. → 29 авг.» (one span with two ends, not two facts). The «Осталось» figure keeps its emphasis as accent-coloured text instead of the tile's tinted fill. Cells are bottom-aligned with the figure in a fixed 24 dp box, so the smaller date figure does not step its label out of line, and that cell gets `weight(1.8f)` because a date pair is far wider than a two-digit count. **That bottom alignment is also what lets the strip survive an enlarged system font.** At 1.5× the three cells no longer fit their thirds: the dates ended as «9 сент. → 30 …», losing exactly the date the cell exists to carry, and «Заложено» as «Заложе…». The date value is now `maxLines = 2` and the labels take a second line with `Hyphens.Auto` — by syllable, never by letter, since «Заложен / о» is the very defect being fixed in the incubator header. Bottom-aligned, a second line grows its cell upwards and the labels of all three stay on one line together. **The card's head is the species with the status chip opposite it, the breed on its own line under it, and «День N/M · осталось K дней» last — «осталось K часов» once less than a day is left.** The status left `dayLine()` for the same `StatusChip` the card wears (`ui/batch/StatusChip.kt`): as a grey word inside the day line «Не завершено» was invisible, and the chip is red for exactly that case. The breed is a separate `CaptionEmphasis` line rather than a «Курицы · Ломан Браун» tail on the species — deliberately unlike the batch card's caption: at the card's `SectionTitle` size the two words in one face read as one long name, and a long breed pushed the chip onto a second line; on its own line it is plainly the answer to a second question (whose eggs, not which bird). Blank breed, no line. What replaced the status in the day line is the remaining term, counted to `BatchDetailUiState.finishesAt`, which is `batchFinishMoment` from `ui/incubator/FinishedBatchPrompt.kt` — the hatch date at the laying hour, the very moment the «Инкубация завершена» prompt is keyed to — so «срок вышел» and the prompt arrive together. **Days before the last day, hours only on it — and the days are `totalDays − day`, the very calendar days of «День N/M», not hours to the term divided by 24.** The day number turns at midnight, the term at the laying hour, and counting the tail by hours printed «День 21/21 · остался 1 день» on the morning of the last day (the hatch at 10:00 tomorrow is more than a day off) — two halves of one line contradicting each other. So on day N of M the tail reads «осталось M − N дней», and on day M it is hours to `finishesAt`, which may be over twenty (up to the laying hour of the next morning): «363 часа» is a number nobody converts in their head, while «1 день» on the hatch day is too coarse when the chicks pip towards evening. `hoursLeft` rounds a started hour *up*, so five minutes before the term is still «остался 1 час», never «0 часов»; `hoursLeftPhrase` / `daysLeftPhrase` agree the verb («остался 1 час», «осталось 2 дня»), and past the moment the line says «срок вышел». A finished batch gets no tail (`finishesAt` is `null` for it, and `archive()` clears it), because it has nothing left to wait for. `dayLine(state, now)` takes the clock as a parameter so `DayLineTest` (`app/src/test`) can pin all of that on a fixed moment. **The batch's own note closes the card**, under the figure strip behind a second hairline, through the same `ExpandableNote` the measurement rows use, now with `collapsedLines = 2`: two lines with an ellipsis, a tap unfolds the whole text, a note that fits is not clickable at all. Under the strip rather than under the species because it is about the clutch as a whole, and between the head and the figures it would have cut the card in two. `BatchDetailUiState.note` carries it, trimmed, and a blank note draws nothing — not even the hairline. The species emoji in the card's circle became `ProgressRing` — the same composable `IncubatorScreen` draws on its batch cards, now `internal` with a `diameter` parameter (named `diameter`, not `size`, because `size` inside `drawBehind` is already the canvas). It restates «День 15/21» visually and costs nothing: the circle was there anyway.
- **The sheet has two pages — «Обзор» and «Расписание» — swiped between in a `HorizontalPager`,** with the same pill switcher `IncubatorScreen` uses sitting under the header — literally the same composable, `SlidingTabSwitcher` in `design/components/SlidingTabs.kt`; each caller passes its own `List<SlidingTab>`, a `position` lambda and the outer padding, and gets back the page index. **Its white pill slides rather than jumps**: it is drawn once under the labels and offset by `pagerState.currentPage + currentPageOffsetFraction`, so it follows the finger mid-swipe and coasts with the page when a tab is tapped, while each label's tint lerps by how close its page is. **The label scales on the same fraction** (`TabIdleScale` 0.92 → 1), so the tab that left the screen also steps back rather than only fading; scaling is applied to the icon-plus-label row through `graphicsLayer`, never to the tab itself, which has to keep its width for the layout and the touch target. A tap presses the label to `TabPressScale` on a bouncy spring and the ripple is off (`indication = null`) — a circle-wide ripple next to the moving pill reads as a second indicator arguing with it. The fraction arrives as a lambda read inside the switcher: read it in the caller instead and every frame of a swipe would recompose the whole screen along with the pager. The mockup draws neither: in it the schedule is a separate screen. But a day is edited exactly when today's readings are on screen, and a swipe is cheaper than leaving the sheet and coming back. The header and the switcher are fixed; each page scrolls on its own, which is why the sheet's content column is `fillMaxHeight()` — otherwise the switcher would jump as the two pages differ in length. **The track's height is a minimum, not a constant, and the label may take two lines with `Hyphens.Auto`**: at 13 sp on an enlarged system font «Статистика» ended as «Статис…», i.e. the tab stopped naming its page. Two things inside had to move for that: the «pill» is now a `BoxWithConstraints` wrapped in `matchParentSize`, so it takes its size from the track instead of being asked for one, and the label row is `height(IntrinsicSize.Min)` — `TileRow`'s trick — so the tabs still share one height. Without either, the track asks its children how tall it should be while the children ask it the same thing, and the switcher unrolls to fill the screen. **And the label row is `align(Alignment.Center)`**, which it did not need while it was `fillMaxSize()`: at the ordinary font size the labels are shorter than the track's minimum height, so the `Box` would otherwise park them against its top edge — above the middle of a pill that still runs the full height.
- **«Расписание» is the day list, and the only one the app still has.** One card per day: a day badge, «День N», «8 авг. · сегодня» (the date is derived from the batch start, the schedule stores only the day number), the four mode pills of «Завтра — День N», and the note — `DayNotePlate`, a `PillSurface` plate captioned «ПРИМЕЧАНИЕ» under the pills, two lines with an ellipsis (`DayNoteLines`) and the whole plate a tap to unfold it and fold it back; a note that fits is not clickable, so the tap falls through and opens the day as before. Today's card is outlined in accent green — the old screen outlined it in black — and the list opens scrolled to it. Tapping a card expands it into a day editor — the only place the plan of a day is edited; since v9 its «ПЕРЕВ., РАЗ» and «ПРОВЕТ., РАЗ×МИН» are numeric fields like temperature and humidity, and an empty one means «no quota», not «zero». **Airing here is the same masked cell as in the batch form's schedule table** — «2×15», `filterAiringInput()` — because it is the same regimen edited from two places, and typing it two different ways would be a trap. **The editor writes the `Value` row and never touches its id**, so the measurements hanging off that row stay with their day.
- **A day card also carries that day's readings, and that is where a measurement is written or fixed after the fact.** Expanded, the card shows the day's measurements above the plan editor — fact first, then plan — with the full entry form, the «Изм.» / «×» row controls and the «Аналитика» chip, which opens `BatchAnalyticsSheet` for *that* day, not for today. The collapsed card carries the count in its caption («8 авг. · прошёл · 3 замера»), so a day with readings is findable without opening every card.
- **The retroactive entry attaches to the day's `Value` row like any other**, which is the whole reason it is safe: `BatchDetailViewModel.persist(form, dayId)` takes the target row, `save()` passes today's and `saveDayForm()` passes the expanded day's. A measurement can therefore never be moved onto another day by editing it — the day comes from the card it was opened in. **The day form is a second `MeasurementForm` (`dayForm`), not the shared one**: both pages live in the pager at once, and one form would drop a half-typed reading for today the moment the user swiped to the schedule. It resets with the expanded day.
- **In the day form the «ВРЕМЯ» picker is always visible** (`MeasurementEntry(alwaysShowTime = true)`), not only while editing: «now» means nothing for a day that has passed. Left blank it still falls back to the current clock, same as on «Обзор». Days that have not come yet get no form at all — a reading for the day after tomorrow is not a late entry, it is nonsense.
- **The sheet subscribes to the batch's measurements once, not per day.** `ItemsRepository.getBatchMeasurements(batchId)` joins `Batch_measurement` onto `Batch_value` and the ViewModel groups the result by `idValue` into `measurementsByDay`; `BatchDetailViewModel.measurements` — what «Обзор» renders — is derived from it and today's row. A batch holds a hundred or two readings, so one flow is cheaper than a subscription per expanded day, and the counts on the collapsed cards come for free. Within a day the order stays newest-first, which is what makes `measurements.firstOrNull()` the latest reading. **The history lists re-sort it, because «newest» is counted from the laying hour, not from midnight.** An incubation day runs from `Batch.time` to `Batch.time` (root `CLAUDE.md`), and a measurement stores only its clock time — so for a batch laid at 22:29, 07:18 is the *latest* reading of its day, while the database's text sort (and any midnight-based sort) put it at the very bottom, and the folded list showed three evening readings instead of the last three. `newestFirst(dayStart)` in `BatchAnalytics.kt` sorts by minutes since the day's start, descending, by parsed minutes rather than text (an unpadded «8:05» is not after «19:00»), unparseable times last; `BatchAnalyticsTest` pins it. «История замеров» and a day card's «Замеры за день» both use it with `BatchDetailUiState.startTime`; the incubator sheet takes the laying hour of its first running batch (`IncubatorMeasurementState.dayStart`) — batches of one device may differ, and there is no single right answer. Folded, they show the first `VisibleMeasurements`, i.e. the latest. The day chart keeps plain clock order (`chronological()`).
- **`readOnly` is the sheet's one cross-cutting flag, and it removes rather than disables. It now has two sources, joined inside the sheet as `viewOnly`** — the parameter (the batch's incubator is archived) **or the batch's own `finished`**, plus `!loaded`, so nothing writable flashes over a batch whose status the database has not answered for yet. The second source is not a parameter because this sheet is no longer opened from one place only: it reads the batch itself, so it can answer «кончилась ли она» without being told. A finished batch has an outcome and no continuation — a reading typed into it would be a fact invented after the event — and the way back to editing is «Вернуть в инкубацию» in the card's menu, which is also the only thing that knows what to do with the recorded result. It drops the measurement form on both pages, the «Изм.» / «✕» pair in every measurement row (`MeasurementRow` already took nullable handlers — the delete dialog needed a plain row), the candling button on `TodayCandlingCard` and the candling card inside a day, the `DayEditor`, and «Завершить инкубацию». What stays is everything that reads: tiles, deviation bars, the day log, «Аналитика», and «Завтра» while the batch is still running. Two touches keep it from looking broken where the subtraction leaves a hole —  an empty day still says «За этот день ничего не записано.» instead of collapsing into an empty expanded card (`DayMeasurements` returns early only when it is *not* read-only), and «Замеры за сегодня» says «За сегодня замеров не записано.» rather than inviting a recording nobody can make. **A day still expands** — the expansion is `dayEdit` state, not a write — because the readings of a past day are exactly what someone opens an archived device to see.
- **A finished batch stands on the day it ended, not on today, and the rest of «Обзор» follows from that one number.** `BatchDetailViewModel.load` stops counting at the end once `status != Active` — the same arithmetic `batchProgress` does on the card, deliberately, because two figures about one batch must not disagree. Without it the day kept running after the batch had stopped: a clutch pulled on day 5 of 28 read «День 28/28» a month later, with a full ring and the last day's plan, i.e. exactly the incubation that did not happen. **The two finished statuses stop at different places, and both match the card.** `Stopped` counts to `dateEnd` — that date is all that is known about the moment it was pulled — and `incubationFraction` therefore does *not* fill its ring (`finished && !stoppedEarly`), so an interrupted clutch shows its real quarter. `Hatched` goes straight to `totalDays`: «Завершено» means the term was served, and finishing is allowed from the penultimate day (`canFinishIncubation`), so a batch closed on day 27 of 28 would otherwise print «День 27/28» beside the card's «День 28/28». On top of that number, `dayCaption` swaps «сегодня / завтра / через N дн.» for «день остановки» (or «последний день») and «не наступил», since days after the end will not arrive; and **«Завтра — День N» disappears entirely** — the mode pills are a promise about the next day, and there is no next day.
- **«Замеры за сегодня» disappears with it, and the причина завершения takes its place.** The card is about the current day, and a finished batch has none: it was showing the last day of incubation, which is normally empty (nobody takes readings on the day a clutch comes out) and, when it is not, is one day out of thirty picked by nothing but being last. It answered neither «что сейчас» nor «чем кончилось». The whole journal is already laid out day by day on «Расписание», and per-day «Аналитика» opens from there, so nothing is lost — which is why the Обзор of a finished batch is deliberately short. In its place stand two cards, in the order the questions are asked: **why it ended, then how it was run.**
- `EndReasonCard` prints `Batch.endReason`, in the `Expense` / `ExpenseSurface` red of the «Не завершено» chip and of the «Завершить досрочно» button that wrote it. **Only when the reason is non-blank**: a batch that ran its term has none by construction (see `Batch.endReason` in the root `CLAUDE.md`), and «Причина: —» over a normally hatched clutch would report a problem that did not happen. The reason is free text, so the card wraps it whole rather than clipping to a line — «Отключали свет на двое суток» is the point of having asked.
- `BatchTotalsCard` is «Итог по замерам» — the same twelve figures as «Аналитика за день», in the same three rows and the same order (counters, temperature, humidity), but over the whole incubation. Same order on purpose: it is the same set of questions at a different scale, and someone who has opened the day analytics does not have to learn this card. **It renders even with no measurements**, saying so in one line — and there it differs from `EndReasonCard`, which vanishes when empty: a missing reason means «ничего не случилось» and the summary card already says «Завершено», while «замеров не записывали» is stated nowhere else, and without the line the Обзор of such a batch looks like data that got lost.
- **The arithmetic is `batchTotals()` in `BatchAnalytics.kt`**, next to `analyticsOf` and Compose-free for the same reason — `BatchAnalyticsTest` runs it on the JVM. Two rules in it are load-bearing. **The coverage denominator is the days the batch actually ran**, not the length of its schedule: a clutch pulled on day 5 of 28 still has 28 rows, and «замеры в 3 днях из 28» would read as negligence about 23 days that never happened. Hence the `daysRun` parameter, fed from `BatchDetailUiState.day` — which is exactly why that day had to stop at `dateEnd` first. **And the deviation is measured against each day's own plan**, not against one average target: the regimen changes day by day, so `tempOffPlan` averages `факт − план того дня` over the measurements. Over the measurements, not over the days — a day measured ten times really does say more about the incubation than a day measured once. Days whose plan has no target contribute nothing rather than zero.
- **The line under the tiles reuses the day analytics' `InsightPart` model and its tolerances** (`AVG_TOLERANCE_TEMP` / `AVG_TOLERANCE_DAMP`), so «в цели» for a day and «по плану» for a batch never disagree about what counts as a deviation. `insightAnnotated()` — the plain/bold/mono renderer — moved to `BatchAnalyticsSheet.kt` as `internal` and now serves both.
- **The tiles are `StatRow` / `StatTile` from the analytics sheet, made `internal` and given `surface` / `border` parameters** — white with a hairline on the cream sheet, filled with `DesignPalette.MeasureTile` and no border inside this white card. A local copy was written first and immediately proved the point: it used `DesignType.MeasureValue` (right for the half-width tiles of «Замеры за сегодня») and clipped «38.2°» to «3…» in a quarter-width tile, which is precisely what the analytics sheet's smaller `AnalyticsValue` exists to avoid. One tile, two colours — and reusing it immediately paid for itself, since the clipping it exposed turned out to be the day grid's too (see «Проветрено, мин» there).
- **`BatchScreen` — «Расписание на весь экран» — is gone, and so is the row at the bottom of the schedule page that led to it.** It offered nothing the sheet's «Расписание» does not: the same days, only at full width and one navigation away. With it went the `Batch` route, the `BatchDestination` object, the `"Переход в расписание"` AppMetrica event and `IncubatorScreen`'s `navigateToBatch` parameter; `BatchDetailSheet` lost `navigateToSchedule` and `SchedulePage` lost `onOpenFullScreen`. **Two things survived it for a while and are now gone too** — `MyRowIncubatorSettting`, the old day row, and `BatchViewModel`, both of which had moved into `BatchArchiveScreen.kt` as its last remaining users. That screen went the same way the moment finished batches started opening in this sheet, taking with it `BatchArchiveDestination`, its route, the `"Переход в Архив"` AppMetrica event, `IncubatorScreen`'s `navigateToArchivedBatch` parameter and the now-orphaned `TopAppBarEdit` in `InventoryApp.kt`. **`BatchDayScreen` went with it**, along with `BatchDayViewModel`, the `BatchDay` route, `BatchDayDestination`, the `"Переход в редактор дня"` event and the `AppViewModelProvider` entry — nothing but the removed screen ever navigated there, and the day's plan is edited in the schedule card. **`ValueUiState` and its `toValueUiState()` / `toValue()` mappers survived that file** — the schedule card's editor holds one — and moved into `BatchUiState.kt`, next to the batch form's own state. `ItemsRepository.getBatchValueForDay` is left in place unused: it is a one-line data-layer query, and the day editor is the obvious future caller. **`BatchScreen` also used to own the finish flow — an `EndIncubator` dialog that opened by itself when the term was up — and that went earlier**, along with «Завершить закладку» in the batch form and the `AddBatchViewModel.archive()` behind it. Both wrote `arhive = "1"` while knowing nothing of `endReason` or the chick price, so a batch finished through either lost its result; `FinishBatchDialogs.kt` is now the only way a batch ends. **Do not reintroduce a second finish path.** Opening the sheet still reports `"Переход в закладку"` — it is the same user action as before.
- **Candling opens from the schedule page and from the overview card, and the sheet stays open behind it.** `BatchDetailUiState.candlingStage(day)` — the catalog held in the state — decides which cards get the button; the old free `setOvoskop` is `internal` to `:domain` now, because a custom species keeps its candling days in the database and only the catalog can see them. Stage titles go past three (`stageTitle`: «Четвёртое», «Пятое», then «N-е»), and `stageGoal` / `candlingImage` treat everything after the second candling as the final check — a custom species may mark as many days as it likes, and through the shell the picture after the second look only darkens; `CandlingSheet` is opened as a sibling of the batch sheet's `ModalBottomSheet` and the sheet itself reports the `"Переход в Овоскопирование"` event — see «The candling sheet» below.
- **`ItemDao.getBatchValues` sorts by `day`.** Both the day list and this page treat row N as day N; before the `ORDER BY` that held only because days are inserted in order and SQLite happened to return them by rowid.
- **The sheet writes `Measurement` rows, never `Value` rows**, attached to today's `Value` row — so the day survives a corrected start date or a changed phone clock, and the record button is disabled if the batch somehow has no row for the current day. The four inputs (t°C, влаж.%, «ПРОВ., МИН» and the «ПЕРЕВ.» toggle) plus a note save immediately on «Записать замер»; «Изм.» loads a row back into the form, «×» deletes it. The button is disabled until at least one reading is filled — an empty measurement is not worth a row (what that disabled state looks like is `accentButtonColors()`, above). **The four captions over the fields are `FieldCaption`, and they wrap rather than clip**: they are already cut to the bone — four columns, and the units only fit abbreviated — yet at 1.5× even «ПРОВ., МИН» ran out into «ПРОВ., …», so the field stopped saying what goes in it. The break falls on the space after the comma, and all three rows holding such fields are `Alignment.Bottom`, so the fields themselves stay on one line when one caption grows taller than its neighbours.
- **A column handed to the incubator's automation is locked in the measurement form too, on both pages.** `MeasurementEntry(autoTurn, autoAiring)` — fed from `BatchDetailUiState.autoTurn` / `autoAiring` by «Замеры за сегодня» and, through `DayMeasurements`, by the day form on «Расписание» — draws «ПРОВ., МИН» as the same cream `enabled = false` cell reading «Авто» that `DayEditor` and the batch form's table use, and replaces the «ПЕРЕВ.» toggle with an identical locked cell rather than a greyed checkmark: two columns given to the automation should look the same, and an unpressed tick beside an «Авто» field reads as «you forgot to turn». The rule is the plan's own, applied to the fact — under `Batch.over` / `Batch.airing` the incubator turns and airs by itself, and a turn typed by hand there would be a record of something the person did not do; the counters above already say «на автомате» for the same reason. **`BatchDetailViewModel.persist` strips those fields too** (`over`, `airingCount`, `airingTime` → `null`) rather than trusting the form: a draft survives a collapsed sheet, and a composition can outlive the state it was built from. Rows recorded before the lock keep what they hold until they are edited, at which point the same strip applies.
- **Under the four fields stands the airing timer — `AiringTimerCard` in `ui/batch/AiringTimerCard.kt` — and it is there on the «today» forms only.** `MeasurementEntry(timer: AiringTimerSlot?, onTimerAction)` draws it when the slot is non-null, the airing column is not on automation (the cell is locked «Авто» and there is nowhere to put the minutes) and `canRecord`; `MeasurementsCard` passes it through from «Замеры за сегодня» and from the incubator's measurement sheet, `DayMeasurements` passes nothing — a reading entered into a past day is written after the fact, and a timer there would time nothing. Закройте инкубатор. N минут подставлено в форму — запишите замер.» and one accent «Готово, выключить сигнал». The slot is `BatchDetailState.timerSlot` / `IncubatorMeasurementState.timerSlot` — a cheap getter over three fields — and the card's actions come back as `AiringTimerAction` inside one `…Intent.AiringTimer(action)`; the ViewModel refuses `Cancel` / `Finish` / `Dismiss` over a timer that is not its own and `Start` when there is nothing to record into. **While a timer runs, `AiringTimerFab` (`ui/batch/AiringTimerFab.kt`) floats in the bottom-*start* corner of every screen** — the end corner and the bottom centre are already taken by «+ Инкубатор», the mini «+» and «Внести замер» — the same `TimerRing`, 56 dp with a 4 dp stroke, 20 dp off the edges — the height and inset of «+ Инкубатор» and of the incubator screen's buttons, so the ring stands in one line with them as their left-hand pair. It sits in the activity's root `Box` under the update and ad notices, so it survives every navigation and is covered by any open sheet, which live in their own windows. **It hides on the one form that already shows the card**: both sheets call `RegisterTimerForm(target)`, a `DisposableEffect` that sends `AiringTimerFabIntent.FormShown` / `FormHidden` and so marks the target in `AiringTimerController.openForms` for the life of the composition, and the FAB is hidden while the timer's target is in that set — the ViewModel could not answer this, since it lives as long as the screen and does not know whether its sheet is up.
- **Editing a measurement also exposes its time**, in a full-width «ВРЕМЯ» picker that sits above every other field and, on «Обзор», appears only in edit mode — in its own `AnimatedVisibility` next to the one holding the «Редактирование замера» caption, since the schedule's day form shows the field without the caption. A new measurement is still stamped «now» without asking — that is the common case and a prompt every time would be in the way — but a row entered after the fact would otherwise be stuck with the time it was *typed*. `MeasurementForm.time` and `save()` already carried the value; only the field was missing. Input is the shared `TimePicker` dialog rather than free text, because a hand-typed «HH:mm» can come out in a shape neither `parseClock` nor the sort understands; `clockOrNow()` guards the dialog, which parses its argument with `toInt()` and would crash on a blank.
- **The block reads in three parts, in the order of the job: «Внести замер» (the entry form, right under the summary — and under the candling card on a candling day), then «Замеры за сегодня» (tiles, bars, counters, the «Аналитика» chip), then «История замеров» (the day's log).** Recording is why the sheet is opened, so the form comes first; a read-only sheet has no form and starts at «Замеры за сегодня». Both headings are `MeasurementsHeading`, the `CardHeading` of «Замеры за сегодня». Since «Изм.» is pressed in the history at the bottom and loads the reading into the form at the top, the form section carries a `BringIntoViewRequester` and a `LaunchedEffect(form.editingId)` scrolls it into view whenever a measurement is taken into editing — without it the edit began off screen and the tap looked dead.
- **The big tiles show the day's average — «Средняя температура» / «Средняя влажность» — and each quantity averages only the measurements that carry it.** It used to be the latest measurement whole, so a reading with humidity alone blanked the temperature tile and its bar, and vice versa. The average is the same plain mean as «Средняя t» in the day analytics, so the two figures agree; the deviation and its bar are that average against the plan, and a bar appears once its quantity has at least one reading. Bar scales are the mockup's: ±1.5 ° and ±10 %; the marker clamps at the ends.
- **Under the bars sit two more tiles — «Перевороты» and «Проветривания» — and they count the whole day, not the last measurement.** Temperature and humidity read as "what it is right now", but turns and airings only mean anything as a total: how many so far, how many left. The numbers come from `actionCountsOf()` in `BatchAnalytics.kt` — the same function the analytics sheet's figures use, so the two can't disagree about what counts as a turn. Since v9 the day's quota **is** a number in the plan, so «осталось N» is plain subtraction and nothing parses text any more (`plannedCount` and `isAutoPlan` are gone). An empty quota means there is nothing to ask of the user: the tile says «на автомате» when the batch runs on the device's automation (`BatchDetailUiState.autoTurn` / `autoAiring`) and «без нормы» otherwise — the day row itself no longer carries the word «Авто». An unmet quota is grey, not red — mid-day it is not a deviation, there is still the evening — and only «план выполнен» goes accent green. The airing tile also carries total minutes — measurements store the count and the length of one airing separately, so the day's minutes are the sum of count × length, and a measurement written through the form contributes one airing of the minutes typed — and its plan line reads «2×5 мин», where the remainder is counted from the times alone.
- **Under the counters stands «Примечание ко дню» — `DayNoteCard`, a white bordered card with one multi-line field and no save button.** It is `Value.note` of today's plan row — the same note the schedule's `DayEditor` edits and its day card prints — so nothing new is stored. It saves itself: 600 ms after the last keystroke (`NoteSaveDelayMillis`) and once more in `onDispose` if something is still unsent, so a sheet swiped shut mid-sentence keeps the tail; the write is `BatchDetailIntent.SaveDayNote(dayId, note)`, which copies the note into the row as the schedule flow last delivered it (`viewModelScope`, so it outlives the card) — never into a snapshot, or a regimen corrected on «Расписание» would be put back. The same intent also writes the note into an open `dayEdit` of that day: the day editor saves its whole copy of the row, and without that its «Сохранить» would put the old note back over the new one. **The typed text lives in the card, not in the ViewModel**: the row comes back from Room after every write, and a field overwritten by that answer would drop the characters typed meanwhile; the card adopts the database's note only while it has nothing unsent (`text == sent`), which is how an edit from the day editor still reaches it. Batch sheet only — `MeasurementsCard(onDayNoteChange = null)` in the incubator sheet, whose `plan` is an average with no row behind it. Read-only shows the text, or nothing when it is blank.
- **«Завершить инкубацию» sits at the bottom of «Обзор», and its colour is the warning.** Red (`DesignPalette.Expense`) until the term is nearly up, accent green on the last two days — `canFinishIncubation(type, day)` in `:domain`, `day >= days - 1`. Two days rather than one because chicks do not pip strictly on the calendar, and a tray already peeping a day early should not meet a reproachful red button. **The button stays tappable in both states**: a batch is finished early because it died, not by accident, and the app is in no position to forbid that. A caption under it says in words what the colour says. The mockup draws no such button — a batch has to end somewhere, and its own edit screen is gone. **Only the green state is filled; the red one is an outline.** Both were filled, and that stood the screen on its head: for nineteen days out of twenty-one the largest and loudest thing on «Обзоре» was a solid red bar across the full width — captioned «ещё рано» — while «Записать замер», the reason the batch is opened every single day, sat above it looking switched off (it is `enabled = false` until a reading is typed, which is exactly the state the screen opens in). The warning survives the outline: the red is the same red and the caption is unchanged. What moves is the weight of a filled button, onto the one day it is actually wanted.
- **Which dialog opens depends on the same flag, and the two ask opposite things.** The choice itself, plus the AppMetrica events, lives in `FinishBatchDialogs()` rather than at either call site — the batch card's «Убрать в архив» opens the same pair, and a second `if` would have drifted from this one. Early: a warning, an obligatory reason — blank leaves the confirm button disabled, because there is no coming back to fill it in — and a red tile naming what goes to expenses, in roubles when the batch has a price and in eggs when it does not (a bare «0 ₽» would claim the eggs were free). Four preset reasons sit under the field as chips; typing your own is always allowed. On time: the chick count, its field **clamping** to the eggs left after the candlings (`hatchLimit(eggAll, candling)` — the manual cull is not a limit, because finishing rewrites it as the remainder: everything that did not hatch is cull, and the caption under the field says how many that will be) rather than rejecting the keystroke (the same choice as `CandlingViewModel.updateRejected`), plus the price with a «за птенца / за всех» switch. Zero chicks is a result, so only a *blank* field disables the button. One hatch field and one price, because a batch has one breed — a tray of two breeds is two batches, each finished through its own dialog, which is how «which breed hatches better and sells for more» is answered without a second ledger inside a batch. The field and the price are one `FinishRow` (hatched + price + per-head together) under a `listSaver` that flattens it to three strings for rotation; `onConfirm` hands back a `HatchOutcome` that `BatchDetailViewModel.finish` passes straight to `Batch.finishedOnTime` in `:domain` — the clamping is decided there, not in the dialog. The summary card of the sheet prints the breed on its own line under the species, name only, its count being «Заложено» in the strip below. Both close the sheet on success; the batch list under it is a flow and refreshes itself — and an on-time finish with chicks then raises the celebration on the screen underneath (`onHatched`, see the incubator screen section). **The reason is also what the summary card's status chip reads back**: `StatusChip` shows «Не завершено», not «Завершено», once `BatchDetailUiState.stoppedEarly` is up — the sheet is one of the places a batch is stopped, and it must not report the batch as having run its course a second after it was pulled. That flag sits beside `finished` rather than replacing it with a `BatchStatus`, because the sheet asks «всё ли кончилось» far more often than «чем именно»; both are written from `Batch.status`, so `stoppedEarly && !finished` cannot occur.
- **`PriceRow` / `PriceSummaryTile` live in `design/components/SheetForm.kt`, not in the batch form.** The finish dialog asks for the chick price exactly the way the batch form asks for the egg price — only the two labels differ, so they are parameters. **In the form the field and the switch split the row in half** (`weight(1f)` each, and the two chips split the switch the same way): the rows above it are already halves — count + cull, date + time — and the two summary tiles below it are too, so a switch sized by its own labels was the one crooked line in the column. **The dialog passes `evenSplit = false`**, and it is the only caller that does: its row is half as wide and its labels longer, so «за птенца» came out as «за пте…». There the switch keeps the width of its labels, but `IntrinsicSize.Max` still gives both chips the width of the longer one.
- **The AppMetrica events are the old screen's**, `"Полное завершение"` and `"Досрочное завершение"` (`Events.FINISH_ON_TIME` / `FINISH_EARLY`), with the same parameter names plus «День» and, for the early one, «Причина». **A third event goes out beside them, and not from here**: `"Итог инкубации"` — the report tying the device (бренд, модель, «Эффективность, %») to the result — is sent from `BatchDetailViewModel.archive`, after the write and before `onDone()`. It belongs there rather than in the dialog because the incubator archive ends batches without opening any dialog at all, and «which model hatches best» has to count those too; the reasoning is in the root `CLAUDE.md` and in `analytics/IncubationReport.kt`.
- **A small «Финансы» card stands at the bottom of «Обзор», above «Завершить инкубацию»** (`BatchMoneyCard`, owner's request, 2026-10-02) — two lines and nothing else: «Куплено яиц» (`eggsCost`, with «N яиц по X ₽» / «за всё» under it, «цена не указана» rather than «0 ₽» when no price was typed) and «Электроэнергия» (rubles; under them the hours run — «N часов прошло» while running, «N часов работы» once finished, `batchRunHours`, the very span `batchSpan` the bill is counted over and at the same `now`, so hours and kWh describe one stretch, and shown even when there is no tariff to price it — then kWh and «общие часы поделены…» when shared). **On a two-zone tariff two indented lines follow, «Дневной тариф» and «Ночной тариф»**, each with its own sum, kWh and time — the window («07:00–23:00» / «23:00–07:00», `BatchDetailUiState.nightWindow`, read from the batch's settings over the device's) and the hours spent in it (`ElectricityCost.nightHours` / `hours`, real hours, **not** shares: neighbours split the money, not the time; day hours are the run hours minus the rounded night, so the two add up to «N часов» above) — `ElectricityCost.nightKwh` / `nightRubles` / `twoTariffs`, accumulated in `electricityCosts` per segment and split between neighbours like the total, the day part being the difference; the day line's rubles are the rounded total minus the rounded night so the two always add up to the line above. A batch whose own tariff is single (its settings win over the device's as a whole) shows no split. The electricity is `electricityOfFinished` — the same arithmetic «Финансы» and the celebration use, so the three agree — read once per opening in a child coroutine of `load` (`BatchDetailUiState.electricity` / `electricityLoaded`, a dash until it answers). It is a snapshot: a running batch's sum grows by the hour and the sheet re-reads it on every opening. No profit line — a running batch has none yet, and a finished one has it in «Финансы» beside its income. Shown in read-only sheets too: it reads.
- **There is no bottom button besides the finish one.** The mockup draws a permanently disabled «Сохранено» there, which reads as breakage — everything on this page is already saved by the time it would be visible. A «Готово» that only closed the sheet stood there for a while and went the same way: the cross in the header and the swipe down already close it, exactly as in every other sheet.
- **«Аналитика» opens `BatchAnalyticsSheet`** — a sheet over this one, hosted the same way the delete dialog is (a sibling of the `ModalBottomSheet` call, so it lands in its own window above). With no measurements it stays at 40 % opacity and is not clickable: there would be nothing to count. It reports the AppMetrica event `"Переход в аналитику"`. **The weight in its header row belongs to the heading, not to the gap between them.** Under `SpaceBetween` both were measured by their own text, so on an enlarged font they simply met in the middle: «Аналитика» broke into two lines inside the chip and pressed against «Замеры за сегодня». The heading now carries `weight(1f)` and two lines of its own, and the chip's label is `softWrap = false` — it takes what it needs first, and the heading yields. The host state is the `Value` being analysed rather than a boolean, because the schedule page opens it for any past day.
- **«Осталось» is «Заложено» minus everything culled** — `BatchDetailViewModel.rejectedTotal`, which is the sum over `Batch_candling` **plus** `Batch.eggRejected`, the cull typed by hand in the batch form for eggs lost between candlings. It used to equal «Заложено» only because there was nowhere to record a cull at all. `CandlingViewModel.eggsBefore` subtracts the manual figure too: at a candling, eggs already thrown out are not in the tray. The figure flips to «Выведено» for a finished batch. The candling rows are held as a flow, not read once: the candling sheet opens over this one and closes with a number the summary has to pick up.
- **On a candling day a `TodayCandlingCard` sits between the summary and «Замеры за сегодня».** Candling falls on two or three days out of thirty, and on such a day it is the thing the batch was opened for, so it goes above the measurements rather than inside the schedule. It is not the `CandlingCard` plashka from a schedule day card: that one is a caption on one row among thirty, this one names the occasion (`stageTitle` — «Первое овоскопирование · День 7») and carries a full-width «Начать овоскопирование». **What the candling is looking for (`stageGoal`) is deliberately not on this card** — a paragraph of prose sitting on top of the summary would push «Замеры за сегодня» down every second time the sheet is opened; the explanation waits in the candling sheet the button opens, and the card keeps only the occasion and the way in. **A candling already done today does not remove the card** — it turns into «Открыть овоскопирование» plus a line with the recorded cull, because that is the only way back in to fix a mistyped number. A finished batch never shows it.
- **«Завтра — День N» warns when tomorrow is a candling day** — `CandlingPlannedNotice`, under the mode pills, in the same spot the schedule day card puts its own candling plashka so the notice does not move between the two views. Candling needs preparing for (a dark room, the candler, ten free minutes), and the evening before is more use than the morning of. It is a caption, not the clickable `CandlingCard`: that one opens the candling sheet, and tomorrow's candling is not done today — a button there would promise something that must not be done yet.
- **Mode pills get their value already short.** `compactMode()` is gone with the text plan: `planTurnLabel()` and `planAiringPill()` in `ValueFormat.kt` render the numbers straight — «3», «нет», «2×5», and «Авто» only when the batch runs on the incubator's automation. The wordier «2×5 мин» is `planAiringLabel()`, for places with room for it — today the day counters alone, since the archive screen that was its second caller is gone.

## The incubator measurement sheet

`ui/incubator/IncubatorMeasurementSheet.kt`, hosted by `IncubatorScreen` like every other sheet, with `measurementDraft` on the screen so a swipe keeps the typed reading and the cross discards it. It has no mockup: it is the «Замеры за сегодня» card of the batch sheet raised to the device — literally the same `MeasurementsCard` (in both sheets it stands straight on the sheet's background with no white card around it; its own tiles — «Температура», «Влажность», «Перевороты», «Проветривания» — are white with the `CardBorder` hairline like every other card of the sheet, not `MeasureTile`-filled; the two deviation bars share one such card, and the journal rows (`MeasurementRow`, also used in the schedule's day cards and the delete dialog) are white with the same hairline instead of the `MeasureRow` tint) from `BatchDetailSheet.kt`, now `internal` and fed explicit parameters (the plan for targets and norms, the automation flags, `canRecord`, the journal, a `historyKey` and an `emptyText`) instead of `BatchDetailUiState`, so that the batch sheet and this one cannot draw two different cards for the same thing. `SheetCard` and `ConfirmDeleteMeasurementDialog` are exported the same way. **The ViewModel refuses writes on its own** (`IncubatorMeasurementState.archived`, read from `getIncubator` as a flow): an archived incubator has no running batches and therefore no targets, but a refusal by coincidence is not a refusal, and the screen hides the button in the archive anyway. What the data does underneath is in the root `CLAUDE.md` («A measurement can be taken for the whole incubator»): one copy per running batch, one `groupId`.

- **A card above the readings says where the record will go, and chooses it** — `TargetsCard`, one row per running batch — emoji, name, the same «вид · порода» line the batch card carries, «N яиц · День N/M», and a checkbox at the trailing edge (read on the left, answer on the right, and the boxes line up in one column); rows are separated by the card-border hairline, since two-caption rows with no divider read as one column. **Every box starts checked and the copy goes only to the checked ones**; «Выбрать все» / «Снять все» sit under the list as two equal halves (`weight(1f)` each — a pair, not a tail), each disabled when it would change nothing. The choice is kept as the set of *deselected* ids (`IncubatorMeasurementState.deselected`, `selectedTargets()` in `IncubatorMeasurements.kt`), not selected ones: a batch that appears while the sheet is open is then selected by itself and a finished one drops out without a trace — a set of selected ids would have to chase the target list on every database answer. It is input like the form and resets with it on `Load(resetForm = true)`. The common plan, the automation flags and `canRecord` are computed over the selected recipients only, so unchecking the one batch whose plan differs restores «цель» for the rest. A row is `toggleable` with `Role.Checkbox` (the whole row, not the 20 dp box), and a batch without a day row has its box disabled and unchecked — nothing could be written there whatever the choice. **It opens collapsed, titled «Справка», with a chevron**, and a tap on the card expands it into the full heading («Запись попадёт в каждую идущую закладку»), the explanatory note and the list; the same tap folds it back. Collapsed by default because the sheet is opened for the form and the explanation is read once — expanded, it pushed the tiles and the form below the fold on every open. The state is `rememberSaveable` inside the card, so it survives rotation and resets with the next open. A batch that has no row for today («в расписании нет такого дня») stays in the list in red rather than vanishing: a person with two such batches out of three would otherwise record «в инкубатор» and find the reading in one batch without knowing why. The card's note also says the reading can be corrected both here and inside each batch, since a copy edited from a batch sheet is just that batch's row.
- **The journal shows a group as one line** (`deviceMeasurements`) — **stitched, not picked**: copies of one group differ only by what each batch's automation stripped, so the line takes time and readings from the first copy and turning / airing from the first copy that has them; picking any one copy would show «—» where a hand-turned batch holds a 3, count zero turns, and load an empty field into «Изм.» that saving would then write into every copy — and never the readings typed inside a batch — those belong to their batch, and a line here could not say whose it was. «Изм.» loads the stitched line into the form and saving rewrites every copy of the group (`updatedCopies`), the cross deletes them all after the same confirmation dialog the batch uses — **and both fetch the copies by `groupId` from the database (`getMeasurementGroup`), not from today's rows**, so a copy sitting in a batch that was finished after the reading is corrected or removed along with the rest instead of keeping a value the device never showed. The mark itself survives a correction made inside a batch sheet: `MeasurementForm.groupId` carries it through `persist`. Three lines collapsed, `ShowAllToggle` beyond that, as in the batch.
- **The tiles' target, the deviation bars and the counters' norm come from `averagePlan()`** — the mean of the selected batches' day plans, per field over the batches that set it (temperature to hundredths, humidity to tenths, counters to a whole — the precision the tiles print), «цель не задана» only when no selected batch sets the field — and the form's locked «Авто» cells appear only when *every* target is on that automation (`IncubatorMeasurementState.autoTurn` / `autoAiring`): one batch turned by hand is enough to open the cell, and the batches on automation still get `null` in their copies. «Аналитика» opens the same `BatchAnalyticsSheet` on the group's journal with that common plan.
- **The ViewModel is a `StatefulMviViewModel` like the batch sheet's** — targets from `getBatchesFor` filtered to `Active`, then one `getBatchValueForDay` per running batch under `flatMapLatest`, then one `getMeasurementsForDays` over those day ids; `loaded` waits for the first answer so an empty journal is never shown as «no readings yet» before the database has spoken. It has no effects: saving does not close the sheet, the journal simply updates.

- **A mini FAB floats over the content in the bottom-end corner and opens the QR scanner** — `ScanFab`, a 48 dp `SmallFloatingActionButton` in `Accent` / `OnAccent` with `ic_qr_scanner_design`, the same circle as the mini «+» over the batch list. It is here because this is where the person is standing: on a round of the hatchery a reading goes into one device and the next sticker is a camera's length away, whereas «close the sheet, back to the list, find the card, open it, «Внести замер»» is five taps per device. **It floats rather than standing in a footer row, and three rules keep a floating button from covering the sheet.** It is *small* — anything wider than the circle would sit over the form's fields. It *hides while the list is scrolled down and returns on the first pull up* (`NestedScrollConnection` on the content column with the same 3 px threshold and the same 160 ms fade-and-scale the incubator screen's FAB uses), so while someone reads the journal or reaches for «Записать замер» there is nothing over them. And it *hides with the keyboard* (`WindowInsets.isImeVisible`): the sheet's window shrinks to the strip above the IME and a circle in that strip's corner would hang exactly over the field being typed into. A footer row under the scroll was tried and rejected: it cost the sheet its height permanently for a button needed for a second. **The bottom reserve (`FabReserve`, 96 dp) is applied *after* `verticalScroll`**, so it is the tail of the scrolled content — the last journal line comes up above the button — and not a strip that shortens the viewport; before `verticalScroll` it left a blank band under the content with the FAB alone in it. The tap is `navigateToScanner`, threaded from the nav graph through `IncubatorScreen`; a found device replaces this incubator on the back stack (see «The QR sheet and the scanner»).

## The QR sheet and the scanner

`ui/qr/` holds the two screens behind a device's QR code; what the code contains and how launching by it works is in the root `CLAUDE.md` under «QR codes». Neither has a mockup.

- **`IncubatorQrSheet` is a `ModalBottomSheet` hosted twice** — by `IncubatorScreen` (the QR icon in the header, left of the pencil, live in the archive too since a code is a property of the device) and by `StartScreen` («QR-код» first in the card's «⋮» menu, above the archive item, because it is the one item that changes nothing and the one an archived device still needs). It takes an `incubatorId` and loads through `IncubatorQrIntent.Load`, like every sheet; there is no `SheetDraft`, since nothing is typed. **The card is `Color.White` with `Color.Black` modules in both themes** — the one deliberate exception to the «`Color.White` is reserved for content on `Expense`» rule in the theme section: this card is a print artefact to be photographed and printed, not an element of the screen, and a dark card with cream modules would read worse to a camera and print as something else entirely. `QrImage` draws the `QrModules` grid on a `Canvas` with a two-module quiet zone, each module half a pixel oversize so fractional cell widths leave no hairline gaps (a finder pattern drawn as a dotted square is what a camera then refuses), and **the launcher icon on a white pad in the middle** by `logoLayout()` — the same geometry `QrBitmap` prints and `QrCodeTest` blanks, see «QR codes» in the root file; the icon is `appIconBitmap` remembered per package name, the same system call «О приложении» makes. Under the code: the device name (`CardTitle`, two lines) and `modelLine` (`Mono`), so four codes on a table can be told apart before they are stuck on. **Two modes sit above the card — «Кратко» / «Подробно», two equal `ChoiceChip`s, and only when the incubator has a note** (`QrMode` in `IncubatorQrState`, kept across incubators for the ViewModel's life since it is a choice about what to print, not a property of the device). «Подробно» adds `Incubator.note` under a hairline on the card, captioned «ПРИМЕЧАНИЕ» and shown whole — a sheet hung beside the device is read by eye, and paper has no tap to finish a clipped line. The PNG follows the mode: compact prints the name only, as always; detailed passes `QrDetails` to `QrBitmap`, which adds the brand/model line and the note as a word-wrapped `StaticLayout`, sizing the bitmap to what is actually there. With a blank note there is no «Подробно» at all: the chip row is hidden (two identical cards are not a choice), and `IncubatorQrState.effectiveMode` reads as `Compact` for the card, the PNG and analytics, while the stored `mode` is kept so the choice comes back once a note is written. `QR_EXPORT` / `QR_SHARE` carry «Режим». Chips rather than `SlidingTabSwitcher` because that one demands an icon per tab; `ChoiceChip` centres its content for this (no effect on content-sized chips). **The switch is animated over 180 ms** (`ModeSwitchMillis`, the filter row's duration): the note block expands from the top with a fade inside the card, the chip row does the same when a note appears or disappears, and the leaving note keeps its last text while it collapses (a plain holder, not `State`, so composition does not write state it reads). `ChoiceChip` crossfades fill, border and label (`animateColorAsState`) — app-wide, so the batch filter and the settings chips glide too. Two notes under the card say what the code does and what it does not (renaming keeps it, another phone cannot open it). **The two buttons are the export dialog's pair** — accent «Сохранить картинку» (`CreateDocument("image/png")`, file name from `IncubatorQrViewModel.fileNameFor`) and `IncomeSurface` «Отправить в другое приложение» (`ACTION_SEND` with a FileProvider URI from `exports/qr`) — for the reason that pair exists everywhere else: a file for oneself and a file for someone else are different intentions. **The two buttons are a fixed footer, and only the code and its notes scroll** — the middle `Column` is `weight(1f, fill = false)` + `verticalScroll`, so on a short screen or an enlarged font the buttons stay on screen instead of waiting below the fold, and while everything fits the sheet is as short as its content. The outcome comes back as an effect and is shown in the same «Готово / Не получилось» dialog `ScheduleTransferDialog` uses. `Events.QR_SHOWN` is reported by both hosts at the tap, like every other «open» event, and not from the sheet's `LaunchedEffect` — that re-runs on rotation and would count a turn of the phone as a second opening.
- **`ScanQrScreen` is a navigation destination (`ScanQrDestination`), reached from the scanner icon beside the hamburger on `StartScreen` and from the measurement sheet's FAB, and it is the one screen that does not wear the app's silhouette.** It is a camera: black ground, `PreviewView` in an `AndroidView` filling the screen, a 55 % scrim with a rounded square cut out by `BlendMode.Clear` (which needs `CompositingStrategy.Offscreen` on the canvas, or Clear would erase the preview under it), a white 2 dp frame around the window, the title centred at the top, and at the bottom the hint line and **two round camera controls with captions — «Фонарик» and «Закрыть»** (`CameraControl`, 60 dp circles: a camera is held at arm's length and the targets are bigger than in a list). Both live at the bottom, under the thumb of the hand holding the phone; there is no back button at the top, which would be a second way to do the same thing. **The torch control is always drawn**, disabled at 40 % and captioned «Нет вспышки» when `cameraInfo.hasFlashUnit()` is false (or the permission is missing): a button that exists on some phones and not on others reads as broken on the others. Switched on it is painted `Accent`, so «горит» reads from a distance at which the caption does not. The status bar goes black with light icons through `StatusBarAppearance`, like any camera app. **The camera permission is asked on entry, without a rationale screen first** — the screen was opened for the camera, and explaining why a scanner wants one is explaining nothing — and after a refusal the camera's place is taken by `PermissionDenied`: an explanation and two buttons, «Разрешить» (ask again) and «Настройки приложения» (`ACTION_APPLICATION_DETAILS_SETTINGS`), the second because Android stops showing the dialog after the second «no» and the screen would otherwise be a dead end. `denied` is `rememberSaveable` so a rotation does not re-ask. **CameraX is bound in a `DisposableEffect` keyed on the lifecycle owner**: `bindToLifecycle` releases the camera in the background and retakes it on return, `onDispose` unbinds when the screen is left (otherwise the camera would stay open behind the app until the activity died) and shuts down the single-thread executor the analyzer runs on. `KEEP_ONLY_LATEST` drops stale frames rather than queueing them; the analysis resolution asks for 1280×720 or the closest, since at the default 640×480 a 3 cm sticker read only from up close. `QrFrameAnalyzer` calls back on the analysis thread, and the screen hops to the main one through `rememberCoroutineScope` before sending `ScanQrIntent.Decoded` — intents are main-thread calls like everything in Compose. The torch exists because incubators live in back rooms and cellars, and a sticker there reads worse than on a table.
- **`ScanQrViewModel` answers a decoded text in one of three ways, and only one of them navigates.** Not a link (`QrLink.parse` → null): «Это не QR-код инкубатора». A link whose id `getIncubator(id).first()` returns null for: «Такого инкубатора нет в приложении — код напечатан с другого телефона или инкубатор удалён». Found: `done = true` and `ScanQrEffect.Open(id)`, once — the camera keeps delivering frames while the navigation runs, and without the flag one sticker opened its device twice. **The lookup is here and not on the incubator screen** because the person is standing at the device with the camera up, and «нет такого» has to be said there, not after a jump to an empty screen (`MissingIncubator` on `IncubatorScreen` still covers the camera-app path, which never passes through this ViewModel). Messages are state, not effects — they hold for `MESSAGE_MILLIS` (3 s) and clear themselves — and the same text repeated by the analyzer at frame rate does not restart the timer: `shownText` remembers what is being said, so a wrong code held in front of the lens shows one steady pill instead of a flicker. The pill keeps its last text while fading out (`shown` in the screen), or it would collapse to a dot before it disappears.
- **A found device is navigated to with `popUpTo(StartDestination.route)`**, from the nav graph's `onFound` — the same navigation the camera-app path makes for a `QrTarget`, so the two ways of scanning a sticker cannot end on different back stacks. The scanner and the incubator it was opened from (when it was opened from the FAB) leave the stack together, and «назад» from the new device goes to the list. `Events.QR_OPENED` is reported there with «Источник» = «сканер»; the camera-app path reports «камера».

## The day analytics sheet

`ui/batch/BatchAnalyticsSheet.kt` follows mockup [node 21:9088](https://www.figma.com/design/B48q96fOq7Nsy569AXrbWY/Untitled?node-id=21-9088): a chart of the day's readings, a 4×3 grid of figures and a verdict card. It takes the measurements and today's `Value` as parameters rather than loading them — `BatchDetailViewModel` already has both, and a second ViewModel would read the same rows twice.

- **All the arithmetic lives in `BatchAnalytics.kt`, which imports no Compose**, so `BatchAnalyticsTest` in `app/src/test` runs it on the JVM. Adding a figure to the grid means adding a field to `DayAnalytics`, not a calculation inside a composable. The file now holds three entry points, all Compose-free for the same reason: `analyticsOf` (this sheet), `averagedScheduleOf` (the batch form's «среднее по замерам», below) and `batchTotals` (the «Итог по замерам» card on a finished batch's «Обзор», see the batch sheet section). They share `actionCountsOf`, so no two of them can disagree about what a turn is.
- **`averagedScheduleOf()` lives in that same file and belongs to the batch form, not to this sheet.** It turns a finished batch's measurements back into a `List<Value>` — a plan built out of what actually happened — for «Взять из архива → среднее по замерам». It is here because it is the same arithmetic under a different name (`actionCountsOf()` counts its turns and airings, so the two can never disagree about what a turn is) and because being Compose-free is what makes it testable. Three rules are load-bearing, all pinned by tests. A day with no measurements stays the source batch's plan, and so does any single column the measurements never filled — an unfilled counter is `null`, `actionCountsOf` reads it as zero, and a zero written into a plan means «do not turn», a quota nobody set; a recorded zero, by contrast, is kept. Temperature rounds to one decimal and humidity to none, the same budget the tiles and the input fields use. And `airingTime` is minutes of *one* airing, so it comes out as the day's total minutes divided by the number of airings, never as the sum.
- **The grid reads by rows: counts, then temperature, then humidity** — «Замеров / Переворотов / Проветриваний / Проветрено, мин», then «Средняя t / Разброс / Минимум / Максимум», then the same four for humidity. That is why «Минимум» and «Максимум» appear twice without saying of what: the row's own values carry the ° or the %. Airing gets two tiles because a measurement stores the count and the length of one airing separately — `airings` sums the counts, `airingMinutes` sums count × length.
- **The «В цель ±0.3°» tile is gone** — mockup 21:9088 gave its place to humidity's min and max, so `inTargetPercent` and `TARGET_BAND_TEMP` were removed rather than left computed and unshown. Nothing else read the hit rate; bringing it back means restoring both plus a thirteenth tile.
- **Four tiles across is tight, and the labels wrap rather than truncate.** The mockup ellipsizes «Проветр…» and «Ср. влажность» at a fixed 66 dp tile height; here the tile keeps `heightIn(min = 66.dp)`, its right inset drops from the mockup's 12 dp to 6 dp, and `Hyphens.Auto` lets a long label take a second line — so on a 360 dp phone rows 1 and 3 may stand one line taller than row 2 instead of losing words. `StatRow` equalises height *within* a row, not across the grid.
- **The value has no such escape, and that is why «Проветрено» carries its unit in the label.** A figure wraps to nothing — it is `maxLines = 1` with an ellipsis, since a number split across two lines is worse than a clipped one — **and since it is `TruncatedText`, a clipped one shows itself whole on tap** (on an enlarged font every temperature tile reads «35…»; the tap answers «35.0°»). «Итог по замерам» on a finished batch's «Обзор» shares `StatTile`, so it got the tooltip with it. Still, «130 мин», the only value in the grid with a word in it, came out as «130 …» on a 375 dp screen: the tile lost exactly the thing it exists to show. It is now «Проветрено, мин» over a bare `130`, and the label takes the third line the same way «Провет-ри-ваний» beside it does. The same string is used by the «Итог по замерам» card, which shares the tile — the clipping was found there first and turned out to be this grid's too.
- **The temperature line is red and humidity is a second, blue line** — the mockup draws one green line. Green already means accent and «в норме» everywhere else in the app, and the two series need to be told apart at a glance. They carry **separate axes**, temperature on the left and humidity on the right, because 37.5 ° and 58 % share no scale; when only humidity was recorded it takes the left gutter instead.
- **Events are drawn by shape, not by colour alone**: a turn is a solid vertical line across the plot, a note is the same line dashed, and an airing shades the time span it covered — it is the only one of the three with a duration, and the shaded span is the whole time the incubator stood open (count × the minutes of one airing; a measurement written through the form always has a count of one, so it is simply the «ПРОВ., МИН» value). One measurement can emit all three at the same minute. The legend lists only the kinds that actually occurred.
- **`niceAxis` checks the step against the *rounded* bottom, not against the raw range.** Flooring the low end eats into the window: readings 37.1…37.9 span 0.8, which a 0.2 step would seem to cover, but the axis then runs 37.0…37.8 and the maximum gets drawn above the top gridline. `BatchAnalyticsTest` sweeps a grid of ranges against both step sets to pin this.
- **Lines between points are straight, though the mockup curves them.** A smoothed curve bulges past the highest reading, and «Максимум» is a tile directly under the chart.
- `turns`, `airings` and `airingMinutes` are three sums over numeric fields: turns, airing counts, and count × the minutes of one airing. An unfilled field is `null` and contributes nothing — in a measurement it means «not recorded», which on a day counter is indistinguishable from zero. **The entry form never asks for the airing count** — one entry is one airing, so `MeasurementForm.airingCountValue` is `1` whenever the minutes field is filled and `null` when it is empty; the count is stored anyway, because the *plan* uses it («2 раза по 5 минут») and both sides share the column. All three live in `actionCountsOf()` rather than inline in `analyticsOf()`, because the batch sheet's «Замеры за сегодня» card shows the same three figures; `DayAnalytics` just carries what that function returned.
- The verdict text comes back from `insightParts()` as plain/bold/mono segments rather than a finished `AnnotatedString`, so the wording stays testable and the composable picks the type.
- Chart colours are `DesignPalette.Chart*`; the tile figure is `DesignType.AnalyticsValue` (Fraunces 20/20). One tile — «Проветрено, мин» — is brown (`DesignPalette.DateEmphasis`) for any value, exactly as the mockup paints it; the other eleven are `onSurface`.
- The chart card is still titled «Показания в течение дня», not the mockup's «Температура в течение дня», because humidity is drawn on it too.
- **The chart opens full screen, and only there does it zoom.** An expand icon (`ic_expand_design`, drawn only when there is a chart) in the card's title row opens `FullscreenChartDialog` — a `Dialog` with `usePlatformDefaultWidth = false` and `decorFitsSystemWindows = false` plus `safeDrawingPadding()`, so it fills the screen in either orientation and stays out from under the status bar on Android 15+. **Orientation there is changed by a button, never by the sensor**: while the dialog is open the activity is held in `SCREEN_ORIENTATION_LOCKED`, and the rotate button (`ic_rotate_design`, first in the tool row) requests `PORTRAIT` or `LANDSCAPE` — someone reading a chart tilts the phone as is comfortable, and a chart that flips under the hand is worse than one that stays; the request lives in `rememberSaveable` because it recreates the activity, and `onDispose` returns `UNSPECIFIED` only when `!isChangingConfigurations`, or the dialog would release the lock at the very moment it asked for the turn. There is no hint text about the gestures — the row holds the rotate and zoom buttons only. **The rotate button carries a word, «Повернуть», beside a phone-with-arrow glyph**: a bare circular arrow read as «refresh». **In landscape the dialog tightens**: the gaps above and below the chart halve, and `ChartLegend(singleLine = true)` lays the whole legend out in one row that scrolls sideways when it does not fit — height is the scarce thing there, and a second legend row was taken straight out of the plot. Inside it is the **same `DayChart`**, handed a `ChartViewport` and an `onViewportChange`: a pinch scales 1×–8× around the fingers, one finger pans in both directions, a double tap resets. In the card the chart takes no gestures at all — a pan there would fight the sheet's scroll and its dismiss drag, and a pinch inside a `ModalBottomSheet` is the gesture that closes it. **`ChartViewport` (`ui/batch/ChartViewport.kt`) is the arithmetic and imports no Compose**: scale, an `offsetX ≤ 0` / `offsetY ≥ 0` pair in plot pixels, `transformed(zoom, cx, cy, pan…)` keeping the content point under the centroid where it is, and `clamped()` so the content's edge never leaves the plot's edge (an empty field on a full screen reads as a chart that failed to draw). `ChartViewportTest` pins it. Three consequences inside the drawing: the content is drawn under a `clipRect` of the plot while the axes stay at the edges; gridlines and their labels move with the content and are dropped when off the plot; and at 2× / 4× / 8× the axis step is halved / quartered / … (`ChartAxis.ticks(subdivisions)`, `ChartViewport.subdivisions` — the largest power of two not above the scale, so ticks do not flicker in and out mid-gesture). **Sub-tick positions are exact, not rounded to hundredths** — `ticks(n)` rounds only binary noise, so a step of 0.1 split in eight gives equal 0.0125 gaps rather than gridlines dancing between 0.01 and 0.02 — **and a sub-tick is labelled only when the label can print it exactly**: `ChartAxis.printable(value, decimals)` (two decimals for temperature, one for humidity, `ChartSeries.labelDecimals`) — the gridline is drawn either way, at its exact position, but 37.125 stays an unlabelled line rather than a line captioned «37.13» a hair away from where it is; 0.5 therefore labels down to 0.25 and 1 % down to 0.5 %. **Zoom is also reachable without a pinch**: «−», «+» and «1:1» (`ZoomButton`, `ZOOM_STEP` = 1.5) sit at the right of the tool row (`ChartToolButton`) and scale around the plot's centre — the chart reports its plot size through `onPlotSize`, since a button, unlike two fingers, has no centroid of its own. **Time labels are thinned by pixels, not picked by index**: `timeLabelIndices(xs, minGap)` keeps the first, adds a point once it is a label-width clear of the last kept one, and lets the last point evict the previous pick rather than be dropped — in a 300 dp card with a handful of points that is the mockup's two or three labels, and zoomed in it is exactly as many as fit. «Раскрыт» lives in `rememberSaveable` in the sheet — rotating into landscape recreates the activity — and the two hosts had to survive that too: `BatchDetailSheet.analyticsDayId` (the day's `Value.id`, resolved against `uiState.schedule`) and `IncubatorMeasurementSheet.analyticsOpen` are `rememberSaveable` now where they were `remember`. The viewport itself resets on rotation on purpose: the plot has a new size, and the old offset would show the wrong place. `Events.CHART_EXPANDED` is reported at the tap.
- **A note is an icon under its dashed line, and tapping it shows the text.** `ChartEvent.note` carries the measurement's note (trimmed); when the day has any, the chart reserves an 18 dp row (`NoteRowHeight`) between the plot and the time labels — only then, so the mockup's chart loses no height when there is nothing to put there — and draws a small «sheet with lines» glyph (`drawNoteIcon`, in the Canvas rather than a drawable so it is placed by the same `ChartFrame` the tap handler uses) under the end of each note's line. `noteGroups(notes, xs, minGap)` folds notes whose lines stand closer than the icon's width — two notes in one minute, or neighbours at a squeezed scale — into one icon drawn as a small stack, and the tap opens them together (`visibleNoteGroups` filters to the notes inside the plot **before** grouping, so a neighbour still on screen is not dragged off it by an anchor that scrolled past the left edge, and clamps the icon fully inside the plot): `NotePopup` is a `Popup` anchored above the icon (below it when there is no room), the same white card with a hairline and a shadow that `TruncatedText` uses, each note under its own time; it is not focusable, so a tap outside closes it and still reaches whatever it landed on — a tap on another icon opens that note at once. The tap that closes it is read at **press**, as in `TruncatedText`, because the popup's `ACTION_OUTSIDE` and the canvas's tap race; a viewport change closes it too, since the icon has moved out from under it. The tap goes through `detectTapGestures` on the Canvas with a `NoteTouchSlop` of 8 dp around the icon; there is no per-icon composable; `DayChart` owns the open note itself (`shownNote`) and draws the popup inside its own `Box`, so the card and the full-screen dialog need no plumbing for it. **The Canvas carries semantics**: a `contentDescription` built by `chartDescription()` (count, temperature and humidity ranges, notes, plan batches — Compose-free, pinned by `BatchAnalyticsTest`) and one `CustomAccessibilityAction` per note, so TalkBack can open a note without finding a 13 dp glyph.
- **Opened from the incubator's measurement sheet, the chart also draws every batch's plan.** `IncubatorMeasurementSheet` passes `planLinesOf(state.recipients)` — the same selected targets `averagePlan` is computed from, so a batch unticked in «Справка» leaves both the target and its line — and `analyticsOf(measurements, plan, planLines)` carries them as `DayAnalytics.planLines` (`ChartPlanLine`: label, temp, damp; a line is kept only for a quantity that was actually **measured** that day — a temperature plan on a day with humidity readings alone has no axis to lie on and is dropped, so neither the chart nor the legend promises a line that is not drawn). Each batch takes a colour from `DesignPalette.ChartBars` **by position**, as the species bars do; its temperature plan is a dashed horizontal on the temperature axis and its humidity plan one on the humidity axis, each labelled at its right end with the value and unit («37.8°», «55%») in the batch's colour — the unit is what tells the two lines of one batch apart, since the colour is per batch and the axes differ; **one label per distinct value**, because two batches of one species on the same day ask for the same plan, their lines coincide, and two labels in two colours on top of each other read as neither. The plan values enter `niceAxis`'s range, or a plan above every reading would sit invisibly beyond the top gridline; but a series exists only for a quantity that was actually measured, so a plan alone never conjures an axis. The legend gets a third row, «план:» followed by the batch names in a `FlowRow` (names are the user's, capped at 150 dp with an ellipsis). **The batch sheet passes no lines and its chart is unchanged** — one batch has one target, and it already stands in the tiles.

## The candling sheet

**Candling is a `ModalBottomSheet`, not a navigation destination** — `ui/batch/CandlingSheet.kt`.
It used to be a route, `Candling/{day}/{type}`, and going there closed the batch: you had to
part with it at exactly the moment its eggs were in your hands. Now it lies over the batch
the way `BatchAnalyticsSheet` does, and closing it returns the same schedule day. There is
no `CandlingDestination` any more and nothing in `InventoryNavGraph` for it; the ids arrive
as parameters and go into `CandlingViewModel.load(batchId, day, type, stage)`. **The stage
arrives from the host, not computed here**: the batch sheet already holds the catalog
that knows a custom species' candling days, and a second read of the database for one
integer would only add a frame in which the title says the wrong ordinal.

One host, the thing that opened it: `BatchDetailSheet` — the «Обзор» button and a schedule
day card. It reports the original `"Переход в Овоскопирование"` AppMetrica event
(`Events.OPEN_CANDLING`) at the point of opening; that used to be the nav graph's job.
`BatchScreen` was a second host until the full-screen schedule was removed. **The species
now travels as `mapOf("Вид" to state.type)` rather than as a bare second argument**: that
overload takes a JSON string, so a plain species name was never valid JSON and AppMetrica
dropped the value without saying so — the event has been arriving parameterless for as
long as it has existed. The name is unchanged, so the series stays comparable; only the
value it was already supposed to carry now actually arrives.

**Recording the candling reports `Events.CANDLING_SAVED` («Овоскопирование записано»),
from `CandlingViewModel.save`** — вид, день, этап, отбраковано, осталось, and a «Правка»
flag, since a second save for the same day overwrites the first rather than adding a
candling. It is a funnel step in its own right: until it existed, only *opening* this
sheet was counted, so an abandoned sheet looked exactly like a recorded result.

It has **no mockup** — it is built out of the other sheets' pieces (drag handle, `SheetHeader`,
white cards at radius 22, Fraunces headings) so it does not read as a different app.

- **The sheet's shape follows how candling is actually done**: an egg in one hand, the
  phone in the other, in a darkened room. That is why the content column is `fillMaxHeight()`
  with «Фонарик» and «Завершить» in a fixed row under the scroll rather than at the end of
  it — they are the only two things needed at that moment — and why the instructions are
  numbered steps rather than a paragraph: they are performed one at a time, looking away
  at the egg in between. That row needs no navigation-bar padding of its own: `ModalBottomSheet`'s
  default `windowInsets` already include the bottom system bars.
- Reading order is picture first, text after: the picture is what the egg is compared
  against and the reason the sheet was opened. Then «Как проводить» (white, an
  instruction), then «Что важно помнить» (warm `SpeciesTileSelected`, because those are
  the things that ruin a clutch, not steps).
- **The reference pictures are rendered photos — `img_candling_1/2/3.jpg` in
  `drawable-nodpi` — one per stage, not per species.** They replaced fourteen PNGs that
  were only three distinct images between them (see the species-knowledge note above),
  and the first redraw fixed a real bug on the way: quail day 6 showed `quail2`, the
  *third*-stage picture, because both quail days pointed at one file. After that they were
  flat vectors; the owner asked for something that looks like what a candler actually
  shows, so they are now generated by `tools/CandlingImages.java` (plain JBR, no Gradle,
  fixed seeds, so a rerun reproduces them): an egg on a lamp in a dark room, its colour
  computed as Beer–Lambert absorption per channel through shell, albumen, tissue and blood
  — whatever is denser reads darker and redder, as through a real shell — plus shell
  mottling, branching vessels, the sinus terminalis ring on stage 1 and bloom around the
  egg. All three share one egg outline and the air cell grows from stage to stage.
  **`drawable-nodpi` is load-bearing**: in plain `drawable` a 1000 px JPEG counts as
  1000 dp and is decoded about three times larger on an xxhdpi screen. The card's frame is
  `CandlingPhotoBackground`, the photos' own background, so the side margins `Fit` leaves
  continue the dark room. The old stage-1 vector survives as `ic_candling_mark` — the
  tinted column icon of the schedule table, which needs a vector.
- The stage card carries **no heading of its own** — «Овоскопирование» is already in the
  sheet header, and «Первое овоскопирование» directly under it read as a stutter. The
  ordinal moved into the caption line beside the day and the species.
- **The torch is `CameraManager.setTorchMode`, which needs no permission since API 23** —
  so there is no `CAMERA` line in the manifest and no runtime prompt, and there must not
  be: a candling sheet asking for camera access reads as something else entirely. It
  picks a back-facing camera with a flash (a front "flash" is screen glow on many phones
  and `setTorchMode` silently does nothing on it), swallows `CameraAccessException` back
  into the off state rather than crashing mid-candling, and **turns itself off on dispose
  and when the result dialog opens** — a torch left on is a dead battery and a hot flash
  in a pocket. On a device with no flash the button greys out instead of vanishing.
- **«Завершить» opens the result dialog: было — отбраковано — останется.** Three figures
  side by side rather than the single number typed, because the point of a cull is how
  many eggs are left, and that has to be visible before saving, not after; «Останется»
  recomputes while typing.
- **«Было» is not «Заложено» — it is `eggAll` minus the culls of every *other* candling.**
  That is also the input ceiling: at the third candling you cannot cull eggs that the
  first one already removed. `CandlingViewModel.updateRejected` clamps the *value* rather
  than refusing the keystroke — typing «50» against forty eggs becomes «40», because a
  field that silently ignores input looks broken.
- **One field, one number** — a batch has one breed (a tray of two is two batches, each
  candled on its own), so there is nothing to divide the cull by, and
  `CandlingState.rejected` is a single string clamped to `eggsBefore`.
- **Zero is a result too**, so the save button does not grey out on an empty field:
  «candled, nothing wrong» is a record, not the absence of one. Saving closes the sheet:
  the candling is over, and the batch underneath picks the number up through its own
  `getCandlings` flow.
- Re-opening a day that already has a result loads the number back into the field and
  says so in both the stage card and the dialog; saving overwrites the row rather than
  adding a second (the unique index on `idPT` + `day` enforces that in the database).

## Dismissing a sheet: the swipe keeps the draft, the cross discards it

A bottom sheet is pulled shut with the same downward drag that scrolls its contents, so
closing one by accident is easier than closing it on purpose — and every form in this app
lives in a sheet. **A sheet dragged down keeps what was typed in it**: opened again, it
shows exactly the input it was collapsed with. **The cross in the header is a refusal**
and throws the input away; so does leaving the screen. Saving throws it away too, which
is the case that is easy to miss: without it, «Новый инкубатор» pressed twice in a row
would open on the incubator just created.

The input itself never moves — it is where it always was, in the form's ViewModel, which
belongs to the screen and outlives the sheet. What is new is one bit of bookkeeping,
`design/components/SheetDraft.kt`: `claim(key)` answers «fill this form from scratch or leave
it as it is», and the sheet's `LaunchedEffect` calls its `load` only on a `true`. The
`key` is everything the form's content depends on — the batch id, the candling day —
because the draft of batch 7 is no draft at all for batch 8.

- **`rememberSheetDraft()` belongs to the composition of the *screen*, not of the sheet.**
  That single placement is what makes the whole rule work: the sheet's composition is torn
  down when it closes, so a draft held there would die with it, and the screen's is torn
  down when you navigate away, which is precisely when the input is supposed to go. No
  lifecycle observer and no navigation callback is involved. For a sheet standing on
  another sheet — the species constructor over the batch form, candling over the batch —
  «the screen» is the sheet underneath: close it and you have closed what stood on it.
- **One draft per ViewModel, not per call site.** `IncubatorScreen` opens `AddBatchSheet`
  twice, for creating and for editing, and both share `batchFormDraft` — they share an
  `AddBatchViewModel`, and two drafts over one state would each promise to keep an input
  that the other had already overwritten.
- **`onDismissRequest` keeps, the header's `onClose` discards.** They are the same
  callback everywhere else in Compose, and separating them is the entire feature: the
  drag, the scrim and the back press all arrive as `onDismissRequest` and all leave the
  draft alone.
- **Two of the five sheets re-read the database anyway.** `AddIncubatorSheet`,
  `AddBatchSheet` and `CustomSpeciesSheet` are forms end to end — the draft *is* the
  truth, and reloading would overwrite it. `BatchDetailSheet` and `CandlingSheet` are
  views with a form inside: while they sat collapsed the batch could have been finished
  from the card menu, or eggs culled on another candling day, so their `load` runs every
  time and takes `resetForm` / `resetInput` to say whether the typed part goes with it.
  Candling re-clamps the kept number against the fresh ceiling instead of trusting it.
  `BatchAnalyticsSheet` takes no input at all and has no draft.
- **The draft survives a rotation and not a process death**, and one line decides both:
  the `Saver` writes the marker into the `Bundle` only when `isChangingConfigurations` is
  true. The input rides in the ViewModel, which survives exactly a configuration change;
  a marker that also survived a process killed in the background would meet a brand-new
  empty ViewModel, and the form would open blank and stay blank, because a live marker is
  the one thing that stops `load` from running.

## Loading: "not read yet" is not "nothing there"

Every screen fed by a `StateFlow` starts on `initialValue = SomeUiState()` — an empty
list and a row of zeros — and until this change nothing on screen distinguished that
first value from a real answer. The start screen greeted a farm of five incubators with
«Добро пожаловать!», an incubator with a dozen batches said «Закладок пока нет», and the
batch sheet opened on a summary of zeros over an empty measurement log. Every one of
those is a *statement*, made before there was anything to state, and the reading it
invites is that the data is gone.

The fix is one flag per state and one composable. `StartUiState.loading`,
`IncubatorUiState.loading` and `AnalyticsUiState.loading` default to **`true`** — that is
literally the flow's initial value — and are set to `false` inside the `combine` block,
where by construction every source has emitted. The sheets already had the equivalent
(`BatchDetailUiState.loaded`, `CandlingUiState.loaded`), it was only used to guard
writes; `AddIncubatorViewModel.loading` and `AddBatchViewModel.loading` were added
beside `scheduleReady`, which answers the narrower question about the day table.
**The two form flags are true only while editing**: creating fills the fields on the
spot, and a spinner over a form that is about to be blank promises something.

`design/components/LoadingState.kt` holds what that looks like. `LoadingBox` fills the space
the content will take and centres `LoadingSpinner` in it; `statValue(loading, n)` is the
figure tiles' «—».

- **The spinner waits 150 ms before appearing** (`SPINNER_DELAY_MILLIS`). The database is
  on this phone and the usual answer arrives faster than the eye catches it; a wheel that
  flashes for two frames reads as the screen twitching, not as loading. The *box* is
  there from the first frame, so nothing jumps when the answer lands — only the wheel
  inside it is delayed.
- **A dash, not a zero, in the figure tiles.** «0 · Активных закладок» in the largest type
  on the incubator's green header is an assertion about a working device; a dash asserts
  nothing and needs no more room.
- **The loader replaces the empty state, it does not stand beside it.** `StartScreen`
  checks `uiState.loading` *before* `cards.isEmpty()`, `BatchesTab` returns early before
  it has even built its filter chips (there is no list to filter yet), and
  `AddBatchSheet`'s schedule page turned its silent `if (!ready) return@Column` — which
  left a blank space indistinguishable from «режима нет» — into the same wheel.
- **The batch sheet's header falls back to «Закладка»** while `state.title` is empty. A
  headerless sheet reads as broken, and a batch really can be saved without a name, so
  the fallback is right in both cases.
- `CandlingSheet` is the one place the loader is not a wheel in the content: its content
  is static prose that needs no reading from the database. What does need it is «Было N
  яиц», which is the ceiling on the cull, so **«Завершить» is disabled and holds a small
  `LoadingSpinner` until `state.loaded`** — opening the result dialog earlier would offer
  a tray of zero eggs.

Verified on an Android 15 emulator by temporarily wrapping the `:data` repository's flows
in `onStart { delay(2500) }` — the only way to see these states at all, since Room answers
in a frame or two. That hack does not belong in the repository and was removed; add it
again the same way if these screens ever need re-checking.

## Cards standing side by side are always the same height

`TileRow` + `RowScope.tileWeight()` in `design/components/TileRow.kt` is **the** way to put two
or more cards in one row. A plain `Row` measures each child by its own content, so the
moment one tile's caption wraps to a second line its neighbour ends 10–20 px higher and the
row reads as having slipped. `TileRow` is a `Row` at `Modifier.height(IntrinsicSize.Min)` —
the height of the tallest child — and `tileWeight()` is `weight(w).fillMaxHeight()`, which
is what hands that height down. **Both halves are needed**: without `fillMaxHeight` the tile
keeps its own height inside a taller row and simply leaves a gap underneath, which is why
the weight and the fill live in one function instead of two modifiers at the call site.

Everything that stands in a row of tiles goes through it: the start screen's two stat cards,
«Доход» / «Расход» and the four `MetricCard`s of «Финансы», the four summary tiles of
«Статистика», the analytics grid and «Итог по замерам» (`StatRow` is now a thin wrapper over
it), «Температура» / «Влажность» and the turn/airing counters in the batch sheet, both price
summaries, and the guide's demo tiles. **A row whose tiles have a fixed height needs none of
it** — the mode pills (63 dp) are already equal, and wrapping them would only add an
intrinsic-measurement pass. The species grid used to be in that company and has left it:
its tiles grow under a long name now (`heightIn`, see the batch form), so the rows go
through `TileRow` like everything else.

Which also means: the caption-length gymnastics that used to hold a row level (`maxLines = 1`
so a neighbour would not grow, `heightIn(min = …)` sized to one known string) are no longer
what keeps it level. Where those limits survive — the counters' plan line, the analytics
tile's 66 dp floor — they stay for their own reasons, stated where they are written.

## Every number on screen carries a thousands separator

`formatCount(n)` in `design/components/NumberFormat.kt` is the rule and the only
implementation of it: «1 200», «12 400 яиц», never «1200» or «12400». It is not a money
rule — a four-digit figure without the gap reads as a code rather than a quantity, and
«1200» and «12000» on a half-width tile differ by one digit in the middle, so the
разряды have to be counted by eye in exactly the place a number is glanced at. A
household of a couple of thousand eggs is ordinary, so this is not a rare case.

- **Two of the three ways to print a number already go through it**, and that is the
  point of the arrangement: `plural(count, …)` — the most common way to put a figure in
  front of a noun — and `formatMoney` / `formatMoneySigned`, both in
  `incubator/IncubatorTabParts.kt`, call `formatCount` themselves. A caller has to
  remember the rule only where a number stands alone without a noun: the tiles, the
  chart labels, the hint denominators, `statValue`. The typographic minus («−», not a
  hyphen, which is lost among monospaced digits) lives in the same one function.
- **The separator is a non-breaking space, written as a ` ` escape rather than as
  the character.** From an ordinary space it is indistinguishable in the source, and one
  editor normalising whitespace would silently switch the rule off — visible only later,
  in a narrow cell on someone else's phone, where «12 400» breaks into «12» with «400»
  under it. `NumberFormatTest` in `app/src/test` asserts that exact codepoint, which is
  the only way such a substitution is ever caught.
- **The exceptions are the figures that are not quantities**: the incubation day («День
  15/21»), the candling stage, a year, a time, the app version, the character counter in
  the name field. None of them reaches four digits, and a separator inside them would
  read as a mistake.

## A figure in a tile is one line, and a truncated one shows itself on tap

`MetricCard` (both tabs, so both the incubator screen and «Аналитика»), the «Доход» /
«Расход» `MoneyTile`s and the balance render their value through `TruncatedText` with
`maxLines = 1`.

- **Because tiles stand two to a row and share one height** (`TileRow`): wrapping
  «1 234 567 ₽» onto a second line would push the label and the denominator down in
  *both* tiles of the row, so one large hatchery would skew a page everyone else reads
  level. Truncation keeps the row flat at any sum.
- **And a truncated figure is tappable, because what gets cut off a number is its low
  digits, i.e. its precision.** The tooltip is the same `TruncatedText` the start
  screen's incubator names use — moved out of `StartScreen.kt` into
  `design/components/TruncatedText.kt` when the second caller appeared, since two copies of
  that gesture handling would have parted ways at the first fix. Everything stated there
  about it still holds: the tap toggles, visibility is read at the press to survive the
  race with the popup's own `ACTION_OUTSIDE`, `enableUserInput = false` replaces
  Material's long-press gesture, and the colours come from the app palette rather than
  the inverted `inverseSurface` pair. `maxLines` is its one parameter that differs by
  caller, and it follows the place rather than the kind of text: two lines on the start
  screen's card, where a name that grows pushes only its own card down, and one wherever
  the line shares its height with something else — a figure in a tile, and all of the
  incubator header (the device's name, «бренд · модель», and each of the three figures),
  which stands above the whole screen and pushes everything on it. **`textAlign` is the other one, and passing it also makes the inner `Text` fill its width** — the caller's `modifier` lands on the `TooltipBox` wrapper, so a `fillMaxWidth()` there left the `Text` inside content-sized and pinned to the left, and `TextAlign.Center` had nothing to centre in: the four `ModePill`s of the batch sheet («Завтра — День N» and every card of «Расписание») read left-aligned for exactly that reason until the fix went into `TruncatedText` itself rather than into the pill.
- **Every clipped name the user typed shows itself the same way.** The rule is now the
  app's, not the start screen's: a species, a breed, a batch — anything a person named
  themselves has unbounded length, and what a clip takes off is precisely what tells two
  of them apart («Ломан Браун» from «Ломан Браун белый», «Куры 2» from «Куры 2 весна»).
  The places: the chart legend's species row and its expanded breed rows; `EfficiencyRow`,
  which serves both the species line and the breeds under it; the batch title on the
  incubator screen's card; and the title-plus-subtitle pair of a row in «История выводов»
  and in the «Финансы» batch breakdown — the subtitle goes through it too, since it is
  where the breed is printed. **On a row that also does something, the tooltip wins the
  tap** — the same trade the start screen's card makes, and only while the name is
  actually truncated: the rest of the row still expands the breeds, or opens the batch.
- **The batch sheet's day cards and counters go through it too.** On an enlarged system
  font a day card on «Расписание» reads «37…», «ВЛАЖ…», «ПРОВ…» and «14 сент. · сегодня ·
  6 заме…» — every one of them the thing the card exists to show, and none of them can
  wrap, because the four pills share a fixed 63 dp and the caption shares a row with the
  chevron. So `ModePill`'s label and value, the day caption, and the «план …» / «осталось …»
  lines of the «Перевороты» / «Проветривания» tiles on «Обзор» are `TruncatedText` with
  `maxLines = 1`. `ModePill` is shared with «Завтра — День N», so that block gets it for
  free. Tapping a clipped pill shows the value and does **not** expand the day — the same
  trade as the start screen's card, and only while the text is actually clipped. For the
  centred pills the anchor is `fillMaxWidth()` with `textAlign = TextAlign.Center`, the one
  parameter added to `TruncatedText` for this: a line stretched to the width of the pill so
  its ellipsis can land would otherwise sit against the left edge.
- **`Modifier.weight()` must never be handed to `TruncatedText` — it is dropped in
  silence.** `TooltipBox` draws `Box { WrappedAnchor(modifier = modifier …) }`: the outer
  `Box` takes no modifier, so the weight lands on a nested node where `RowScope.weight`
  means nothing, and the text then claims whatever width it asks for — precisely the
  behaviour it was put there to stop. In a row, wrap it: `Box(Modifier.weight(1f)) {
  TruncatedText(…) }`. This is the same trap the schedule table's header column widths
  already fell into, one composable up.

## Russian plurals after a numeral

`plural(count, one, few, many)` in `incubator/IncubatorTabParts.kt` is the only correct
way to put a noun after a number in this app: it handles 11–14 (which take the *many*
form despite ending in 1–4) and 21 (which returns to *one*). Several strings used to
hardcode one form — «22 яиц», «1 мест», «по 1 яйцам» — and the giveaway was that they
stood next to correctly declined ones: `sliceFooter` declined «птенца» and left «яиц»
fixed in the very same line. They are now all routed through the helper — the last one to
go was the egg count on the batch card in `IncubatorScreen`, which is to say the most
looked-at line in the app: «2 яиц», «22 яиц», «1 яиц», assembled by hand while eighteen
other call sites went through `plural`. The stock
triples: eggs are `"яйцо", "яйца", "яиц"` (dative `"яйцу", "яйцам", "яйцам"`), capacity
is `"место", "места", "мест"`. Reach for the helper whenever a number is followed by a
noun, including in new copy — it also prints the number itself through `formatCount`, so
going through it is how the separator rule above gets honoured without anyone
remembering it.

## The app menu: profile, settings, about

`ui/menu/` holds the three sections behind the hamburger icon in the start screen's
header — «Аналитика», «Настройки», «О приложении». All three are ordinary navigation
destinations, not sheets: their content (analytics, an export flow, a block of contacts)
does not fit the sheet idiom the forms use.

**They replaced the old info icon and `InfoBottomSheet`.** That sheet showed
«Инкубатор v1.00» and a button into the VK group — exactly what «О приложении» now says,
and more. Two icons in one header leading to the same place raise the question of how
they differ, so the info one is gone. The AppMetrica event `"Информация"` moved with the
content and kept its name; `"Переход в группу"` likewise still fires from the VK button,
now inside «О приложении».

`MenuParts.kt` carries the shared silhouette, and it is deliberately the incubator
screen's: green `HeaderSurface` header, a cream sheet pulled 17 dp into it with 24 dp top
corners, white cards inside. The menu is not a separate world — it is the same data at a
different scope — and a second visual language here would read as a different app. That
extends to the status bar: `MenuScreen` paints it `HeaderSurface` with light icons and
hands the top system inset to `MenuHeader`, exactly as the incubator screen does.
`MenuScreen` scrolls its content by default; `scrollable = false` is passed by «Аналитика»
alone, whose pager pages scroll themselves — an outer scroll on the same axis would break
both their measurement and the `weight(1f)` the pager needs. Turning it off also drops the
shared padding, which each page then sets for itself; otherwise the tab pill would sit
inside the content margins. Cards, headers and metric tiles are imported from
`incubator/IncubatorTabParts.kt` rather than re-declared.

- **«Аналитика» reuses `StatsTab` and `FinanceTab` whole.** Both now take
  `IncubatorStats` / `IncubatorFinance` plus a `TabScope`, instead of `IncubatorUiState`,
  which is the entire change that made the reuse possible. The numbers come from the same
  `:domain` functions the incubator screen uses, fed every batch and
  `incubators.sumOf { it.price }`; a parallel «same sums, but over everything»
  implementation would drift and hand the farm two answers to one question. `TabScope`
  holds the six captions that genuinely differ — «инкубатор + яйца» against «инкубаторы +
  яйца», «Стоимость инкубатора» against «Стоимость инкубаторов», and the payback sentence,
  which is its own string rather than a title plus a verb because the number changes the
  verb («окупился» / «окупились»).
- **The header answers one question only: how big is the farm.** One subtitle line,
  «3 инкубатора · 2 активные закладки», under a fixed «Аналитика» title. A line rather
  than a pair of large tiles: these numbers are scale, not results — the backdrop the
  results are read against. The header used to lead with the owner's name and a balance,
  and both moved out: the name because the section is
  analytics, not a profile, and the balance because a figure that can go negative read as
  a verdict when it stood alone at the top, whereas on the «Финансы» tab the same sum sits
  next to the note saying how much money is still in the incubators. Totals belong where
  their denominators are. The line drops its batches half at zero and disappears entirely
  when there are no incubators: «0 инкубаторов» under a section name is a reproach, not
  information.
- **The tab is «Статистика», not «Аналитика».** It would otherwise share a name with the
  screen containing it, and it matches the incubator screen's tab strip, which is the same
  content at a narrower scope.
- **The owner's name is capped at 20 characters** (`NameMaxLength` in `AnalyticsScreen.kt`),
  and the cap is on input rather than on save — `NameDialog`'s `onValueChange` takes the
  first twenty and drops the rest. It is the one free-text field whose value is printed
  where the width is decided by something else: `NameCard`'s `MenuRow` title. A name of
  any length would push «Владелец хозяйства» around and ellipsize into saying nothing.
  Truncating rather than refusing the keystroke is the same choice
  `CandlingViewModel.updateRejected` makes with its ceiling: a field that silently
  ignores a paste looks broken, whereas a paste that arrives short shows what happened.
  A longer name already in the database — from an import, or from before the cap —
  is left alone until someone edits it. **A «12 / 20» counter under the field is the
  other half of that**, `DesignType.Micro` right-aligned: without it the twenty-first
  character simply fails to appear and the field reads as having stopped responding.
  **At the limit it turns accent green, not red** — nothing went wrong, the name is
  exactly as long as it fits, and red in this app means a loss.
- **The placeholder is «Иван Иванов».** A placeholder is an example of the *shape* of the
  answer, and a real-looking name — the author's own was there — reads as a value
  somebody already entered, the same trap the incubator form's «Rcom, Блиц…» brand
  examples fell into.
- **«Свои виды птицы» is the second card, and it is where a custom species is managed.** Creating one usually happens from the batch form's «Свой вид» tile, but a list, editing and deletion need one home, and the place for things common to the whole farm is this screen. Rows are `MenuRow`s — the name, then «21 день · 3 овоскопирования» (`customSpeciesSummary`, through `plural`) — tapping one opens the same `CustomSpeciesSheet` for editing, and a bin on the right asks to delete. **That bin is neutral grey, and the red waits in the dialog.** It was red, one per species, and on a screen set otherwise in calm dark-on-cream two or three red icons were the brightest thing on it: the eye found the delete buttons before it found the list. Red means «no way back» in this app, and it belongs one step from that, on the confirm button — which is still red. A bin says what it does without any colour at all. **Deletion is refused while a running batch uses the species**: `SettingsViewModel.requestDeleteSpecies` first counts them (`countActiveBatchesOfType`) and `DeleteSpeciesDialog` then either asks «Удалить вид?» or explains why not, with a single «Понятно» — offering «Удалить» beside «нельзя» would promise what will not happen. Finished batches do not object: their plan is baked into their own `Value` rows and their term is over, and the dialog says so, since «what happens to my old batches» is the question the bin raises. **Adding one is a dashed `DashedAddButton` under the list, not a sixth `MenuRow`**: as a row with a chevron it was built exactly like the species above it — same title, same caption, same arrow — and differed only in describing nothing, so the list read as having one entry too many. The dashed button is what this app says «add another» with everywhere else: the reminder in the batch form, a breed, a day in the species constructor, and the «Свой вид» tile in the species grid, which is dashed for the same reason. Its caption («Название, дни, режим и овоскопирования») went with the row — it listed what the constructor asks for, not what the press does. The sheet is hosted here exactly as the forms are hosted by their screens, keyed by `speciesSheet` (`-1` closed, `0` new, an id to edit) in `rememberSaveable`. **Folded, the list shows two species (`VisibleSpecies`) and the rest wait behind «Показать все (N)»**: the card stands in the middle of a scrolling page, and a dozen rows would push «Оформление», the database transfer and «Удалить все данные» off the screen for a list opened once a season. Two is enough to show that the list exists and what a row looks like; whoever wants a particular species presses the button. That button is `ShowAllToggle` in `ui/components/ScheduleTable.kt` — the batch sheet's measurement-history toggle, moved out of `BatchDetailSheet.kt` when this second caller appeared — and it appears only when there is something behind it (`species.size > VisibleSpecies`). The count is in the label because from a folded list nothing says how many more there are. The rows sit in a `Column` with `animateContentSize`, the expansion state in `rememberSaveable`.
- **«Температура» is a pair of `ChoiceChip`s under «Оформление», «Валюта» a dropdown, and the chip is the batch filter's, moved.** `BatchFilterChip` in `IncubatorScreen.kt` became `design/components/ChoiceChip.kt` (same 34 dp pill, white with a hairline, accent when selected; the icon is now optional) the moment a second «one of several» appeared — two ways to say «выбрано» in one app would read as two different actions. Chips rather than the theme's `SlidingTabSwitcher` because that one demands an icon per tab, and telling °C from °F in a 15 dp glyph means drawing letters — here the letters *are* the choice; `ChoiceRow` is the same wrapping `FlowRow` as the filter row. **Currency is `SheetDropdownField` in `SheetForm.kt`** — a `SheetPickerField` with the `ExposedDropdownMenu` of `SuggestingSheetTextField` under it, the closed-list twin of that free-text field: six options as chips took three rows and half the card for a choice made once, while a list costs nothing closed and shows all six open. The picker's own `onClick` toggles it and the box's `onExpandedChange` is a no-op on purpose — with both live, one tap toggled twice and the menu never opened. The selected row is painted accent, no tick. Both read «знак · название» («°F · Фаренгейт», «₸ · Тенге»), and the `Note` line under each card — italic, see below — states the one thing a person will otherwise assume wrongly: temperatures are *converted* everywhere (the display and the input fields alike) and the stored numbers do not change, while for money only the sign changes and nothing is recalculated by any rate. The rules behind that — Celsius in the database, conversion at `ValueFormat`, the lossless two-decimal Fahrenheit, `LocalUnits` for composables and `AppSettings.temperatureUnit` for the three ViewModels that hold temperature strings — are in the root `CLAUDE.md` under `settings/Units.kt`. **What a °F switch changes on screen**: every «T°C» caption becomes «T°F» (`TemperatureUnit.fieldLabel`), the schedule table's temperature tooltip carries the symbol, the temperature field accepts three digits before the point (`integerDigits`), the deviation bar's ±1.5° becomes ±2.7° and the thresholds scale with it so «небольшое отклонение» is the same 0.5 °C either way, the day chart's axis is built on the converted values (nice ticks in Celsius are not nice in Fahrenheit), and «Разброс» on the analytics tiles goes through `asTempDelta` — a spread is a difference and must not gain 32. Verified on an Android 15 emulator: a target of 37 °C reads «цель 98.6°», a reading typed as 99.5 lands as +0.9° · небольшое отклонение, the batch form's table shows «100.22» in the temperature column without clipping, and «Финансы» prints «+13 037 $» after picking the dollar.
- **«Настройки» offers one notification switch and a door into the system settings, and
  no times.** Reminder times and their texts belong to the batch that owns them; repeating
  them here would create a second place to change the same thing and an unanswerable
  question about which wins. The switch and the system permission are shown as separate
  rows because they are two different «no»: the switch is the user's own decision,
  revocable on the spot, while a withdrawn permission is the system's refusal, and a
  switch left on above it would be promising notifications that will not arrive. **The permission is re-read on every resume** (`LifecycleResumeEffect`), which is what `lifecycle-runtime-compose` was added to the version catalog for: it is granted in the system settings — another app — and coming back changes no state of ours, so a value read once would still say «не выдано» over a permission just granted, and the user would conclude it had not worked.
- **The import flow asks before the file picker, not after.** A warning about losing data
  has to stand before someone goes looking for a file — consent collected after a long
  search is collected from someone who has already committed and stopped reading. **Which
  is also why its button is no longer red and no longer says «Загрузить из файла».** The
  press replaces nothing by itself: it opens the warning, and only the warning's «Выбрать
  файл» reaches the picker — so the red belonged to the dialog's confirm button, where it
  still is, and not to the ordinary act of moving a farm onto a new phone. It reads
  «Восстановить из копии» now, the pair of «Сохранить копию» above it: the old label named
  the file, and nobody comes to this card looking for a file. What replaces the colour is
  the row's own description, which states in words that the current data will be replaced.
  **The transfer itself does not belong to the screen** — it lives in
  `settings/DataTransferController.kt`, whose scope is the application's. Putting it in
  `viewModelScope` hid a crash you can only find by using the app: press back a second
  after picking the file, and `importDatabase` — a plain blocking function with no
  suspension points — still ran to completion and still swapped the database, but the
  result had nowhere to go, the ViewModel being gone. Database replaced, connection to
  the old one closed, nobody left to ask for the restart, and the app carried on until
  the first screen that reads the database, i.e. until it crashed. **The restart is
  therefore unconditional and is announced, not offered**: a «I'll stay» button would
  promise something the app cannot deliver. The dialog exists so the person can read why
  it is about to close; the controller kills the process a couple of seconds later.
  A
  successful import ends in a dialog that cannot be dismissed, only «Перезапустить»: the
  old database connection is already closed, and the screen behind it describes data that
  no longer exists. **A failed one that got that far ends the same way** — `TransferState.FailedNeedsRestart`, raised from `ImportResult.RestoredNeedsRestart` — because «данные на месте» is true of the disk and false of the running app, and «Понятно» would drop the user onto screens that crash. `restartApp` calls `exitProcess(0)` unconditionally, even when `getLaunchIntentForPackage` returns null: staying alive is the worse of the two outcomes.
- **«Сохранить копию» asks where, instead of guessing.** The button opens
  `ExportChoiceDialog` with two answers to two different questions: «Сохранить на
  устройстве» is the system document picker (`CreateDocument`), for moving a farm to a
  new phone or keeping a copy to hand, and «Отправить в другое приложение» is an
  `ACTION_SEND` chooser, for mail to oneself, a messenger, a cloud. Sending a copy off
  the phone has to be a press of its own, never a side effect of saving one. The two
  buttons live in the dialog's **body**, not in its confirm/dismiss slots: those lay
  buttons out in a row, and two long Russian labels there either shrink to nothing or
  wrap unevenly. The shared file is a fresh copy written into `cacheDir/exports/` and
  handed out through a `FileProvider` (`${applicationId}.fileprovider`, paths in
  `res/xml/file_paths.xml`, which lists that one cache directory and nothing else) —
  the working database is neither exportable from a private directory nor safe to hand
  over open, without the WAL checkpoint that `exportDatabase` performs. The directory is
  emptied before each write: the file name carries a date, so a month of sharing would
  otherwise be a month of copies sitting in the cache. **The chooser is launched by the
  screen, not the controller** — an intent needs an activity — so `shareCopy` ends in
  `TransferState.ReadyToShare(uri)`, which a `LaunchedEffect` consumes and clears at
  once; a state left standing would reopen the chooser on every return to the screen.
  `FLAG_GRANT_READ_URI_PERMISSION` is not optional: a `content://` URI carries no rights
  of its own, the intent grants them.
- **«Удалить все данные» is its own card, last on the screen and red, and it is three things only**:
  the «Удаление данных» title, one sentence saying every piece of data goes for good, and the
  red button. Keeping it in «Управление данными» would put it third in a row of buttons that
  merely move a file around. The detail — what exactly disappears, the archive included, and
  «save a copy first» — lives in `ConfirmWipeDialog`, whose buttons are deliberately unequal:
  the red «Удалить всё» in the confirm slot, «Отмена» in the accent green of safe actions.
- **«Управление данными» is a title and two rows, «Экспорт» and «Импорт», each with an «i»
  right after its heading** (`TitleWithHint` → `HintIcon` from `design/components/SheetForm.kt`,
  the icon half of `FieldLabelWithHint`, split out for this) and its button under it. What each
  does — and, for the import, that the current data will be replaced — is in the hint rather than
  in two-line descriptions that made the card twice the height of its buttons; the replacement
  warning is still repeated in `ConfirmImportDialog` before the file picker.
- **A line at the foot of the screen says the data never leaves the phone.** It belongs
  here rather than in «О приложении» because this is the page that raises the question:
  having just read «экспорт», «отправить» and «удалить всё», one naturally asks where all
  of it is kept. There is no server and no account, and the only way incubators and
  batches leave is the share button. **It promises that about the data, not about the
  app, and the wording has to stay that narrow.** It first read «Приложение не отправляет
  их никуда и работает без интернета», which was simply untrue: `InventoryApplication`
  initialises AppMetrica, and events — screens opened, saves, these very buttons — go out
  over the network. A privacy claim that the app's own behaviour contradicts is worse
  than none, so the sentence now says only what holds without exceptions: the contents of
  the database never go into analytics, and only the user can carry them out.
- **«О приложении» asks the system for the launcher icon** — `packageManager.getApplicationIcon(packageName).toBitmap(192, 192)`, not `painterResource(R.mipmap.ic_launcher)`. That is not a preference: at `minSdk = 26` the id always resolves to `mipmap-anydpi/ic_launcher.xml`, which is an `<adaptive-icon>`; Compose parses every `.xml` as a vector resource and throws `IllegalArgumentException` on the first root tag that is not `<vector>`, so the screen crashed on open, identically on every device. Going through the package manager also renders exactly what the launcher shows — background composed with foreground, clipped to the OEM mask — which is a more literal reading of «текущая иконка приложения»: the user recognises the one they tapped, and a private copy would fall behind it. Version and release date come from `BuildConfig`
  (`VERSION_NAME` and the `RELEASE_DATE` field declared next to `versionName`), never from
  string literals here. The email button uses `ACTION_SENDTO` with a `mailto:` URI rather
  than `ACTION_SEND`, so only mail apps are offered — a chooser full of messengers under
  «написать письмо» is confusing — and the subject carries the version, since a report
  without one costs a second letter asking for it. All three addresses also appear as plain
  text rows: the buttons help whoever is on this phone, the text helps whoever writes from
  another. **The third address is the VK channel** (`VK_CHANNEL_URL`, event
  `"Переход в канал"`), and it is not the group: the group is where the птицеводы talk, the
  channel is announcements in one direction — which is why it has **no button** in the
  card that asks people to tell you something, and why the row in «Контакты» is the only
  way to it. The event moved onto that row rather than disappearing with the button, so
  the series stays comparable. Its row shows «Новости и обновления приложения»
  rather than the URL, because `vk.ru/im/channels/-239980765` is not an address anyone can
  copy off a screen from memory — the reason `VK_GROUP_LABEL` exists (a spoken form of the
  link) simply has no equivalent here. **The fourth is the Telegram channel**
  (`TELEGRAM_URL`, row «Канал в Telegram» under the VK channel, same reasoning — no button,
  announcements only), and unlike the VK one its address *is* speakable, so the row shows
  `t.me/my_ferma_app`. It reports its own event, `Events.OPEN_TELEGRAM`
  («Переход в Telegram»), not «Переход в канал»: that name already carries the VK
  channel's series, and two channels under one name could not be compared.
- **The паспорт card's rows right-align their value, and `TextAlign.End` is the half that
  is easy to leave out.** `MenuFactRow` hands the value `weight(1f)`, so it takes the
  whole width left over from the label; without the alignment every line of it sits at the
  left edge of that block, which for «Разработчик» — the one value long enough to wrap —
  meant the row read as having slipped out of line with «Версия» and «Дата выпуска» above
  it. `SpaceBetween` alone cannot do it: it positions the block, not the text inside it,
  and it has nothing to position once the block fills the row.
- **The «Рекомендуемые приложения» card (subtitle «Моё хозяйство — учёт животных, кормов и доходов фермы») — two rows, «Скачать в RuStore» and «Скачать в Google Play», each with the store's mark (`ic_rustore.png` / `ic_google.png`, monochrome, supplied by the owner) through the ordinary `MenuIcon`, tinted accent like every other icon on the screen — stands after «Контакты», just above the ad card.** Each opens its own AppMetrica tracking link of the farm app (`FARM_APP_URL_RUSTORE` / `FARM_APP_URL_GOOGLE_PLAY`, not store pages), so the farm's cabinet counts the transition per store. **Both rows are shown in every build, at the owner's request** — not chosen by `IS_RUSTORE_BUILD`: the store the incubator came from need not be the one the person uses. `Events.OPEN_FARM_APP_LINK` counts the taps on this side, with «Магазин». Its own card rather than a row in «Контакты», since those are ways to write to the developer and this is an app to install. It is shown in every build — unlike the store card below, it leads to another app, not back to the store this one came from. `FarmApp.STORE_URL` stays the target of «Обновить «Моё хозяйство»», which is about an app already installed.
- **The «Оценить приложение / Проверить обновление» card appears only in a build for
  RuStore** — `IS_RUSTORE_BUILD`, i.e. a `versionName` ending in «r»; see the root
  `CLAUDE.md` for the rule and for the three other places it switches off. Both rows lead
  into a store the app was not taken from otherwise, and the card between «Как
  пользоваться» and «Расскажите, чего не хватает» simply closes up. Both rows go through `AboutViewModel` (`AboutIntent.Rate` / `CheckUpdate`; the «Спрашиваем RuStore…» / outcome line is its state) — the screen no longer reaches into the container; links and mail stay platform intents opened by the screen.

## The guide: «Как пользоваться»

`ui/guide/` is the first thing a new user sees — eight swipeable pages: what an
incubator is, what a batch is, what the incubator screen's three tabs are for, what to
do every day, and then three pages for what came later — the QR code on the device, the
airing timer, and the hatch result with the calendar and «Моё хозяйство». **That fourth page is also where paging sideways is taught**, since nothing
on a pill switcher says so by itself, and it teaches it by being one. It is the start
destination while `AppSettings.guidePending` holds — **which includes the updating user,
not only the fresh install; what the two of them do not share is the incubator form after
it** (see the root `CLAUDE.md` for the flags) — and it comes back from «О приложении» →
«Как пользоваться» with `revisit = true`.
`GuideScreen.kt` is the frame and the copy, `GuideScenes.kt` the eight illustrations.

- **The illustrations are scenes, not pictures.** Each is built from the app's own
  parts — `MiniCard` is the incubator card, the species tiles are the batch form's, the
  measurement tiles are «Замеры за сегодня», and the tabs page uses the *real*
  `SlidingTabSwitcher` over a real nested `HorizontalPager`. A drawn illustration would
  promise an interface that does not exist; these show the one the user meets a minute
  later, and they follow the theme because they take every colour from `DesignPalette`.
  The figures in them are invented and the same for everyone — an example, not data.
- **Each scene takes `active` and plays its entrance from that moment** — the capacity
  bar fills, the schedule rows rise, the bell swings — where `active` is
  `pagerState.settledPage == index` gated by a one-frame `started` flag, not «composed».
  The flag exists for page one alone: it is settled from the first frame, and
  `animateFloatAsState` never animates the value it starts on. The pager keeps one neighbour built
  ahead (`beyondViewportPageCount = 1`), so a scene keyed on composition would play its
  whole entrance off screen. `appearFraction()` / `Modifier.rise()` are the shared shape
  of that entrance; a new scene should use them rather than its own tween.
- **The fourth page, «Инкубатор знает всё», is the incubator screen in miniature.** Its
  three demo cards are the three tabs — a running batch, the hatch figures, the balance —
  because «Статистика» and «Финансы» are indistinguishable as words and unmistakable once
  seen. **It replaced a page whose subject was swiping itself**, and with it went
  `SwipePlaces`, the card listing every pager in the app: a table of screens nobody had
  opened yet is a reference, and a reference in an onboarding page is read by no one. What
  it was there to teach the scene teaches by being swipeable, and the caption under the
  card — «Именно так — и везде, где есть такой переключатель» — carries the
  generalisation alone now. **The body is one short paragraph on purpose**: the page
  scrolls, but text pushed under the page dots reads as absent, and the scene above it is
  the same height as on every other page, so about seven lines is the whole budget.
- **That page demonstrates the gesture with the gesture.** A translucent «finger»
  (the touch marker of a screen recording, deliberately not a hand) slides across the
  card while `animateScrollToPage` moves the page under it and the pill follows — one
  `coroutineScope` running both so they cannot drift — then pauses and repeats. The
  moment the user drags the demo pager or taps a tab (`tried`, in `rememberSaveable`),
  the demo stops for good and the caption under it turns into a confirmation: someone
  who has done it does not need it shown again. Both of the finger's values are read in
  `offset { }` / `graphicsLayer { }` lambdas, never in composition — they change every
  frame of the demo. The nested pager hands the drag to the outer one only at its own
  ends, so leaving this page by swipe means first reaching its first or last tab, which
  is a fair price for a page about exactly that.
- **Both layers of a page move at their own speed** (`Modifier.pageParallax`): the scene
  lags the pager by 35 %, the text by 12 %, and each fades to 60 % as it leaves. That is
  what separates pages sliding from slides switching. The offset is read inside
  `graphicsLayer`, or every frame of a swipe would recompose the screen.
- **The top row differs by entrance, and the system back button pages, it does not
  leave.** On first launch the corner holds «Пропустить» — a cross there reads as «close
  the app» — and it fades out on the last page, where «Начать» stands below; on a revisit
  the corner holds the same 36 dp cross `SheetHeader` draws — literally `SheetCircleButton` from `SheetForm.kt`, not a copy, which is how it stays 36 rather than the 48 an `IconButton` with a background on its own modifier renders (see the batch form's breed card) — and the last button reads «Понятно».
  `BackHandler` is enabled only past the first page and goes one page back: on first
  launch nothing is behind the guide, and the system gesture would otherwise close the
  app from page two. On page one it is not intercepted.
- **The CTA is the forms' save button** — 52 dp, `Accent`, radius 16 — so the first
  button a user presses in the app looks like every one after it. The page dots stretch
  the current dot into a bar rather than only recolouring it: width is visible in
  peripheral vision, colour is not.
- **Pages six to eight are the features added after the guide was first written, and they follow its rule: real parts, not drawings.** `QrScene` draws an actual code — `qrModules(QrLink.encode(1))` through the sheet's own `QrImage`, launcher icon included — under a scanner frame whose line sweeps while the page is settled (read only in the `Canvas`), and «Замеры за сегодня» rises under it as what the scan opens. `TimerScene` is the airing card on the real `TimerRing`: fifteen minutes run out in about four seconds, the ring goes red on «Время вышло!», and the measurement row under the card — there from the start as «— мин» — receives the minutes; the per-frame fraction is passed as a lambda into `DemoTimerRunning` so only the ring recomposes. `HatchScene` is the celebration in miniature — count-up tiles, a profit line, «Календарь» and «Моё хозяйство» as the two doors around a hatch — with the real `Fireworks` drawn **over** the card (the bands above and below it are too narrow in a 320 dp stage, the same fallback the dialog itself makes) and composed only while `active`, since it is a frame loop. They stand after «Каждый день под контролем» because they build on it: the reading and the airing are named there, and these pages show the faster way to do them and how it all ends. **A new feature page goes there too, before `Hatch`, which closes the story** — and every page added is one more press of «Далее» before «Начать», so a feature earns a page only when the first five would not let anyone guess it exists.
- AppMetrica: opening from «О приложении» reports «Инструкция»; closing a first-launch guide reports
  «Инструкция пройдена» or «Инструкция пропущена» — a revisit reports neither, so the pair
  stays a completion rate over first launches — from the nav graph like every other
  screen event.

## The ad card: a banner that looks like everything else

Ads used to be a sticky strip in the root `Scaffold`'s `bottomBar`; they are now **`AdBanner` in `ads/AdBanner.kt`** — the only ad composable, and the only Compose file that imports `com.yandex.mobile.ads` (the whole SDK is confined to `ads/`, see the root file). It draws an *inline* Yandex banner inside a white 22 dp card with the 0.8 dp `CardBorder` and an 8 dp inset, so it reads as one more card of the list it stands in rather than as a foreign element pinned to the screen edge.

- **It goes after the first block of a scroll, not at its end** — and that rule was learned by getting it wrong. The first version put every banner last, which reads well on a mockup and is invisible in life: a farm with ten incubators, or an incubator with ten batches, keeps the end of its list permanently below the screen, and «Статистика» has five more cards under the first one. **The two card lists then went one step further and repeat the banner after every third card**, because a single one at the top has the opposite failure of a single one at the bottom: it leaves the screen with the first flick of a finger. `adSlotAfter(index)` in `ads/AdBanner.kt` is that whole rule and `AdSlotTest` pins it: **the first banner sits right under the first card, and the rest follow every three cards** — after cards 1, 4, 7, 10, which zero-based is simply `index % 3 == 0` — with **at most five slots per list**. The first card is singled out because the list opens on it: that banner is the only one a reader of any list is certain to see, and the even three-card step after it is what keeps the rest turning up while scrolling without crowding the screen. The rule needs no length: every non-empty list has a first card, so short lists need no exception of their own. The cap is a memory limit, not a matter of taste: every slot is a live `BannerAdView` with a `WebView` inside, and «one per three» across fifty batches would put a dozen and a half of them on one screen. It applies to the start screen's first page (`itemsIndexed`, not on the archive page — the archive is devices out of service and an ad among them would be the only thing «в работе» — and not under the empty state, since «Добро пожаловать» wants no neighbour) and to the «Закладки» tab, whose empty list keeps its single banner under the dashed «Добавить закладку» — the one case with no card to stand behind. The blocks that are not lists take one banner each: «Статистика» **after `SummaryGrid`**, «Финансы» **after `BalanceCard`**, «Аналитика за день» **after the chart card**, and — these two being short enough to reach the bottom of — the ends of «Настройки» (after `PrivacyNote`) and «О приложении». **Not in the guide and not in a form**: the guide is the one screen that must not look like the product is an ad, and a form is for typing into. A read-only sheet is fair game, which is why «Аналитика за день» has one. **The one banner that stands in a sheet with a form is in the «Замеры за сегодня» block** (`MeasurementsCard`, so both the batch sheet and the incubator measurement sheet), placed at the owner's request between the day's figures and «История замеров» — below the form, never inside it, and at a seam between two parts so it splits neither; its host is `rememberBannerAdHost()` inside the block, as in the day analytics sheet.
- **The two shared tabs carry their own banner, `StatsTab` / `FinanceTab` taking an `adHost: BannerAdHost?`.** They are rendered by both the incubator screen and «Аналитика», and a placement written at each call site would have drifted between the two the first time one of them moved. `null` means «no ad on this tab», which is what a preview or a future third caller gets. `FinanceTab` puts it **before** its `!hasMoney` early return, so a hatchery that has typed no prices — whose tab is two cards long — still gets one.
- **No card until the ad has loaded.** `loaded` is `host.loadedFor == key`, set in `onAdLoaded`; before that the wrapper is `height(0.dp)` with the `BannerAdView` still inside it (a view that is not in the hierarchy has nowhere to load into), and on load the card grows through `animateContentSize`. An empty bordered card would read as a broken widget, and «no ad» is the normal case on an emulator, offline, or with no fill.
- **The width is decided before the request** — `BoxWithConstraints` hands the SDK the card's inner width in dp for `BannerAdSize.inline(width, 120)`, and the `AndroidView` is `key`ed on it, so a rotation makes a new view for the new width.
- **Nothing until `MobileAdsSdk.ready`.** The composable starts the SDK from a `LaunchedEffect` and returns nothing until the init callback flips the flow; the app-open ad usually gets there first, and the banner just finds it ready.
- **The ad follows the theme.** `AdRequest.Builder(...).setPreferredTheme(AdTheme.LIGHT / DARK)` is asked for from `LocalDesignPalette` being `DarkDesignColors` — the same source the card itself is painted from — and the view is `key`ed on it too, so switching «Оформление» re-requests the banner rather than leaving a white ad in a dark list. The app-open ad does the same through `MobileAdsSdk.adThemeFor(context, settings.themeMode)`, reading the app's own night configuration for «Системная».
- **One card per screen, and the view outlives the card.** `rememberBannerAdHost()` is called at screen level and handed to `AdBanner`; the `BannerAdView` lives in that host and the card only borrows it, so a `LazyColumn` item scrolled away or a pager page swiped off does not re-request the ad when it comes back (the first version made six requests per two impressions on a walk across the incubator's tabs). Because one `View` cannot have two parents while a swipe has two pages composed, **each page of a pager gets its own host** — three on the incubator screen, two on «Аналитика», all declared at screen level. **A list that repeats the banner needs one host per slot, and that is `BannerAdHosts`** (`rememberBannerAdHosts()`), a map from slot number to host, again held by the screen. All of this costs nothing until it is reached: a host holds no view until `AdBanner` first composes inside it, so a tab nobody opens and a slot nobody scrolls to never request an ad. `loadedFor` in the host is the key (width + theme) the ad was loaded under, compared with the card's current key — so a rotation or theme switch reads as «not loaded» by itself, with no state reset from inside `AndroidView.factory`.
